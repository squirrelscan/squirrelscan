- New rule `security/exposed-actuator` finds Spring Boot Actuator endpoints that answer anyone (squirrelscan/repo#1961). When probing is `active` it sends read-only `GET` requests to `/actuator`, `/actuator/env`, `/actuator/configprops` and `/actuator/mappings` under `/actuator` and any same-origin actuator base the crawl found, and on an `aggressive` run one `GET /actuator/heapdump` that reads at most 64 bytes. An exposed server writes a heap dump when asked, so a run asks for at most one: none after any heapdump answer other than `401`, `403` or `404` (a confirmed dump, another 2xx, a 5xx, a redirect, an error or a timeout), and `aggressive` is for sites you run. An endpoint counts only when its answer has that endpoint's shape, never on status alone, so a single-page app's catch-all page is not a finding. Spring Boot 1.x's gzipped heap dump counts when it opens with the gzip magic and is sent as a `.hprof` or `.hprof.gz` attachment (evidence `hprof-gzip`). An open `env`, `configprops` or `heapdump` is critical, the index and `mappings` are warnings, and so is a `heapdump` only listed by an open index. Each request has a 10 second timeout, a timeout ends that base, and the rule stops after 30 seconds; a `429`, a bot challenge, a 5xx, a path `robots.txt` disallowed, or a run that did not reach every path is reported as not checked, never as a pass. The heapdump has its own checks (`exposed-actuator-heapdump`, `-heapdump-closed`, `-heapdump-not-checked`): only an `aggressive` run that gets a `401`, `403` or `404` for it under every base clears it, so an `active` run never clears a heap dump an earlier `aggressive` run found. Findings name the endpoint and the kind of evidence, never a value from the response. A path that names a state-changing action, or a `POST`, `PUT`, `PATCH` or `DELETE` call site, is never probed, and on a passive run the rule reports not checked. See [security/exposed-actuator](https://docs.squirrelscan.com/rules/security/exposed-actuator).
