- `security/supabase-rls`, a loud probing rule for Supabase tables anyone can read with the public anon key. It finds the Supabase project and anon key a site ships, then sends one `HEAD /rest/v1/<table>` with `Prefer: count=exact` to each table the site's own code queries, and judges only the status, the content type and the row total in `Content-Range`: a total above zero fails. It never sends a `GET`, never reads a response body and never guesses table names, so no row, value or column name is fetched or stored. It runs only with `--probe aggressive`, not with `--offline`, at most ten requests per audit, and never with a service-role or secret key. A `429`, a bot challenge, an HTML `401`, `403` or `404` page, a network error or a table left out by the caps makes the run not checked (`probe-incomplete`), never a pass, and a table meant to be public can be waived with `[[ignore]]`. See [security/supabase-rls](https://docs.squirrelscan.com/rules/security/supabase-rls). That makes 341 rules, 32 of them in Security (squirrelscan/repo#1959).
