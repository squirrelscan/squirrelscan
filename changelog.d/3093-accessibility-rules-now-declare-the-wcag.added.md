- Accessibility rules now declare the WCAG success criteria they map to, each with its level and WCAG version; the ten whose checks test no success criterion (such as `a11y/heading-order` and `a11y/landmark-one-main`) say why instead, and `a11y/duplicate-id-aria` maps to 4.1.2 Name, Role, Value. JSON issues carry `wcag` and `wcagLevel`, the report has a top-level `wcagByLevel`, and the HTML, Markdown and text reports show the criterion and level. `squirrel audit --wcag-level A|AA|AAA` (or `[rules] wcag_level`) only runs the accessibility rules mapped to a criterion at or below that level (`AA` keeps Level A and AA). Rules with no WCAG criterion are not run under it, at any level including `AAA`. Such a run is marked as a partial audit that names the level (`meta.partialAudit.wcagLevel` in JSON, and a partial-audit line in every format including HTML), is not auto-published (like a `--rule-include` run, only an explicit `--publish` sends it), and an `--rule-include` that selects only rules the level leaves out is refused before the crawl. These automated checks cover part of WCAG; passing them does not mean a site conforms. `a11y/touch-targets` is now tagged 2.5.5 Target Size (Enhanced), Level AAA, and its advice says so. JSON schema version is 1.27. Each accessibility rule page lists its criteria, or why it has none, generated from the rule metadata (squirrelscan/repo#3093).
