# Component-aware findings: before/after evaluation (repo#2307)

Acceptance criterion 8 of repo#2307 asks for a reproducible
before/after comparison of component-aware findings: source provenance,
inspected cases, group-count changes, incorrect and missed merges, and
performance observations, with missing historic DOM evidence recorded
explicitly. This is that record.

## Scope and provenance

- **Source: synthetic fixtures authored for this evaluation.** Fourteen small
  sites (3 to 6 pages each, 60 pages in total, all on `https://eval.example`)
  written as HTML strings in
  `packages/rules/tests/fixtures/component-eval/cases.ts`. No real site
  content, no personal data, no credentials.
- **Generated by the harness at public main `3f1d94b8` plus the evaluation
  files added by the pull request that adds this record**, Bun 1.4.4 on Linux
  x86_64.
- **What ran.** The real `a11y/link-text` and `content/stale-copyright` rules
  (with `current_year` pinned to 2026), then the real report grouping
  (`groupIssuesByCategory`, which calls `componentFixGroups`) and
  `componentFixRollups`. Nothing is mocked.
- **Historic DOM was NOT replayed and no recapture was made.** The frozen
  Product Hunt reports and the crawl store at `/Volumes/BACKUP/squirrel-store`
  were not available in the environment that produced this record. Reports
  alone cannot reproduce DOM ancestry (region nesting, structural signatures
  and subtree ladders come from the page DOM, which a stored report does not
  carry), so this record makes **no claim about the Product Hunt corpus** and
  its numbers must not be extrapolated to it. Replaying that corpus remains
  open work; this evaluation covers the grouping logic on controlled input
  where the right answer is known.
- **Labels are human ground truth.** Each case file lists, for every
  (page, rule, element locator, region nesting) observation, the `fixKey`
  naming the real edit it needs. The labels were written by reasoning about
  the fixture, not read back from the grouping output.

## Metric definitions

| metric | definition |
|---|---|
| observations | `componentOccurrences` entries the rules emitted |
| detections | warn or fail checks per rule. Pinned as a golden in each case (`expect.detections`: sorted `[path, status, message, itemsJson]` rows, checked by hand against the fixture); the test asserts the rules' actual output equals it, which is AC6 for this evaluation set: detection did not change |
| before groups | `groupIssuesByCategory` over the same checks with `componentOccurrences` stripped: the message groups (`GroupedCheck`) a report that predates evidence shows. This is the honest legacy equivalent, but it merges by message shape across pages, so "1 before group" means one message line with a page list, not one repair |
| after groups | every `componentFixGroups` entry (observed-evidence groups and repeated-subtree promotions) |
| rollups | `componentFixRollups` units over the after groups (presentation only; groups stay separate in JSON) |
| affected pages | union of pages in after groups, pages of ungrouped observations, and pages of detections that carry no evidence; must equal the pages that have a detection |
| incorrect merges | after groups whose members carry more than one `fixKey` |
| missed merges | `fixKey`s marked `expectGrouped` whose observations are not all in one observed-evidence group |

Also checked per case and asserted in
`packages/rules/tests/component-findings-eval-2307.test.ts`: no observation
labelled `expectObserved: false` ever lands in an observed-evidence group
(overclaims), group ids and membership are identical under forward, reversed
and shuffled page order, and a stripped (legacy) report
renders through `renderJson`, `renderLlm` and `renderText` without throwing
and without fix groups. Evidence is checked to change presentation only: the
grouped message view (check names, statuses, messages, counts, pages, items)
and the health score (`calculateHealthScore` from audit-engine) are identical
with and without it. That comparison is of the report layer; it is not a
detection check, which is what the golden above is.

## Inspected cases

1. **identical-footer-across-layouts** (4 pages, 4 layouts): the same footer
   with one generic link on all four pages is one observed group covering all
   four, whatever wraps `main`. Right: it is one template.
2. **different-footer-variants** (5 pages): the main footer (3 pages) and the
   shop footer with an extra social section (2 pages) stay two groups and two
   rollups. Right: repairing one template does not repair the other. The family
   rollup did not join them.
3. **same-text-different-locations** (4 pages): "Learn more" in a footer, a
   header, an aside and a second footer with a different
   destination gives three observed groups; the aside link (no landmark, so an
   uncertain observation) is ungrouped. The two footer links stay apart because
   their destinations differ.
4. **two-faulty-elements-in-one-footer** (3 pages): two different bad links in
   one footer are two groups (6 observations) and ONE rollup line, because the
   rollup merges groups with the same root and the same pages. Groups keep the
   distinct edits; only the display combines them.
5. **repeated-cards-with-differing-data** (4 pages, 12 observations): the cards
   are never an observed (site-chrome) group. Repeated-subtree promotion does
   promote them into ONE `repeated-subtree` group across the 4 pages (the card
   skeleton recurs on at least 3 pages and each card is under half of the
   region text), which is the documented weaker attribution. The fixture is a
   templated card, so one template edit really does repair all twelve and the
   group is right; the label says so. A page whose cards are NOT from one
   template would be wrongly merged by this promotion, which is why case 6
   exists. See the findings below.
6. **repeated-cards-hand-authored** (4 pages): the same words in `main` but
   with different markup per page. Nothing recurs structurally, so there are 0
   groups and the legacy page-scoped lines remain. Right.
7. **nested-article-header-vs-site-header** (4 pages, 8 observations): the
   site header link is one observed group over 4 pages; each article header
   link is `content-nested`, not groupable, and ungrouped. Right: the site
   header is a template, an article header is authored with the article.
8. **no-semantic-landmarks** (4 pages): links in plain divs get
   `no-region` (uncertain) from the rule. Repeated-subtree promotion then
   creates ONE `repeated-subtree` group over the 4 pages, never an observed
   one. In this fixture the block really is shared chrome, so the group is
   correct; where such a block is not shared, the same logic would overreach.
   Recorded as promotion behaviour, not as landmark evidence.
9. **one-page-exception** (4 pages): the footer is shared, but one page has a
   different defect in it. Two groups: the shared defect on 3 pages, and the
   exception alone with `affectedPages = 1`. Right.
10. **stale-year-shared-footer** (4 pages): one observed group over 4 pages.
11. **stale-year-footer-variants** (5 pages): different footer templates and
    different years, two groups.
12. **stale-year-article-local-footer** (6 pages): a stale year in a site
    footer on 3 pages is one group; on the 3 pages where only an article
    footer carries the year, the observations are `content-nested` and stay
    ungrouped. Right. (The rule judges the newest year across all footers, so
    an article footer is an observation only on a page where it is the one
    asserting that year.)
13. **mixed-site-order-independence** (6 pages, 17 observations): shared
    footer with two link defects plus a stale year, a shop variant, a blog page
    with its own footer and two cards. Seven observed groups, six rollups.
    Group ids, membership and rollups are identical under forward, reversed and
    shuffled order (the shuffle is a fixed-seed one).
14. **legacy-report-without-evidence** (3 pages): evidence stripped, as a
    report that predates it. 0 observations, 0 fix groups, two message groups
    remain, and the three renderers produce output without throwing and
    without a fix-once line. Right.

## Incorrect and missed merges

- **Incorrect merges: 0 of 24 groups.** No group carries more than one labelled
  fix.
- **Missed merges: 0.** Every `expectGrouped` fix is in exactly one observed
  group.
- **Overclaims: 0.** No observation the rules judged uncertain landed in an
  observed group.
- This is a result about labelled synthetic cases. A different corpus can
  produce incorrect merges, and the cards case shows the mechanism: repeated
  subtree promotion groups structurally identical blocks whether or not one
  template renders them. The `repeated-subtree` attribution exists to mark that
  weaker claim, and nothing here tests how a reader weighs it.

## Known limits

- **Repeated cards.** Repeated-subtree promotion groups structurally identical
  blocks as one `repeated-subtree` group whether or not a single template
  renders them. In `repeated-cards-with-differing-data` the evaluation labels
  all twelve card links as ONE template fix, because the fixture is a templated
  card; it is a labelling choice about that fixture. A page whose cards are
  hand-written but happen to share markup would be grouped the same way, and
  this evaluation cannot tell the two apart. Such a group is never observed
  site-chrome evidence (`attribution` is `repeated-subtree`, and the test
  asserts it). `repeated-cards-hand-authored` shows only that differing markup
  does not promote.
- **No landmarks.** Links in plain divs are uncertain (`no-region`) in the rule,
  and promotion over a recurring block can still group them. In
  `no-semantic-landmarks` that is right because the fixture is one shared
  block; nothing in the DOM proves it, and the evaluation does not test a case
  where such a block is not shared.
- Detection goldens are pinned from a run and hand-checked; they guard against
  change, they are not an independent oracle for what the rules ought to flag.

## Performance observations

Machine: `x86_64`, Linux 6.8.0, Bun 1.4.4. Timings are the minimum of 5
grouping runs per case and one rule run per page in one process, so the
first case includes JIT warmup.

- Rule time for the whole corpus: about 28 ms across 60 pages and 120 rule
  runs, about 0.24 ms per rule run on average. Evidence (hashing, region
  signatures, ladders) is a part of that; this record does not isolate it
  because the rules do not expose an off switch.
- Grouping with evidence: 6.9 ms in total over 14 cases, against 0.3 ms with
  evidence stripped. That is a large ratio on a tiny base. The largest single
  case (17 observations) costs 1.6 ms. On the corpus sizes here it is
  negligible, and it says nothing about thousand-page sites; the
  1,000-occurrence path is exercised by the existing unit tests.
- Heap: about 2 MB retained across the whole run, almost all of it the first
  case (module and parser warmup); later cases are within noise of zero
  (small negative values are collection noise).

## Reproduce

```bash
cd packages/rules
bun test tests/component-findings-eval-2307.test.ts        # 130 tests, the case matrix
cd ../..
bun benchmarks/harness/component-findings-eval.ts            # prints the table
bun benchmarks/harness/component-findings-eval.ts --json out.json --repeats 5
```

Everything except the timing and heap columns is deterministic. The JSON also
holds every group (id, pages, fix keys, members) and the rollup summaries.

## Not covered

- The frozen Product Hunt corpus and any real site (see provenance).
- Rules other than `a11y/link-text` and `content/stale-copyright`, the only
  two that emit `componentOccurrences` today.
- Rendered-DOM versus raw-HTML differences (all fixtures are served as raw
  HTML, `rendered: false`).
- Corpora larger than six pages per site.
