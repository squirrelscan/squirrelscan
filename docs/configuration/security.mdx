The `[security]` section sets the **probing intensity** of an audit. Probing is
one of the [audit level's](/guides/audit-levels) settings, next to the page
budget (`--level`, `--max-pages`) and rendering (`--render-mode`). It says how
hard each page is poked beyond what the crawl already fetched.

## Configuration

```toml
[security]
probe = "active"
budget = "30s"
```

Both keys are optional. Leave them out and the audit level picks the default
(see below). Setting `probe` to a value other than the level's makes the audit
custom.

## Options

### `probe`

**Type:** `"passive"`, `"active"` or `"aggressive"`
**Default:** the audit level's: `"passive"` for quick, `"active"` for surface and full

| Level | What it sends |
|-------|---------------|
| `passive` | No probe rules. The audit runs today's rules and passive rules only, plus the [discovery probes](/configuration/crawler#discovery-probes) unless they are disabled. |
| `active` | Passive, plus quiet probes: a handful of requests that look like normal traffic. |
| `aggressive` | Active, plus loud probes: many requests and many 404s. It can trip a WAF. |

`aggressive` is never a default. You must ask for it, here or on the command
line.

<Warning>
Aggressive probing requests paths that `robots.txt` disallows, on purpose.
Only use it on websites you own or are authorized to test.
</Warning>

```toml
[security]
probe = "aggressive"
```

### `budget`

**Type:** duration string or number of seconds
**Default:** `"30s"` for `active`, `"2m"` for `aggressive`

A wall-clock cap for **all** probing in one audit, shared by every probing rule.
Once it runs out, no new probe starts. Write it as `"500ms"`, `"30s"`, `"2m"` or
`"1h"`, or as a plain number of seconds. The maximum is one hour.

```toml
[security]
budget = "45s"
budget = 45      # the same, in seconds
```

A value that is not a positive duration of at most an hour fails config
validation, so a typo never becomes an unbounded budget.

## Defaults

| Context | Default level |
|---------|---------------|
| CLI audit at the quick level (the signed-out default) | `passive` |
| CLI audit at the surface or full level (the signed-in default) | `active` |
| Cloud audit, website ownership verified | the audit level's |
| Cloud audit, website ownership not verified | `passive`, locked |

A locked cloud audit stays passive whatever you ask for. Asking for `active` or
`aggressive` there fails with a message that says why, and how to verify
ownership of the website. It is never lowered without telling you.

## Precedence

Highest first:

1. `--probe <level>` (or `-P`)
2. `--passive`, `--aggressive` or `--pentest`
3. `[security] probe`
4. The audit level's probe setting

For the budget: `--probe-budget`, then `[security] budget`, then the level's
default.

## Rules that probe

These rules send requests only when probing is `active` or `aggressive`. Below
the level a rule needs, it records one skipped check and sends nothing. The GraphQL,
API, auth endpoint, admin endpoint, open redirect, query error, actuator, exposed-files and exposed-backups probes go only to the audited origin, and the Supabase probe only to the project host the site's own scripts name; see below for the form check. `--offline` does not turn them off: offline is about which hosts are requested, passive is about probing, and they are separate. An offline `surface` or `full` run still probes unless you pass `--passive` (see [Offline and passive are separate](/cli/audit#offline-and-passive-are-separate)). The Supabase probe is the exception: it requests another host, so `--offline` skips it.

| Rule | What it sends | Level |
|------|---------------|-------|
| [`security/graphql-introspection`](/rules/security/graphql-introspection) | One `GET /graphql?query={__schema{types{name}}}` per GraphQL endpoint, at most five | `active` |
| | One `POST` of the same read-only query, only when the `GET` answer is GraphQL without a schema | `aggressive` |
| [`security/graphql-get-mutations`](/rules/security/graphql-get-mutations) | One `GET /graphql?query=mutation{__typename}` per GraphQL endpoint, at most five. The no-op mutation names no schema field and cannot write | `active` |
| [`security/unauthenticated-api`](/rules/security/unauthenticated-api) | One `GET` per same-origin API endpoint the audit found, at most ten, with no cookies, no `Authorization` header and no query string. Never a path that only takes `POST`, `PUT`, `PATCH` or `DELETE`, and never a session or state-changing path such as `login`, `logout`, `verify` or `webhook` | `active` |
| [`security/json-sensitive-fields`](/rules/security/json-sensitive-fields) | One `GET` per same-origin API endpoint found in your pages and scripts whose call site uses `GET` or states no method, at most ten. No cookies, no request body | `active` |
| [`security/exposed-files`](/rules/security/exposed-files) | One `GET` to a random path (the baseline), then one request per path on a fixed list of 20 sensitive files such as `/.git/HEAD`, `/.env` and `/db.sql`, each a `GET`. Stops on a `429` or a bot challenge | `aggressive` |
| [`security/exposed-backups`](/rules/security/exposed-backups) | Per crawled server-side file (such as `/shop/cart.php`), at most 15 files: one `GET` each for six sibling names in the same directory (`cart.php.bak`, `cart.php~`, `.cart.php.swp`, `cart.php.old`, `cart.bak`, `cart.php.zip`), plus one `GET` for the same shape of a random file name when a sibling looks exposed. At most 120 requests per run. Stops on a `429` or a bot challenge | `aggressive` |
| [`security/auth-endpoint-disclosure`](/rules/security/auth-endpoint-disclosure) | One `GET` per current-user or session endpoint (such as `/api/me` or `/api/session`), at most six. No cookies, no `Authorization` header, no body: credentials are never submitted | `active` |
| [`security/open-redirect`](/rules/security/open-redirect) | Per same-origin URL with a redirect-shaped query parameter (`next`, `url`, `returnTo` and the like), at most ten: one `GET` with that parameter set to `https://squirrelscan-redirect-probe.invalid/`, and a second with `//squirrelscan-redirect-probe.invalid/` when the first is not redirected off-site. The redirect is never followed | `active` |
| [`security/query-error-fuzz`](/rules/security/query-error-fuzz) | Per same-origin URL with a query string, one unmodified `GET` (the baseline), then per parameter, at most eight, one `GET` per token with only that parameter changed to a quote, a double quote, `%00`, `[]`, `99999999999999999999` or `-1`. A parameter stops at its first finding, and a whole run stops at 60 requests, a `429` or a bot challenge. Never a `POST`, `PUT` or `DELETE`, no cookies, redirects not followed, at most 64 KB read | `aggressive` |
| [`security/client-side-authz`](/rules/security/client-side-authz) | One unauthenticated `GET` per admin API endpoint your pages and scripts reference (a path word such as `admin`, `staff` or `internal`), at most eight. Never a path that names an action, never a URL only called with a write method, and never the query string | `active` |
| [`security/exposed-actuator`](/rules/security/exposed-actuator) | One `GET` each to `/actuator`, `/actuator/env`, `/actuator/configprops` and `/actuator/mappings` per actuator base path, at most three bases | `active` |
| | One `GET /actuator/heapdump` with `Range: bytes=0-63`, reading at most 64 bytes, whether or not an open index lists it. Spring Boot 1.x's gzipped dump counts when it opens with the gzip magic and is sent as a `.hprof` or `.hprof.gz` attachment. At most one per run: none after any heapdump answer other than `401`, `403` or `404`, including a timeout. An `aggressive` run asks for the heap dump, and an exposed server writes one when asked, which costs that server a pause and disk space, so use `aggressive` only on sites you run. | `aggressive` |
| [`security/supabase-rls`](/rules/security/supabase-rls) | One `HEAD /rest/v1/<table>` with `Prefer: count=exact` per table the site's own code names, to its Supabase project host (`<ref>.supabase.co`), with the anon key the site ships, at most 30 tables per project and 40 in all, the first by name. Never a `GET`, never a query string, and no response body is read, so no row is ever read: only the status and the `Content-Range` row total. A `429` or a bot challenge stops the run as not checked. `aggressive` is for sites you run. Only when the audit may request other hosts (not `--offline`, external link checks on) | `aggressive` |
| [`crawl/custom-404`](/rules/crawl/custom-404) | One `GET` to a random path that cannot exist, such as `/squirrelscan-missing-page-<hex>`. No cookies, no redirect followed, at most 256 KB read | `active` |
| [`reliability/broken-forms`](/rules/reliability/broken-forms) | One `HEAD` per distinct form action URL the crawl did not fetch, then one `GET` when the `HEAD` is refused or fails. Never a `POST`. A form action on another site is probed only online with external link checks on; an offline run stays on the audited site | `active` |

The GraphQL endpoints are the ones the audit found in your pages and scripts,
plus `/graphql` and `/api/graphql`. A path that names a state-changing action,
such as `logout` or `delete`, is never probed. Below `aggressive`, a path that
`robots.txt` disallows is skipped, read as the crawl's robots group
([`robots_user_agent`](/configuration/crawler#robots_user_agent), or
`User-agent: *` when the file has no group for it). Probe requests carry no cookies and do not
follow redirects.

The actuator base paths are `/actuator` plus any path with an `actuator`
segment found in your pages and scripts. A discovered path that names a
state-changing action, or whose call site uses `POST`, `PUT`, `PATCH` or
`DELETE`, is never used.

An `aggressive` run asks for the heap dump, and an exposed server writes one when asked, which costs that server a pause and disk space, so use `aggressive` only on sites you run.
The `Range` header does not stop the dump being written. squirrel asks for at
most one heap dump per run: after any heapdump answer other than `401`, `403`
or `404` (a confirmed dump, another 2xx, a 5xx, a redirect, an error, or a
timeout, since a large heap can take longer than the timeout to start
answering), no other base is asked.

## Discovery probes turn probing off

When `[crawler] disable_discovery_probes = true` or `--disable-discovery-probes`
is set, probing resolves to `passive` and no probe sends a request. If you also
asked for a higher level, the audit prints a note saying why it stayed passive.
See [Discovery probes](/configuration/crawler#discovery-probes).

## Turn rule families on and off

Probing intensity sets how loud probes may be, not which ones run. Use the
[rules configuration](/configuration/rules) (`[rules] enable` and `disable`) or
`--rule-include` and `--rule-exclude` to pick rule families.
