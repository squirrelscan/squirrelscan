The `[output]` section controls how squirrelscan formats and saves audit reports.

## Configuration

```toml
[output]
format = "console"
path = ""
```

## Options

### `format`

**Type:** `"console"` | `"text"` | `"json"` | `"html"` | `"markdown"` | `"llm"` | `"xml"`
**Default:** `"console"`

Output format for audit reports.

**Available Formats:**

- `"console"` - Rich terminal output with colors and formatting
- `"text"` - Plain text output without colors
- `"json"` - Machine-readable JSON for automation
- `"html"` - Interactive HTML report in browser
- `"markdown"` - Markdown format for documentation
- `"llm"` - Compact token-optimized XML/text for coding agents (40% smaller than xml)
- `"xml"` - Verbose structured XML for enterprise integration

**Note:** The `sarif` format is only available via the `report` command, not during `audit`. See [Reports documentation](/reports) for details.

---

### `"console"` (default)

Rich terminal output optimized for human readability.

**Features:**

- Colored output (red/yellow/green for fail/warn/pass)
- Progress indicators during crawl
- Summary statistics
- Issue grouping by rule
- Interactive formatting

**Example output:**

```text
🔍 Crawling https://example.com...
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✓ Fetched 100 pages in 12.3s

📊 Running audit rules...
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ISSUES FOUND (23)

❌ core/meta-title (8 pages)
  /about - Missing page title
  /contact - Title too short (12 chars, min 30)

⚠️  links/broken-links (15 links)
  /blog/post-1 → /missing-page (404)

✓ All other checks passed

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Health Score: 78/100 (Good)
```

**Configuration:**

```toml
[output]
format = "console"
```

**Use cases:**

- Local development
- Manual audits
- Terminal-based workflows
- Quick visual feedback

### `"json"`

Machine-readable JSON output for automation and integrations.

**Features:**

- Health score with group and category scores
- Pass, warning, fail and skipped counts
- Findings grouped by rule, with affected pages
- Checks skipped because a scan limit was hit, listed apart from findings
- Audit status and metadata

**Example structure:**

```json
{
  "meta": {
    "version": "0.0.105",
    "baseUrl": "https://example.com",
    "timestamp": "2026-01-17T10:30:00.000Z",
    "totalPages": 100
  },
  "status": "completed",
  "score": {
    "overall": 78,
    "grade": "C",
    "groups": [],
    "categories": [{ "name": "Core SEO", "score": 82 }]
  },
  "summary": { "passed": 1204, "warnings": 15, "failed": 8, "skipped": 2 },
  "issues": [
    {
      "ruleId": "core/meta-title",
      "name": "Meta title",
      "description": "...",
      "category": "Core SEO",
      "group": "seo",
      "severity": "error",
      "checks": [
        {
          "name": "meta-title",
          "status": "fail",
          "message": "Missing page title",
          "affectedPages": ["https://example.com/about"],
          "affectedPagesCount": 1,
          "affectedPagesHasMore": false
        }
      ]
    }
  ],
  "skippedChecks": [
    {
      "ruleId": "content/hidden-text",
      "name": "Hidden text",
      "check": "hidden-text",
      "reason": "scan-truncated",
      "pages": ["https://example.com/huge-page"],
      "pagesCount": 1,
      "pagesHasMore": false
    }
  ]
}
```

See the [JSON output schema](#json-output-schema) for every key.

**Configuration:**

```toml
[output]
format = "json"
path = "reports/audit.json"  # Optional: save to file
```

**Use cases:**

- CI/CD pipelines
- Automated testing
- Data analysis
- Integration with other tools
- API responses

**CLI usage:**

```bash
# Output to stdout
squirrel audit https://example.com --format json

# Save to file
squirrel audit https://example.com --format json --output report.json

# Pipe to jq for filtering
squirrel audit https://example.com --format json | jq '.score.overall'
```

### `"html"`

Interactive HTML report that opens in your browser.

**Includes:**

- Health score and the four group scores
- Issues to fix first, and every finding banded by severity, filterable by group
- A **Copy fix prompt** button on each finding for your coding agent
- The same findings by page
- Site profile, tech stack and the entity map

It is one standalone file that makes no network request when opened. See [the html format](/reports#html) for each section and the fix prompts.

**Configuration:**

```toml
[output]
format = "html"
path = "reports/audit.html"  # Optional: custom path
```

**Default behavior:**

If `path` is not specified, HTML report is saved to:

```text
reports/audit-{timestamp}.html
```

**Use cases:**

- Client presentations
- Team sharing
- Visual analysis
- Stakeholder reports
- Archive audits

**CLI usage:**

```bash
# Generate and open in browser
squirrel audit https://example.com --format html

# Save to custom location
squirrel audit https://example.com --format html --output reports/my-audit.html
```

### `"llm"`

**Compact token-optimized format for coding agents** - hybrid XML/text structure designed to minimize tokens while maintaining structured data.

**Features:**

- 40-70% smaller than verbose XML format
- 1-space indentation for token efficiency
- Inline attributes instead of nested elements
- Text prefixes (`Desc:`, `Fix:`, `Pages:`, `Items:`)
- Comma-separated lists for pages and URLs
- Hybrid XML/text structure for easy parsing

**Size Comparison:**

For a 51-page audit:
- XML format: 209KB
- LLM format: 125KB (40% reduction)

**Format Structure:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<audit version="0.0.13">
<site url="https://example.com" crawled="42" date="2025-01-18T10:30:00Z"/>
<score overall="87" grade="B">
 <cat name="Core SEO" score="100"/>
 <cat name="Links" score="85"/>
</score>
<summary passed="83" warnings="13" failed="9"/>
<issues>
 <rule id="content/word-count" severity="warning" category="Content" group="seo" status="warn">
  Low word count detected
  Desc: Pages should have sufficient content for good SEO
  Fix: Add more relevant content to improve page depth
  Pages (3): /blog/post-1, /blog/post-2, /about
 </rule>
</issues>
</audit>
```

**Use Cases:**

- Piping to Claude Code, Cursor, GPT, or other coding agents
- Token-limited API contexts (cost optimization)
- Agent-based workflows requiring structured output
- AI code review and analysis

**CLI usage:**

```bash
# Direct output during audit
squirrel audit https://example.com --format llm

# Or export from stored audit
squirrel report <audit-id> --format llm

# Pipe directly to a coding agent
squirrel audit https://example.com --format llm | claude "analyze and prioritize fixes"
```

See [OUTPUT-FORMAT.md](https://github.com/squirrelscan/skills/blob/main/skills/audit-website/references/OUTPUT-FORMAT.md) for complete format specification.

### `"xml"`

**Verbose structured XML format** for enterprise integration, archival, and strict schema validation.

**Features:**

- 2-space indentation for readability
- Fully nested elements (all metadata in dedicated tags)
- Explicit structure with strict schema compliance
- All information preserved without abbreviation
- Enterprise-ready for XML parsers and validators

**Format Structure:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<squirrelscan-audit version="0.0.117">
  <site>
    <url>https://example.com</url>
    <pages-crawled>42</pages-crawled>
    <audit-date>2025-01-18T10:30:00.000Z</audit-date>
    <scan-scope origin="cli" crawled="42" max-pages="100" capped="false"/>
  </site>
  <health-score overall="87" grade="B">
    <category name="Core SEO" score="100"/>
  </health-score>
  <summary passed="180" warnings="6" failed="2"/>
  <issues>
    <rule id="content/word-count" severity="warning" category="Content" group="seo">
      <name>Word Count</name>
      <description>Pages should have sufficient content</description>
      <solution>Add more relevant content</solution>
      <check name="word-count" status="warn">
        <message>Low word count: 150 words (min: 300)</message>
        <affected-pages count="2" examples="2" has-more="false">
          <page url="https://example.com/blog/post-1"/>
          <page url="https://example.com/blog/post-2"/>
        </affected-pages>
      </check>
    </rule>
  </issues>
</squirrelscan-audit>
```

`<scan-scope>` says where the audit ran (`origin`: `cli`, `ci` or `cloud`), how many pages it crawled, the page limit in force (`max-pages`), and whether that limit stopped the crawl (`capped`). `requested-max-pages` appears only when the limit you asked for was lowered, and `stop-reason="time"` only when the crawl time budget ended the crawl. `unfetched` appears when the crawl stopped with in-scope URLs still queued: pages it found (in a sitemap, linked from a crawled page, or carried from an earlier audit) but never fetched. `crawled` plus `unfetched` is how many pages the crawl knew of. It is a floor: the links on the pages still queued are unknown, so the site may have more. On a rate-limited run, the `unfetched` count on `<rate-limited>` already includes these. A report from before scan scope existed has no `<scan-scope>`. A white-label report's root element is `<audit>`.

**Comparison: LLM vs XML**

| Aspect | LLM Format | XML Format |
|--------|-----------|------------|
| Size (51 pages) | 125KB | 209KB |
| Indentation | 1 space | 2 spaces |
| Structure | Hybrid XML/text | Pure XML |
| Metadata | Inline attributes | Nested elements |
| Best For | Coding agents, tokens | Enterprise, archival |

**Use Cases:**

- Enterprise data integration and ETL pipelines
- Long-term audit archival with full metadata
- Schema validation and compliance requirements
- XML processing tools and libraries
- Integration with enterprise systems (SAP, Oracle, etc.)

**CLI usage:**

```bash
# Direct output during audit
squirrel audit https://example.com --format xml --output audit.xml

# Or export from stored audit
squirrel report <audit-id> --format xml --output audit.xml

# Validate with xmllint
squirrel audit https://example.com --format xml | xmllint --format -
```

## `path`

**Type:** `string`
**Default:** `""` (empty = stdout for console/json, auto-generate for html)
**Required:** No

Output file path for saving reports.

**Behavior:**

**Empty (default):**
- `console` format → stdout (terminal)
- `json` format → stdout
- `html` format → `reports/audit-{timestamp}.html`

**Specified:**
- Saves to exact path provided
- Creates directories if needed
- Overwrites existing files

**Examples:**

Save JSON to file:
```toml
[output]
format = "json"
path = "reports/latest.json"
```

Save HTML with custom name:
```toml
[output]
format = "html"
path = "audit-reports/example-com-2026-01-17.html"
```

Console to file (unusual):
```toml
[output]
format = "console"
path = "logs/audit.log"
```

**Path expansion:**

Relative paths are relative to current working directory:

```toml
[output]
path = "reports/audit.json"
# Resolves to: /path/to/project/reports/audit.json
```

Absolute paths work too:

```toml
[output]
path = "/Users/you/audits/report.json"
```

**Directory creation:**

squirrelscan automatically creates parent directories:

```toml
[output]
path = "reports/2026/january/audit.json"
# Creates reports/2026/january/ if needed
```

## Configuration examples

### console output (default)

Terminal output with colors:

```toml
[output]
format = "console"
```

Run:
```bash
squirrel audit https://example.com
```

### JSON for CI/CD

Save JSON report for automated testing:

```toml
[output]
format = "json"
path = "reports/audit.json"
```

Then in CI:
```bash
squirrel audit https://staging.example.com
cat reports/audit.json | jq '.score.overall'
```

---

### HTML for sharing

Generate shareable HTML report:

```toml
[output]
format = "html"
path = "reports/client-audit.html"
```

Share the file:
```bash
squirrel audit https://client.com
# Send reports/client-audit.html to client
```

---

### Multiple outputs

Use CLI to generate multiple formats:

```bash
# Console output
squirrel audit https://example.com

# JSON for automation
squirrel audit https://example.com --format json --output reports/data.json

# HTML for sharing
squirrel audit https://example.com --format html --output reports/visual.html
```

## CLI override

CLI flags override config file:

**Config file:**
```toml
[output]
format = "console"
path = "reports/default.json"
```

**CLI override:**
```bash
squirrel audit https://example.com --format json --output custom.json
# Uses: format=json, path=custom.json
```

**Precedence:**

1. CLI flags (`--format`, `--output`) - Highest
2. Config file (`[output]` section)
3. Built-in defaults - Lowest

## Output schema

### JSON output schema

Top-level keys. Keys marked optional are omitted when they do not apply.

```json
{
  "meta": {
    "version": "string",
    "schemaVersion": "1.2",
    "baseUrl": "string",
    "requestedUrl": "string (optional; deep start URL)",
    "timestamp": "ISO 8601 date",
    "totalPages": 0,
    "maxPages": 0,
    "requestedMaxPages": 0,
    "stopReason": "time",
    "unfetched": 0,
    "seedRedirect": {},
    "originalUrl": "string",
    "redirectChain": [{ "url": "string", "status": 0 }],
    "coverage": {},
    "auditLevel": {},
    "rulesCache": {}
  },
  "status": "completed|partial|failed|blocked",
  "statusReason": "string",
  "statusReasonCode": "string",
  "maxDuration": { "seconds": 0, "unfetchedPages": 0, "pagesNotEvaluated": 0, "siteChecksCut": false },
  "rateLimited": { "pages": 0, "hosts": [] },
  "refusedFetches": [],
  "wafBlocked": { "total": 0, "providers": [], "pages": [] },
  "wafSuspect": { "total": 0, "providers": [], "pages": [] },
  "score": {
    "overall": 0,
    "grade": "A|B|C|D|F|N/A",
    "groups": [
      { "group": "seo", "name": "string", "score": 0, "passed": 0, "warnings": 0, "failed": 0, "total": 0 }
    ],
    "categories": [{ "name": "string", "score": 0 }]
  },
  "summary": { "passed": 0, "warnings": 0, "failed": 0, "skipped": 0 },
  "pages": [{ "url": "string", "status": 200, "ruleCount": 0 }],
  "pagesTotal": 0,
  "pagesTruncated": false,
  "issues": [
    {
      "ruleId": "core/meta-title",
      "name": "string",
      "description": "string",
      "solution": "string",
      "category": "string",
      "group": "string",
      "subcategory": "string",
      "severity": "error|warning|info",
      "checks": [
        {
          "name": "string",
          "status": "fail|warn",
          "message": "string",
          "affectedPages": ["string"],
          "affectedPagesCount": 0,
          "affectedPagesHasMore": false,
          "items": [],
          "details": {}
        }
      ]
    }
  ],
  "skippedChecks": [
    {
      "ruleId": "content/hidden-text",
      "name": "string",
      "check": "hidden-text",
      "reason": "scan-truncated",
      "pages": ["string"],
      "pagesCount": 0,
      "pagesHasMore": false
    }
  ],
  "notChecked": [
    {
      "ruleId": "links/broken-external-links",
      "name": "string",
      "check": "broken-external-links",
      "reason": "external-links-not-checked",
      "message": "string"
    }
  ],
  "passedRules": [
    {
      "ruleId": "core/canonical",
      "name": "string",
      "category": "string",
      "scope": "page|site",
      "pages": 0
    }
  ],
  "editorSummary": {},
  "technologies": {},
  "structure": {},
  "entities": {},
  "siteProfile": {}
}
```

**Unreachable start URL:** when the start URL cannot be reached the audit writes `{ status: "unreachable", url, statusReasonCode, statusReason, message }` instead of a full report and exits `5` (see [Unreachable start URLs](/cli/audit#unreachable-start-urls)).

**Always present:** `meta`, `status`, `score`, `summary`, `issues`. `meta.schemaVersion` is the schema version of the report, `major.minor`: `1.1` added the opt-in `pages` list, and `1.2` added the optional `meta.requestedUrl` field for a deep start URL. A report without `meta.schemaVersion` predates 1.1 and is read as `1.0`. A new optional field bumps the minor version and never changes the meaning of an existing one. `pages`, `pagesTotal` and `pagesTruncated` appear only with [`--include-pages`](/cli/audit#pages-list): `pages` lists every crawled page as `url`, `status` (HTTP status) and `ruleCount` (distinct rules that reported on it, skipped checks not counted), cut at 2,000 entries, with `pagesTotal` the real count and `pagesTruncated` `true` when the cut dropped entries. The rest are optional. `statusReason` and `statusReasonCode` appear when `status` is `failed` or `blocked` and on a `partial` report cut short by [`--max-duration`](/cli/audit#time-limit), where the code is `max_duration` and a `maxDuration` object (`seconds`, `unfetchedPages`, `pagesNotEvaluated`, `siteChecksCut`, `resourceChecksCut`, `probesSkipped`, `pagesTooLarge` and `tooLargePages`) says what was left. `meta.maxPages`, `meta.requestedMaxPages`, `meta.stopReason`, `meta.unfetched`, `meta.canonicalVariants`, `meta.seedRedirect`, `meta.originalUrl`, `meta.redirectChain`, `meta.coverage`, `meta.auditLevel` and `meta.rulesCache` appear when they apply. `meta.originalUrl` and `meta.redirectChain` appear when the start URL redirected to another site and the redirect was followed (see [Start URLs that redirect](/cli/audit#start-urls-that-redirect)): `baseUrl` is then the destination, and the chain lists every URL requested, each with the status it answered. `meta.coverage` (smart audits) counts `auditedPages` of `knownPages` and the `carriedFindings` kept from earlier audits; `pagesWithStaleCarry` appears when pages this run crawled still carry findings no run has re-observed, which means a rule gave no verdict on them (skipped, or inconclusive) rather than a fix; a finding the run reconfirmed but clipped from a capped report does not count. A rule whose fresh result on a re-crawled page is a plain `info` (such as `No form inputs found`) has given its verdict, so the page's earlier findings of that rule resolve; an `info` that says the rule could not judge the page (content too short, markup unreadable, page type not classified) is marked inconclusive by the rule, is not evidence the page is clean, and the earlier findings carry. `meta.canonicalVariants` counts crawled pages that are counted with their canonical page instead of as pages of their own, and `meta.canonicalVariantPages` lists the first 100 of them with the page each is counted with (see [Query-string variants](/cli/audit#query-string-variants)): `meta.totalPages`, every affected-page count and the entity map's page lists and `entities.summary.pagesTotal` are of canonical pages (a node's `morePages` count is not re-counted), and the scan line and `<scan-scope canonical-variants>` say how many were folded. `meta.unfetched` counts the in-scope URLs the crawl had queued but never fetched when it stopped. Added to the pages this run crawled (`meta.coverage.auditedPages` on a smart audit, `meta.totalPages` otherwise) it is a lower bound on the pages the crawl found. On a rate-limited run, `rateLimited.unfetched` already includes it. `meta.scriptsEvaluated` is the number of first-party scripts the script rules (file size, minification, secrets, source maps) were given, counting any that failed to fetch, the same with or without [`store_scripts`](/configuration/storage#store_scripts); it is local only and not published. `meta.auditLevel` is the [audit level](/guides/audit-levels) the audit ran at: `level` (a level's name, or `custom`), `basedOn`, `changes` (the settings changed from the level) and `settings` (every setting's value: the effective settings of this run, not the level's defaults). On an `--offline` run `offline` is `true` and `settings` has `cloudChecks`, `externalLinks` and `render` switched off, because nothing was rendered or checked in the cloud, while `level` and `basedOn` still name the level you asked for. The text, markdown, HTML and LLM outputs say the same in their audit level line. `rateLimited`, `refusedFetches`, `wafBlocked`, `wafSuspect` (stored pages that look like a provider's refusal without a block marker; they were audited, see [blocked by a WAF](/guides/failed-audits#blocked-by-waf)), `editorSummary`, `technologies`, `structure`, `entities` and `siteProfile` appear when the audit produced that data. `editorSummary.priorities` is the [editor's summary](/cloud/editor-summary) ranked to-do list: each entry has `title`, `why`, `action`, `effort` (`quick-win`, `moderate` or `significant`), `ruleIds` and `technologies`.

**Issues:** `issues` holds findings only. Every check in it has status `fail` or `warn`. `affectedPages` is a sample, and `affectedPagesCount` is the true total, so compare the two (or read `affectedPagesHasMore`) before treating the list as complete.

**Skipped checks:** `skippedChecks` lists checks a rule could not finish evaluating, so an absence of issues on those pages does not mean they are clean. It appears only when at least one check was skipped. Skipped checks are never part of `issues`, and do not count toward `passed`, `warnings`, `failed` or the score.

| Field | Meaning |
|-------|---------|
| `ruleId` | Rule that skipped, e.g. `content/hidden-text` |
| `name` | Rule display name |
| `check` | Check name within the rule |
| `reason` | Why it was skipped: `scan-truncated` (the page hit the rule's scan limit and was only partly scanned: `content/hidden-text`, `content/dev-leakage`) `rule-timed-out` (the rule ran past its time budget and was not evaluated; the audit records it once, and `pagesCount` is how many pages hit the budget, so `pages` may be shorter or empty) or `rule-errored` (the rule hit an internal squirrelscan error and was not evaluated: a defect in squirrel, not in your pages). More reasons may be added, so treat unknown values as a skip |
| `pages` | Skipped page URLs. A sample when `pagesHasMore` is true |
| `pagesCount` | True number of skipped pages |
| `pagesHasMore` | `pagesCount` is larger than `pages.length` |

`summary.skipped` is the sum of `pagesCount` across `skippedChecks`, and is 0 when none were skipped.

A consumer that closes a finding when a rule stops reporting it should leave the pages in `skippedChecks` for that rule open, because the rule did not finish looking at them.

**Info checks:** `infoChecks` lists the notes rules recorded with status `info`, for example `crawl/robots-meta-conflict`'s `redundant-noindex` ("2 page(s) blocked in robots.txt also have noindex") or "No dialog elements found". An info check is neither a finding nor a skip: it is never part of `issues`, and it never changes `passed`, `warnings`, `failed` or the score. It appears only when at least one was recorded.

| Field | Meaning |
|-------|---------|
| `ruleId`, `name`, `check` | The rule and the check, as in `skippedChecks` |
| `message` | The check's message (the first, when the check repeats), cut at 500 characters |
| `pages` | Up to 10 page URLs, sorted |
| `pagesCount` | True number of pages |
| `pagesHasMore` | `pagesCount` is larger than `pages.length` |

Many rules record an info check on every page where they had nothing to check, so on a typical audit this list is long. The LLM output leaves them out unless you pass `--include-info` to `squirrel audit` or `squirrel report`; then it lists the first 25 with three pages each and counts the rest.

**Not checked:** `notChecked` lists rules whose check did not run for this audit, so an absence of issues for them means nothing was checked. It appears only when at least one rule was not checked. An entry has `ruleId`, `name`, `check`, `reason` and `message`, and, for a rule that hit an internal error (see [A rule that throws](/rules#a-rule-that-throws)), `pages`: the first ten pages it was not evaluated on. Like skipped checks, these are never part of `issues` and never scored.

| Field | Meaning |
|-------|---------|
| `ruleId` | Rule that was not checked, e.g. `links/broken-external-links` |
| `name` | Rule display name |
| `check` | Check name within the rule |
| `reason` | `external-links-not-checked`: external link checking was off (`--offline`, `--no-external-links`, `[external_links] enabled = false`, or switched off for the website or run). `external-links-over-cap`: more external links than the audit's limit (`[external_links] max_links`, by default the page budget or 200, whichever is more); the most-linked were checked. `external-links-out-of-time`: a cloud audit's link check ran out of time, or waited too long on one request, before these links were answered. `link-targets-not-fetched`: the crawl did not follow links (Quick level, Sitemap crawl strategy) and some internal link targets were fetched neither by the crawl nor by the internal link check (one `HEAD` per target, on by default; `[internal_links] enabled = false` or `--no-internal-links` turns it off). `Crawl capped before the frontier was exhausted`: the crawl stopped at its page cap with pages still queued, so `links/orphan-pages`, `links/weak-internal-links` and `links/no-contextual-inbound` could not count every inbound link (`--max-pages` or `[crawler] max_pages` raises the cap) |
| `message` | The line every report format shows, e.g. `Not checked: Broken External Links. External link checking was off for this audit, so 12 external link(s) on the audited pages were not checked. Turn external link checks on to check them: in the CLI pass --external-links (or drop --no-external-links, --offline, or external_links.enabled = false); in the cloud they are a website setting.` |

The console, text and Markdown reports list each notice, without the `Not checked:` lead-in, under a Not checked heading in [Report detail](#report-detail) at the end of the report. The HTML report shows each one, with the `Not checked:` lead-in, among the dismissible notices at the top of the page. The LLM report has a `<not-checked>` element with one `<rule>` per entry inside its `<report-detail>` element, and the XML report has the same element at the top level of the document. A consumer that closes a finding when a rule stops reporting it should leave findings for these rules open.

**Blocked pages:** `wafBlocked` appears when a WAF or bot manager answered a page with a challenge or block page. `total` counts every blocked page, `providers` names the providers, and `pages` lists up to 50 of the pages that were not the audited one, each with `url`, `status`, `provider`, `signal` (what matched) and `code`. When the audited page itself was blocked, `status` is `blocked` and `seed` carries the same fields; its `code` is `blocked_by_<provider>` (`blocked_by_cloudflare`, `blocked_by_aws_waf`, or `blocked_by_waf` when no provider was named). Blocked pages are never audited or scored. See [blocked by a WAF or bot manager](/guides/failed-audits#blocked-by-waf).

**Passed rules:** `passedRules` appears only with [`--include-passed`](/cli/report#list-what-passed), and only when at least one rule passed. Each entry is a rule with at least one passing check and no warning or error. `scope` is the rule's own (`page` or `site`). `pages` counts the distinct pages with a passing check. It is usually 0 for a site rule, and 0 for a page rule whose passing checks carry no page, which the other formats show as `pages not recorded`. A failed or blocked audit lists none.

**Use for:**
- Automated analysis
- Data warehousing
- Custom reporting
- Integration testing

### Source pages

An item that is a resource found on pages, such as a broken link, lists those pages in `sourcePages`, each page once. `pageCount` is how many pages it was found on when `sourcePages` lists fewer, as in a published report. The link rules (`links/broken-links`, `links/broken-external-links`, `links/broken-anchors` and the `links-to-redirect` check of `links/redirect-chains`) add `sources`, one entry per page:

```json
{
  "id": "https://example.com/old-page",
  "label": "https://example.com/old-page (404), linked in the page content and the footer",
  "sourcePages": ["https://example.com/about", "https://example.com/contact"],
  "sources": [
    { "page": "https://example.com/about", "links": 2, "sections": { "content": 2 } },
    { "page": "https://example.com/contact", "links": 1, "sections": { "footer": 1 } }
  ]
}
```

`links` is how many of the page's links point at the item, and `sections` counts them by where they sit, using the section names in [link sections](/rules/links/broken-links#what-squirrel-checks); it is absent when no link on that page had a known section. The XML report writes each source page as `<page url="..." links="2">` with a `<section name="content" links="2"/>` per section. The HTML, Markdown, text, LLM and console reports print one row per page, `from: /about (2 links, in the page content)`, and the check's summary counts links and pages apart: `1 broken internal link(s) (4xx/5xx), found on 2 pages`. HTML shows the first three rows and expands the rest inside the item. Markdown, text and console show the first three and the LLM report the first five, then `+N more pages`.

Items that can say where they sit also carry `regions`: how many pages the item sits on, by section, counting every page, not only the ones listed (`{ "header": 49, "content": 3 }`). A page counts once in each section the item has on it. Rules that look at one page at a time set it on each page's item (`a11y/link-text`, `links/anchor-text`, `links/tel-mailto`, `links/https-downgrade`, `links/invalid-links`, `links/nofollow-internal`), and the report adds them up across pages, building a `sources` row for each listed page; a row from these rules has `sections` and no `links`. `content/stale-copyright` names its region on the check instead, as `details.region` (`"footer"`).

When an item sits in a template region (the site header, footer or navigation, a sidebar, the breadcrumbs, the pagination, or the newsletter signup, social share, business details or account links) on at least 80% of the pages that have that region (and on at least 2 pages), the report shows it once for the region; see [findings in a shared page region](/reports#findings-in-a-shared-page-region). The JSON report adds `scope` to that item, and to a check scoped by `details.region`, beside the bounded page list:

```json
"scope": { "region": "header", "pages": 49, "regionPages": 53, "otherPages": 3 }
```

`region` is `header`, `footer`, `navigation`, `sidebar`, `breadcrumbs`, `pagination`, `newsletter_signup`, `social_share`, `business_info` or `account_login`; `pages` is the pages the item sits on in the region; `regionPages` is the audited pages that have the region (from the [page structure](#page-structure) block); `otherPages` is the pages the item is on outside it. The XML report writes the same as `<scope region="header" pages="49" region-pages="53" other-pages="3"/>` inside the item or check. An item with a `scope` has the section phrase taken off its `label` (`https://example.com/old (404)`, not `https://example.com/old (404), linked in the footer`), in every format, as the region says where it is; `meta.sections` still carries the counts. An item with no `scope` keeps its page rows and its label.

A check that names a classifier page type in `details.pageType` (with `details.pageTypeSource` set to `"model"`), and is on every page or nearly every page of that type, gets a `scope` of its own, beside its bounded page list; see [findings on every page of one page type](/reports#findings-on-every-page-of-one-page-type):

```json
"scope": { "pageType": "docs", "pages": 9, "typePages": 11 }
```

`pageType` is the classifier's label, `pages` is the pages the check is on, and `typePages` is the audited pages of that type, from the [page structure](#page-structure) block. The XML report writes `<scope page-type="docs" pages="9" type-pages="11"/>` in the check. A `scope` with `region` is a region and one with `pageType` is a page type; a check has at most one.

### Report detail

The console, text, Markdown and LLM reports end with a Report detail section (the HTML report keeps its notices at the top of the page and shows the page structure as its own section after the site details). It holds the notes about the audit itself, so the top of the report stays the title, URL, date, page count and version, then the score, the summary and the issues. It leaves out whatever it has nothing to say about, and is absent when it has nothing at all. In order, it has:

- **Not checked**: one list item per check this audit did not run, so a skipped check never reads as clean. See `notChecked` in the JSON schema above.
- **Page structure**: where the links on the audited pages sit, below.
- **Scan details**: the notes that qualify the score. Pages the host rate limited, a refused off-site seed redirect, the scan scope, the audit level, smart-audit coverage, the local or private host note, the partial scan hint, and pages recovered by a direct fetch.

```text
## Report detail

### Not checked

- Broken External Links. External link checking was off for this audit, so 12 external link(s) on the audited pages were not checked. Turn external link checks on to check them: in the CLI pass --external-links (or drop --no-external-links, --offline, or external_links.enabled = false); in the cloud they are a website setting.

### Page structure

Page types: 20 product pages, 6 blog posts, 2 contact pages; 30 not classified.

| Section | Pages | Links |
|---------|------:|------:|
| Footer | 58 | 986 |
| Navigation | 58 | 742 |
| Content | 52 | 311 |
| Header | 58 | 174 |
| Sidebar | 14 | 63 |

2,311 links counted; 35 could not be placed in a section.

88% of internal links sit in the header, footer, navigation and sidebar; 12% in the page content.

### Scan details

- Scan: 100 pages crawled from the CLI v0.0.76 (page limit 100 reached)
```

The JSON and XML reports keep every one of these as data fields where they were: `notChecked`, `structure`, `meta` and the rest. The LLM report ends with a `<report-detail>` element that holds `<not-checked>` and `<page-structure>`. Its scan notes stay where they were, as the `<rate-limited>`, `<seed-redirect>`, `<start-redirect>`, `<scan-scope>`, `<coverage>` and `<audit-level>` elements, because an agent needs them before it reads the issues.

#### Page structure

Every report can carry a Page structure block: where the links on your pages sit (the header, footer, navigation, sidebar, page content and so on) and what type of page each one is. It is informational and never part of the score.

It is computed over the pages that answered with a 2xx status, from link sections that page markup and the bundled [page classifier](/configuration/classifier) give each link. It needs a crawl made with a version of squirrel that records link sections: a report built from an older crawl has no Page structure block. With the classifier off (`[classifier] enabled = false`) the block still appears from markup alone, and shows no page types.


What each number means in the Page structure example above:

- **Pages** is the audited pages with at least one link in that section. **Links** is every link in that section, summed over those pages. Each anchor counts, repeats included, so a footer link on 58 pages is 58 links.
- **Could not be placed** is links that neither the markup nor the classifier could assign to a section. They are counted in the total but not listed as a section.
- **Chrome share** is internal links in the header, footer, navigation and sidebar, divided by those plus internal links in the page content. Links in other sections, such as the pagination or the comments, are left out of both sides. A share near 1 means almost every internal link on the site is repeated site furniture, which is common and not a problem by itself. It is the context for findings such as [links/no-contextual-inbound](/rules/links/no-contextual-inbound).
- **Page types** are counted only where squirrel stands behind the label: an answer from the classifier's model, or an answer from the page markup at 0.8 confidence or more. A page with no answer, the label `unknown` or a weaker markup answer counts as not classified. The labels are `homepage`, `product_detail`, `product_listing`, `article`, `blog_post`, `about`, `contact`, `docs`, `legal`, `pricing`, `listing_index` and `other`. Only a page at the root path (`/`) can be a `homepage`: a page at any other path never gets that label, however much it looks like a home page.

The block sits in Report detail (in the HTML report, a Page structure section after the site details), and is left out when there is nothing to show. The LLM and XML reports use a `<page-structure>` element with one `<section>` per row. In the JSON report it is the `structure` key:

| Field | Meaning |
|-------|---------|
| `pages` | Audited pages the numbers cover: those with a link section or a page type |
| `sections` | `{ section, pages, links }` rows, most links first. `unknown` is not a row; sections with no links are left out |
| `unknownLinks` | Links that could not be placed in a section |
| `totalLinks` | Every link counted, `unknownLinks` included |
| `chrome` | `{ links, contentLinks, share }`: internal links in the header, footer, navigation and sidebar, internal links in the page content, and the first over the sum of both, 0 to 1 with three decimals. `share` is `null` when there are no internal links in either |
| `pageTypes.counts` | `{ label, pages }` rows for the labels squirrel stands behind, most pages first |
| `pageTypes.notClassified` | Pages with no label squirrel stands behind |
| `pageTypes.byModel` | Of the counted pages, those whose label came from the classifier's model |
| `pageTypes.degraded` | Pages where part of the classification fell back to the page markup |

## Automation examples

### CI/CD pipeline

Extract health score in CI:

```yaml
# .github/workflows/audit.yml
- name: Run Audit
  run: squirrel audit https://staging.example.com --format json --output audit.json

- name: Check Score
  run: |
    SCORE=$(cat audit.json | jq '.score.overall')
    if [ "$SCORE" -lt 70 ]; then
      echo "Health score too low: $SCORE"
      exit 1
    fi
```

---

### Compare audits

Compare two audits using JSON:

```bash
# Before changes
squirrel audit https://example.com --format json --output before.json

# Make changes...

# After changes
squirrel audit https://example.com --format json --output after.json

# Compare scores
echo "Before: $(cat before.json | jq '.score.overall')"
echo "After:  $(cat after.json | jq '.score.overall')"
```

---

### Generate multiple reports

Run once, output multiple formats:

```bash
#!/bin/bash
URL="https://example.com"
DATE=$(date +%Y-%m-%d)

# JSON for data
squirrel audit $URL --format json --output "reports/$DATE/data.json"

# HTML for sharing
squirrel audit $URL --format html --output "reports/$DATE/report.html"

# Console for logs
squirrel audit $URL > "logs/$DATE.log"
```

## Troubleshooting

### HTML not opening in browser

**Solution:** Open manually:

```bash
squirrel audit https://example.com --format html --output report.html
open report.html  # macOS
xdg-open report.html  # Linux
```

---

### JSON output too large

**Cause:** Large sites generate large JSON files

**Solution:** Use console format or filter JSON:

```bash
# Get only the score block
squirrel audit https://example.com --format json | jq '.score'

# Get only error-severity issues
squirrel audit https://example.com --format json | jq '.issues[] | select(.severity == "error")'
```

---

### Path permission denied

**Cause:** No write permission to output directory

**Solution:** Use writable directory or fix permissions:

```toml
[output]
path = "~/reports/audit.json"  # Home directory
```

Or:
```bash
mkdir -p reports
chmod 755 reports
```
