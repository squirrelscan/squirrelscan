The `audit` command crawls a website and runs SEO rules to generate a report.

## Usage

```bash
squirrel audit <url> [options]
```

## Arguments

| Argument | Description |
|----------|-------------|
| `url` | The URL to audit (required). Without a scheme, `https://` is assumed, or `http://` for a local or private host such as `localhost:3000`, `192.168.1.10` or `myapp.test` (see [local audits](/guides/local-audits-cli#local-and-private-hosts-stay-local)) |

### Audit levels

| Level | Pages | What it does |
|-------|-------|--------------|
| `quick` | 25 | The URL and its sitemaps, no link following, no cloud checks, internal links checked |
| `surface` | 100 | Follows links, one page per URL pattern first, with the cloud checks and the editor's summary |
| `full` | 500 | Every page it can reach up to the budget, with the cloud checks and the editor's summary |

A level also sets rendering, external link checks and probing. Every flag that
changes one of those settings (`--max-pages`, `--render-mode`, `--http`,
`--probe` and the rest) still works, and makes the audit **custom**. The banner
says what changed:

```text
Level     custom (surface + max_pages 200)
```

**The default level is auth-aware.** Any signed-in account (free or Pro) defaults
to `surface`, so the cloud checks and the editor's summary run and a free report
demos the full product. Signed-out and `--offline` runs default to `quick`. Pass
`--level` (or set `[crawler] coverage` in config) to choose either way.

`quick` skips the cloud checks, and nothing else changes about billing: signed
in, a quick audit is a cloud audit like any other level, at 50 credits plus 2
per audited page (up to 100 for 25 pages), and it renders the pages that need
JavaScript in the cloud browser. `--http` skips the browser, not the page
charge. Free and Pro run the same checks: Pro just grants more monthly credits
and lets you top up.

See [Audit levels](/guides/audit-levels) for every setting of every level, custom
levels, and the plan and credit limits.

### Offline and passive are separate

Two settings control what an audit sends, and they are independent:

- **Offline or online** is the network scope: does the audit use the cloud and
  other sites? `--offline` says no. It means no cloud analysis, rendering or
  publishing, no telemetry, and no check of links, scripts or sitemaps on other
  sites. The one request that can leave the audited site is a start URL redirect
  hop, which is how the audit finds where it starts (see
  [Start URLs that redirect](#start-urls-that-redirect)).
- **Passive or active** is how hard the audited site is poked: the
  [probing intensity](#probing-intensity). `--passive` (or `--probe passive`)
  turns the probe rules off. The probe level comes from `--probe` or its
  shortcuts (`--passive`, `--aggressive`), then `[security] probe` in the config,
  then the audit level, and `--offline` does not change it. The run banner's
  `Probing` line shows the level in effect.

| | Passive | Active (the default at `surface` and `full`) |
|---|---|---|
| **Offline** (`--offline`) | The crawl of the audited site, no cloud, no other host. No probe rules, but the 28 [discovery probes](/configuration/crawler#discovery-probes) still run unless disabled | The same, plus the probe rules: GraphQL `GET` requests and, for form actions, `HEAD` then `GET`, all to the audited site |
| **Online** (signed in or out) | The crawl, plus other sites (external link checks) and, signed in, the cloud: rendering, cloud checks and publishing. No probe rules, discovery probes still run unless disabled | Everything above, plus the probe rules |

So `squirrel audit <url> -C surface --offline` is offline and **active**: it keeps
off the cloud and off other sites, and it still sends the probe rules (for example
`GET /graphql?query={__schema{types{name}}}`) to the audited site. Add `--passive`
to stop them.

The [discovery probes](/configuration/crawler#discovery-probes) (`llms.txt`,
`/.well-known/*` and so on, 28 requests) are a third dial, and it only goes one
way. A `passive` run still sends them unless you also pass
`--disable-discovery-probes`; but `--disable-discovery-probes` does force probing
to `passive`, so `-C surface --offline --disable-discovery-probes` runs passive.
To keep the traffic to the crawl itself, with no probes and no cloud:

```bash
squirrel audit https://example.com --offline --passive --disable-discovery-probes
```

That still sends the crawl's own requests: the pages and their scripts,
`robots.txt`, the sitemap path guesses, a `HEAD` for each internal link target
the crawl did not fetch, the soft-404 re-check where it applies, and start URL
redirect hops. On a small test site it was 17
requests, all of them pages, `robots.txt`, sitemap paths and scripts.

The banner's `Probing` line (for example `Probing   active · budget 30s`) shows
what the run will do before it starts.

`robots.txt`, sitemaps, the pages themselves and the checks of internal link
targets are the crawl, and still run.

### Probing intensity

Probing intensity says how hard each page is poked beyond what the crawl
fetched. It is one of the [audit level's](/guides/audit-levels) settings, with
the page budget and rendering.

| Level | What it sends |
|-------|---------------|
| `passive` | No probe rules, and nothing beyond the crawl itself except the 28 [discovery probes](/configuration/crawler#discovery-probes), which `--disable-discovery-probes` turns off |
| `active` | Quiet probes: a handful of requests that look like normal traffic |
| `aggressive` | Loud probes: many requests and many 404s, which can trip a WAF |

The audit level picks the default: `passive` for quick, `active` for surface and
full. `aggressive` is never a default. The audit prints the level and its budget
in the run banner:

```text
Level     surface · max 100 pages
Probing   active · budget 30s
```

`--passive` and `--aggressive` are shortcuts for `--probe`. Using both is refused,
as is a shortcut that contradicts `--probe`, the same way `--render` and `--http`
are. An unknown level or budget fails before the crawl starts.

`--probe-budget` caps the wall-clock time of **all** probing together, not each
probe. Once it runs out, no new probe starts.

The rules that probe, and exactly what each one sends, are listed in
[Security configuration](/configuration/security#rules-that-probe).

`--disable-discovery-probes` (or `[crawler] disable_discovery_probes = true`)
keeps probing passive, and no probe sends a request.

<Warning>
`--aggressive` and `--pentest` request paths that `robots.txt` disallows, on
purpose. Only use them on websites you own or are authorized to test.
</Warning>

```bash
squirrel audit https://example.com --aggressive --probe-budget 1m
squirrel audit https://example.com --pentest
```

To pick which rule families run, use `--rule-include` and `--rule-exclude`. See
[Security configuration](/configuration/security) for `[security] probe` and
`budget`, and the defaults for cloud audits.

## Examples

### Basic audit

```bash
squirrel audit https://example.com
```

### Quick health check

```bash
squirrel audit https://example.com --level quick
```

### Full comprehensive audit

```bash
squirrel audit https://example.com --level full
```

### Crawl more pages

```bash
squirrel audit https://example.com -m 200
```

### Export to JSON

```bash
squirrel audit https://example.com -f json -o report.json
```

### Generate HTML report

```bash
squirrel audit https://example.com -f html -o report.html
```

### Fresh crawl (ignore cache)

```bash
squirrel audit https://example.com --refresh
```

### Resume an interrupted crawl

```bash
squirrel audit https://example.com --resume
```

Resume only continues a crawl when this process can claim it. If another live
process already owns that crawl, the command names its PID and host and starts a
new crawl instead. A lease becomes stale after 5 minutes without a heartbeat;
a live same-host PID remains protected longer. Stop the other process (Ctrl-C
releases its lease immediately), wait 5 minutes for a silent remote owner to go
stale, or use `--refresh` for a fresh crawl. See [crawl leases](/cli/self#crawl-leases).

### Publishing to the dashboard

When you're **logged in and online, every audit auto-publishes to your dashboard as `unlisted`**, independent of cloud rendering or enrichment. You get a shareable link plus issue history with no extra flags. Not logged in (or `--offline`)? Nothing publishes.

**Publishing is included in the audit base charge**, whatever the visibility. The auto-publish default is `unlisted`.

Publishing and tracking the run in the dashboard need a [role](/cloud/team#roles) that runs audits in the organization you are signed in to: owner, admin or editor. As a viewer or billing member the audit still runs locally and its results are complete, but the run is not tracked and the report is not published: the CLI prints the reason (`forbidden_role`). Run with `--no-publish` to skip the publish attempt.

```bash
# logged in → auto-publishes (unlisted) and prints the URL
squirrel audit https://example.com
```

Override the visibility for a run:

```bash
squirrel audit https://example.com --visibility public
```

Once a website has been audited successfully, squirrelscan re-audits it on a weekly [schedule](/cloud/scheduled-audits) by itself. From then on every publish prints one more line saying so, with the link that turns it off:

```text
https://reports.squirrelscan.com/XVv4NO7aPr
Scheduled audits: every week, and each run costs credits. Turn it off: https://app.squirrelscan.com/acme/website/web_1/settings/schedule
```

The cadence it names is the one your plan actually funds.

A site that asked for a schedule your plan has no slot left for is [capped](/cloud/scheduled-audits#schedule-states), and the line says so instead:

```text
Scheduled audits: this site is not scheduled, your plan schedules <n> website(s). Upgrade: <upgrade-url>
```

Every other state prints nothing, and so does a run that published nothing.

Skip publishing for a single run (still runs online):

```bash
squirrel audit https://example.com --no-publish
```

Turn auto-publish off for the project in `squirrel.toml`:

```toml
[cloud]
publish = false
```

`--publish` is still accepted (now redundant when logged in) and forces a publish even if `[cloud] publish = false`. `--publish` and `--no-publish` cannot be combined.

<Note>
Publishing requires authentication. Run `squirrel auth login` first; logged-out runs never publish.
</Note>

<Note>
An audit of a host no squirrelscan server can reach never publishes, never registers a run, and never renders in the cloud, even with `--publish` or `--render`. That covers `localhost`, loopback and private ranges such as `192.168.1.10`, and internal names such as `box.local` or anything under `.internal`. Hosted services cannot reach your machine or your private network, so there is nothing they could screenshot, re-render or re-audit. The audit itself runs and prints normally, except that the transport and delivery rules (HTTPS, HSTS, HTTP/2, compression, caching) are skipped and left out of the score. See [Local audits with the CLI](/guides/local-audits-cli), including [which rules are skipped and why](/guides/local-audits-cli#transport-and-delivery-rules-do-not-apply).
</Note>

### Browser rendering

When you're **logged in, audits render every page in a cloud browser by default**, so JavaScript-heavy sites are audited against their fully rendered HTML. A signed-in audit costs 50 credits plus 2 per audited page whether a page is rendered or fetched over plain HTTP, so rendering never changes the bill. At the levels that check external links it also pays 1 credit per external link the cloud verifies, at most 1 per page; links the cloud cannot answer in time are checked on your machine for free. The first time an audit would spend credits the CLI asks once and remembers your answer, and if your balance can't cover the page limit the CLI lowers the limit to what it covers and tells you. See [Credits and pricing](/cloud/credits).

Force plain HTTP for a run (no cloud browser):

```bash
squirrel audit https://example.com --http
```

Force rendering for a run even if your config disables it:

```bash
squirrel audit https://example.com --render
```

For finer control, `--render-mode auto` renders **only** pages that need it (client-side-rendered shells) and uses fast plain HTTP for the rest. To set the behavior permanently, use `render` in `[cloud]` - see the [browser rendering guide](/guides/browser-rendering).

### Start URL rules

The start URL must be `http://` or `https://` with a host. A bare domain gets `https://` (`http://` for a local name), and `localhost:3000` or `example.com:8080` keep their port. Credentials (`user:password@`) and the `#fragment` are dropped before anything is crawled, logged, registered or sent to the cloud, with a note on stderr; the query string is kept. Use `--header "Authorization: Basic ..."` to crawl a site behind basic auth. A URL longer than 2048 characters is audited but not registered as a dashboard run.

### Start URLs that redirect

A start URL is resolved before anything else: its redirect chain is followed, one request per hop, and the end of the chain is what gets audited. A link shortener is the usual case. `squirrel audit https://bit.ly/abc` audits the site it points to, not bit.ly.

| The chain | What happens |
|---|---|
| Stays on one site: `http` to `https`, apex to `www`, a path change | Followed silently. The report's base URL is where it ended. |
| Ends on another registrable domain or port | Needs your consent, because it changes which site is crawled. |
| Loops, passes 5 hops, or reaches a hop that is refused | Never followed. The run exits `4` with the chain so far. |

On a terminal, a cross-domain redirect asks first:

```text
bit.ly/abc redirects to https://example.com/pricing. Audit example.com instead? [Y/n]
```

Accepting audits the destination. Declining exits `4` and prints the destination. Anywhere else (an agent, CI, a piped report) there is nobody to ask, so give the consent up front:

```bash
squirrel audit https://bit.ly/abc --follow-redirect
```

or set it for a project:

```toml
[crawler]
follow_redirect = true
```

`-y` is not that consent. It approves credit spend, agents pass it routinely, and the redirect may land on a site that is not yours. Without `--follow-redirect` a non-interactive run does not crawl the redirector and does not score it. It exits `4` and prints a `redirected` report that names the destination and the command to run again:

```json
{
  "status": "redirected",
  "reason": "cross-domain",
  "originalUrl": "https://bit.ly/abc",
  "finalUrl": "https://example.com/pricing",
  "redirectChain": [
    { "url": "https://bit.ly/abc", "status": 301 },
    { "url": "https://example.com/pricing", "status": 200 }
  ],
  "rerunCommand": "squirrel audit https://bit.ly/abc --follow-redirect",
  "message": "https://bit.ly/abc redirects to https://example.com/pricing, a different site, so nothing was audited."
}
```

Only the scheme, host, port and path of each URL are printed or recorded, and only the destination's origin and path are audited: userinfo, query and fragment are dropped, because a redirect's query often carries a token. The destination's query, fragment and credentials are not carried to the audit. Shortener destinations are mostly tracking parameters, and the query is where tokens live. A destination that needs a query or credentials has to be audited by typing it directly. `rerunCommand` uses the start URL exactly as you typed it. The same facts come out in every [output format](#output-formats). `reason` is `cross-domain`, `loop`, `too-many` or `refused`. `rerunCommand` is `null` for a loop or a refused hop, where there is nothing to run again.

When a cross-domain redirect is followed, the report records where the audit began. The JSON report has `meta.originalUrl` and `meta.redirectChain` (every URL requested, each with the status it answered; the last is the destination), the text, markdown, LLM, XML and HTML reports say so in their scan notes, and the project, the cloud credit estimate and the crawl scope are the destination's. A same-site redirect leaves no record.

The hops are requested before the credit check and before the run is registered: a balance that is too low, or a shutdown, still leaves those requests sent, but nothing is registered or charged. Every hop goes through the same egress guard as the crawl. A redirect into a private network, a link-local address or a cloud metadata address is refused and never requested, unless the start URL itself is on that private network. The hops are resolved even under [`--offline`](#fully-offline-audit): that is the one request per hop that reaches another site, and what it finds is audited offline. Redirects that a page, rather than the start URL, answers with (a meta refresh or a script) are not part of this chain.

### Fully offline audit

Run an audit with no cloud and no requests to other sites: no cloud analysis, no
publishing, no update checks, no telemetry. The site's own hosts are the audited
host, its `www` or apex twin, the domains in `[project] domains` and the
subdomains of all of them. Nothing goes to any other host:

- External links are not checked, and neither are the third-party scripts,
  stylesheets and fonts the pages load. `reliability/broken-resources` reports
  them as not measured.
- A page that redirects to another host is recorded as the redirect it answered
  with, and the other host is not requested.
- A sitemap that robots.txt lists on another host is not requested.
  `crawl/sitemap-exists` and `crawl/sitemap-valid` say it was skipped, not
  missing, and `crawl/sitemap-4xx` says how many sitemap URLs on another site
  it skipped.
- A stylesheet, script, image, font or PDF on the site that redirects to
  another host is not followed there; `reliability/broken-resources` reports it
  as not requested. One on the `www` or apex twin, or on a `[project] domains`
  host, is checked like the site's own.
- The soft-404 confirmation, the cloaking probe and the AI agent access probe
  stay on the site: a redirect off it is not followed.

Results are stored in the local database as usual:

```bash
squirrel audit https://example.com --offline
```

`--offline` cannot be combined with `--publish` or `--render` (both require
cloud access and login).

`--offline` does not imply `--passive`: see
[Offline and passive are separate](#offline-and-passive-are-separate).

### Ephemeral runs

A signed-in `squirrel audit` does more than use the cloud. It adds the site to your dashboard (or reuses it), turns on [recurring audits](/cloud/scheduled-audits#when-a-schedule-turns-itself-on) after the site's first successful audit, and publishes the report. `--ephemeral` keeps the cloud features and drops all of that:

```bash
squirrel audit https://example.com --ephemeral
```

An ephemeral run:

- does not add the site to your dashboard, so it never counts toward your plan's website limit and never fails with `WEBSITE_LIMIT`
- does not schedule the site, and never turns a schedule on later
- does not publish a report unless you pass `--publish` too. An explicit `--publish` wins, also over `[cloud] ephemeral = true`, and publishes an **unlisted** report that is attached to no dashboard site (the CLI prints its URL and says so). Without `--publish`, the summary says the run was not published
- is charged exactly like the same audit without it: 50 credits plus 2 per audited page, plus any external link checks. Your credit history and usage list it as "Ephemeral CLI run" with the domain, so nothing is invisible to you or your organization owner
- prints a line at the end of the summary saying the run was ephemeral, and prints the Ephemeral mode in the header when the run uses your account

Use it for sites you do not own or manage (prospects, clients, competitors), one-off checks, and CI jobs against preview URLs. Set `[cloud] ephemeral = true` in `squirrel.toml` to make it the default for a project, and pass `--no-ephemeral` to run one audit the normal way.

`--ephemeral --offline` is accepted. An offline run saves nothing anyway, so the CLI prints one line saying the flag has no effect.

The server has to support the option. If it does not confirm the run as ephemeral (an older server that ignores the field), the CLI prints a warning that the site may have been added and scheduled, so you can remove it from the dashboard, and it publishes nothing, even with `--publish`.

### Gate CI on audit results

Use `--fail-on` to fail a CI build when an audit crosses a threshold you set.
Thresholds are absolute, not a comparison with an earlier audit. The command exits
with code `2` when **any** threshold trips (vs `1` for operational errors and
`0` when everything passes), and prints a summary of what tripped:

```bash
# Fail if the overall score drops below 90, or any error-severity issue is found.
# Quote each expression — shells treat bare < and > as redirection.
squirrel audit https://example.com --fail-on 'score<90' --fail-on 'severity>=error'

# Comma-separated form, plus a per-category threshold
squirrel audit https://example.com --fail-on 'score<90,score:perf<80,warnings>0'
```

Supported metrics:

| Expression | Trips when |
|------------|-----------|
| `score<N` | overall health score is below `N` |
| `score:<category><N` | a category score (e.g. `score:perf<80`) is below `N` |
| `severity>=error` | any error-severity finding exists (also `>=warning`) |
| `errors>0` | there is at least one error-severity finding |
| `warnings>0` | there is at least one warning-severity finding |

Operators: `<`, `<=`, `>`, `>=`, `=`; all five work on the numeric metrics
(`score`, `score:<category>`, `errors`, `warnings`). For `severity`, `=` means
the **exact** rank (e.g. `severity=warning` trips on warnings but not errors);
use `>=` for "at least" (e.g. `severity>=warning` trips on warnings *or* errors).

A security rule that ran past its [time budget](/rules#rule-time-budget) did not check some pages, so an empty result there is not a clean one. It stays out of the score, and the gate counts each such rule as one warning-severity finding: `warnings>0` and `severity>=warning` trip on it, `errors` and `score` do not. A gate that only uses `errors` or `score` therefore passes when a security rule timed out: add a `warnings` or `severity>=warning` gate, or raise [`[rules] time_budget_ms`](/configuration/rules#time_budget_ms) and run again. The count appears only in the gate summary (`+1 timed-out security rule`), never as a finding in the report. The summary says which rule timed out and on how many pages. Other rules that time out are not counted.

The gate summary is written to stderr, so machine formats like `--format json`
keep a clean stdout for piping. A malformed expression fails fast (exit `1`)
before any crawl runs.

### Filtering rules

Use `--rule-include` / `--rule-exclude` to run only some rule categories, for
a faster pass or to focus on one area. Bare tokens expand to the whole
category (`ax` → `ax/*`); exact rules also work (`core/meta-title`):

```bash
# Only run agent-experience and performance rules
squirrel audit https://example.com --rule-include ax,perf

# Run everything except images and social
squirrel audit https://example.com --rule-exclude images,social

# Repeatable or comma-separated, same as --fail-on
squirrel audit https://example.com --rule-include ax --rule-include perf
```

`--rule-include` replaces the categories that run for this audit;
Excluding rules also skips the pre-crawl requests that only those rules read:
`--rule-exclude ax` sends none of the
[discovery probes](/configuration/crawler#discovery-probes).

`--rule-exclude` skips categories on top of whatever would normally run. When
either flag is set, the report is **partial**: the health score is recomputed
from only the included categories and the console output prints a
`partial audit: ...` notice in its Report detail section at the end. Only console output carries that
notice: other formats (json, text, markdown, xml, llm) print a warning to
stderr instead, so the report body itself is unchanged. An unknown category
errors before crawling, listing the valid category codes. `--fail-on score:<category>`
referencing an excluded category also errors up front, since it could never
trip.

### Summary output

Use `--summary` for a quick score check without the per-issue detail — useful
in CI logs or a fast re-check:

```bash
squirrel audit https://example.com --summary
```

This prints the header, health score, category breakdown, editor's summary
(when present), and per-category issue counts, but skips individual rule
findings and affected-page lists. Console format only — combine with a
non-console `--format` and the command errors up front.

### Passed rules

Use `--include-passed` to list the rules that passed after the issues, with how many pages each passed on:

```bash
squirrel audit https://example.com --include-passed
```

It works with every `--format`. To list them for an audit you already ran, use [`squirrel report --include-passed`](/cli/report#list-what-passed).

### Pages list

`--include-pages` adds the crawled pages to the JSON report, for a pipeline that tracks which pages a run actually covered:

```bash
squirrel audit https://example.com -f json --include-pages
```

It is off by default, so the report and its size are unchanged unless you ask. Each entry is `{ "url", "status", "ruleCount" }`: the page's URL, the HTTP status it answered with, and how many distinct rules reported on it (a skipped check does not count, and neither do site-wide rules). The list is cut at 2,000 pages; `pagesTotal` is the real count and `pagesTruncated` is `true` when entries were dropped. A URL whose fetch never produced a stored response (a connection error, a server error that survived retries, a rate-limited request) is not a page and is not listed; rate-limited pages are counted in `rateLimited`. To get the list for an audit you already ran, use [`squirrel report --include-pages`](/cli/report#pages-list). In any other format the flag does nothing and the command says so on stderr. See the [JSON output schema](/configuration/output#json-output-schema).

### Verbose output

```bash
squirrel audit https://example.com -v
```

### Progress without a terminal

With no terminal on stdout (a CI job, a pipe, a supervisor), the audit has no spinner. The step after the crawl walks every crawled page before the rules run, and on a big site that takes minutes, so it writes a progress line to stderr about every 15 seconds while it runs. The line is written between batches of pages (a batch is sized by bytes, so on any site one ends every few seconds), which means a single batch that takes longer than 15 seconds shows no line until it ends:

```text
Walking pages: 40/104
```

It goes to stderr, so `--format json` and piped stdout stay clean, and it stops when the walk ends. A terminal keeps its spinner and prints no extra lines. There is no `--quiet` flag; redirect stderr (`2>/dev/null`) to drop the line. Set `SQUIRREL_WALK_HEARTBEAT_MS` to a number of milliseconds to change the 15 seconds, for a supervisor with a shorter watchdog.

## Crawl behavior

The audit command manages crawl sessions intelligently:

| Scenario | Behavior |
|----------|----------|
| First run | Creates new crawl |
| Re-run (completed) | New crawl, uses cache for 304s |
| Re-run (interrupted) | Resumes from where it left off |
| Config changed | New crawl with fresh scope |

<Info>
Changing scope-affecting config (`include`, `exclude`, `allow_query_params`, `drop_query_prefixes`) triggers a fresh crawl.
</Info>

### Empty successful pages

A successful HTML response that permits a body counts as an audited page even
when its body is zero bytes. squirrel treats it as an empty document, so checks
such as missing title and missing H1 apply, and the page is included in the
report's page count, coverage and score. Responses without an HTML content type,
responses whose body was not captured, and no-content statuses such as 204 are
not treated as empty documents.

### Query-string variants

A page and a query-string copy of it (`/contact` and `/contact?subject=Billing`) are two URLs the crawl fetches and checks, but they are one page to the reader. A crawled page whose `rel=canonical` points at another crawled page of the same path is counted with that page: a finding on both lists one affected page, the page total and the scan line count the pages once, and the report says how many variants were folded (`Scan: 5 pages crawled ... 1 query-string variant counted with its canonical.`, `meta.canonicalVariants` in JSON).

Each folded variant is listed with the page it is counted with in `meta.canonicalVariantPages` (the first 100) in the JSON report, so no URL is lost. Only a declared canonical folds a page. A variant with no canonical, with a canonical of its own (a paginated listing, a search or filter page), or whose canonical is another path, another host or a page the crawl did not fetch stays a page of its own and is listed separately. Every variant is still fetched and checked, so scores and issue counts do not change, and a finding on a variant stays in the tallies; only how many pages are counted does. One caveat: a page whose canonical points at another page is folded even when its content differs, for example `/blog?page=2` declaring `/blog` as its canonical (a common pagination mistake). squirrel counts it with `/blog` because that is what the site told search engines; give such a page its own canonical to have it listed separately. The entity map, which describes every crawled URL, still lists them. A smart audit's union of carried pages is not folded.

## Caching

squirrelscan caches page content locally. On subsequent audits:

- **304 Not Modified**: Uses cached content (fast)
- **200 OK**: Fetches fresh content (slower)

Use `--refresh` to bypass the cache entirely.

### Rule results

Skipping the fetch only saves the download. squirrelscan also caches the rule
results for each page, so a re-audit of a page nothing has touched replays its
findings instead of parsing the page and running its rules again. On a site that
has not changed, this is most of the audit.

A page replays only when every input its rules read is unchanged:

- the page's exact HTML, byte for byte
- its status, headers, redirect chain and response timings
- the version of squirrel that produced the results
- the rules' own code, so a rule fix that ships without a version change (or one
  you make in a source checkout) still re-runs the rules on unchanged pages
- which rules are enabled, and the options they run with

Change any of them and that page is audited again. Rules that read the whole site
rather than one page always run.

Every report says what happened, so you never have to guess whether you are
reading a fresh measurement:

```json
"rulesCache": { "pagesReplayed": 2480, "pagesEvaluated": 20 }
```

`--refresh` turns it off along with the page cache. To turn off only the rule
cache, set `SQUIRREL_RULE_CACHE=0`.

While the rule cache is on, squirrelscan runs every rule on every page rather than
running a template-shared rule once per template and reusing its verdict. That
makes the first audit of a site slightly slower and every audit after it much
faster, and it makes the report the one every rule actually computed.

Cached results live in the project database and are removed with the audit they
belong to, so [`squirrel self disk --prune`](/cli/self#disk) reclaims them along
with everything else that audit is holding.

## Audit history

A successful audit retires the audits older than the newest 3 for that project,
so re-auditing does not grow `project.db` without bound. Retired audits stay
listed and can no longer be opened; the page cache the next audit reads is never
part of what goes. A run that ends `failed` or `blocked` neither retires
anything nor counts towards the window. The audit says so on stderr whenever it
retires something:

```text
Retired 1 older audit and freed 95.2 MB inside project.db for the next audit; keep more with [storage] keep_audits (now 3)
```

Change the window, or turn it off, with
[`[storage] keep_audits`](/configuration/storage).

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Success |
| `1` | Error (invalid URL, crawl failed, a site that answered with an error, etc.). A start URL that is not `http://` or `https://` with a host (`ftp://`, `file://`, `mailto:`, `javascript:`) is refused first, before any request: no run is registered and nothing is charged |
| `2` | A [`--fail-on`](#gate-ci-on-audit-results) threshold tripped (CI gate) |
| `3` | The audited page was blocked, so nothing was audited: a WAF or bot manager challenge or block page, or a bare 403 or 429 from the server (see [blocked by a WAF or bot manager](/guides/failed-audits#blocked-by-waf)). Every report with `status: "blocked"` exits `3` |
| `4` | The start URL redirected to another site and the run was not told to follow it (or the chain looped, passed 5 hops, or reached a refused hop), so nothing was audited. See [Start URLs that redirect](#start-urls-that-redirect) |
| `5` | The start URL could not be reached (DNS failure, connect timeout, connection reset or refused, a TLS error), so nothing was audited. With `-f json`, `-f xml` or `-f llm` the run still writes a report with `status: "unreachable"` (see [Unreachable start URLs](#unreachable-start-urls)) |

### Unreachable start URLs

When the start URL cannot be reached, the audit stops before it crawls and exits `5`. The format you asked for still gets a report, to `--output` or stdout, so a batch job can tell a site that is down from a crash without reading stderr:

```json
{
  "status": "unreachable",
  "url": "https://example.com/",
  "statusReasonCode": "dns",
  "statusReason": "getaddrinfo ENOTFOUND",
  "message": "Cannot reach https://example.com/: getaddrinfo ENOTFOUND. No audit ran and there is no score."
}
```

`statusReasonCode` is one of `dns`, `tls`, `connection` (refused, reset, or a connection that timed out), `timeout` or `unknown`, the same codes a [failed audit](/guides/failed-audits) uses. `statusReason` is the probe's own error text, so its wording follows the runtime (for example `ECONNREFUSED: Unable to connect...` or `Connection timed out`). The URL is printed without its query, fragment and credentials. `console` and `text` formats print the same facts as text, and a `✗ Cannot reach ...` line goes to stderr in every format.
