Broken links are easy to make and hard to notice: a page gets renamed, a section is restructured, a site you cite shuts down. squirrelscan checks the links on the pages it audits, so you hear about it before your visitors do.

This page covers what is checked today, how to read the results, and what is coming. Sections marked **Coming soon** describe work in progress, not something you can use yet.

## What gets checked

| | Internal links | External links |
|---|---|---|
| What | Links to pages on your own site | Links to other sites |
| Rules | [`links/broken-links`](/rules/links/broken-links) | [`links/broken-external-links`](/rules/links/broken-external-links), [`links/dead-links`](/rules/links/dead-links) |
| Quick level | On | Off, unless you pass `--external-links` |
| Surface and Full levels | On | On |
| Limit per audit | 200 targets the crawl did not fetch | The audit's page budget or 200 links, whichever is more |
| Link check cost in the CLI | Free | Free |
| Link check cost in a cloud audit | Free | 1 credit per distinct external link, at most one per page of the audit's budget |

An audit itself costs 50 credits plus 2 per audited page, in the cloud or signed in from the CLI; signed out or with `--offline` it is free. In a cloud audit, external links add 1 credit each when external link checking is on. The full price list is in [Credits & Pricing](/cloud/credits), and every switch is in [Link checking defaults](/rules/links#link-checking-defaults).

## Internal links

A link to your own site is checked two ways:

- **Pages the crawl fetched** are checked from the crawl itself: a target that answered with an error (400 or above, other than throttling) is a broken link.
- **Pages the crawl did not fetch** get a status-only `HEAD` request each, up to 200 per audit, the most-linked first. This is what lets a Quick audit, which does not follow links, find a 404 that only a link points at. It also finds a broken page past a Surface or Full audit's page budget.

The status-only check is built not to change anything on your site:
- It never requests links that look like actions (log out, unsubscribe, delete, confirm, add to cart) or that carry a token.
- It sends no cookies, credentials or custom request headers.
- It stays inside the crawl scope and, when the crawl respects it, robots.txt.

The full rules are in [What the internal link check never requests](/configuration/external-links#what-the-internal-link-check-never-requests). Switch it off with `--no-internal-links` or `[internal_links] enabled = false`.

## External links

External links are checked at Surface and Full, and at Quick with `--external-links`. One audit checks at most its page budget or 200 distinct external links, whichever is more. The links on the most pages go first: the nav and footer links every page shares. The rest are listed as **Not checked**.

Where the check runs depends on how you audit:

- **A cloud audit** checks external links with squirrelscan's link checker, Perch, which shares what it learns across audits. Each distinct external link costs 1 credit, at most one per page of the audit's budget. External link checks are a website setting in the dashboard.
- **A signed-in CLI audit at Surface or Full** sends its external links to the same checker, for free. Whatever Perch has not answered within a minute, the CLI checks itself from your machine.
- **Signed out, or at Quick with `--external-links`**, the CLI checks external links from your machine. `--offline` skips them.

Like the internal check, the external check never requests a link that looks like an action or carries a token: a newsletter's one-click unsubscribe, a magic sign-in link, a signed download. It never follows a redirect into one either. See [What the external link check never requests](/configuration/external-links#what-the-external-link-check-never-requests).

## How Perch tells broken from blocked

Many sites refuse automated requests. A refusal says nothing about whether a person would reach the page. So Perch does not take the first answer at face value:

- **A link that a site blocks for automated clients** is checked again with the network fingerprint of a real browser.
- **A link is reported broken only after a confirmed failure:**
  - a 404 or other client error: twice, at least ten minutes apart;
  - a server error (5xx): three times, at least six hours from the first to the last.

  Until then it is listed as status unverifiable, not broken. A link checked again by a later audit counts toward this too.
- **A domain that no longer exists**, or has no address, is reported straight away. Two independent DNS resolvers have to agree. In our samples it is one of the most common kinds of dead external link.
- **A page that answers 200 but whose title is just "404" or "Page not found"** (a soft 404) is broken, confirmed the same way as a 404.
- **A link that still cannot be verified is listed as status unverifiable, never as broken.** This covers a firewall challenge, LinkedIn's 999, a plain 403 or 406, a timeout from our network, or a CDN error page. A rate limit is listed as rate-limited, never as broken.

We replayed 1,631 external links the previous checker had already answered. It had stored 107 of them as broken and 239 more as refused (a 403, 429 or 503). Perch reports 67 broken. Of the 1,281 links the previous checker had found working, Perch called 6 broken (0.47%), and a hand check found all 6 really were gone.

### When the CLI checks a link itself

When the CLI checks a link from your machine (signed out, at Quick, or when Perch has not answered in time), it makes one plain check per link. That check keeps refusals apart from broken links where it can tell them apart:

- **Throttled** (429 or 430, or a 503 with `Retry-After`): listed as rate-limited, status unverifiable, never broken.
- **Blocked by a firewall** (a 403 with a recognisable web application firewall signature): listed as blocked, status unverifiable, never broken.
- **An internal link that answers 401 or 403** to the status-only check: listed as refused, never broken.

Some blocks carry no signature the single check recognises, such as a plain 403, a 406, LinkedIn's 999, or a CDN error page. In a check from your machine those, and a timeout, are still reported as broken. If a link in the broken list loads in your browser, it is probably one of these. A cloud audit, or a signed-in CLI audit at Surface or Full, avoids most of them, because Perch checks the link first.

### The first check of a new link

Perch needs about a minute for a link it has never seen, sometimes longer, because it spaces its requests to each site out. A cloud audit sends its external links to Perch while it crawls, so most are answered by the time the audit asks. Any link Perch has not answered in time gets a quicker single check from the cloud instead, and that check can still report a blocked link as broken. The next audit gets Perch's answer.

## Not checked

When a check did not run, squirrelscan says so rather than reporting the rule as passing. Every report format lists these under **Not checked**, with the reason and what to run instead. The score leaves them out.

| Reason | What happened |
|---|---|
| `external-links-not-checked` | External link checking was off: the Quick level without `--external-links`, `--offline`, `--no-external-links`, `[external_links] enabled = false`, or a website or run that switched it off. |
| `external-links-over-cap` | The audit found more external links than its limit. The most-linked were checked. |
| `link-targets-not-fetched` | The audit did not follow links, and some internal link targets were fetched neither by the crawl nor by the status-only check: it was off, over its limit, or the targets were skipped. |

In the cloud's issue tracker, an open broken-link issue stays open while an audit could not check links for one of the reasons above. A link listed as status unverifiable does not keep it open.
