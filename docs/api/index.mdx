squirrelscan exposes a stable, programmatic REST API under `/v1`. It's the
surface external clients, agent workflows, and MCP integrations can depend on.

<Info>
The machine-readable contract is published as an [OpenAPI 3.1 spec](/openapi.json).
Point your client generator, Postman, or an MCP server at it.
</Info>

## Base URL

```text
https://api.squirrelscan.com
```

## Authentication

Every request authenticates with a bearer token in the `Authorization` header:

```bash
curl https://api.squirrelscan.com/v1/credits \
  -H "Authorization: Bearer <token>"
```

Programmatic **API keys** are prefixed `sq_` and are the intended public auth
mechanism (rolling out, see the API-keys epic). Today the same scheme also
accepts CLI tokens (`sqcli_` prefix, issued by `squirrel auth login`) and
dashboard session JWTs, so you can start integrating immediately.

## Public surface

These are the external-client-facing routes covered by the contract:

| Resource | Endpoints |
|----------|-----------|
| **Audits** | `POST /v1/agent-runs`, `GET /v1/agent-runs`, `GET /v1/agent-runs/{id}`, `GET /v1/agent-runs/{id}/report` |
| **Reports** | `POST /v1/reports`, `GET /v1/reports`, `GET /v1/reports/{id}`, `PATCH /v1/reports/{id}`, `DELETE /v1/reports/{id}` |
| **Credits** | `GET /v1/credits` |
| **Organizations** | `GET /v1/organizations/{id}` |

<Note>
Internal server-to-server callbacks (`/v1/*/internal/*`), webhook receivers
(`/v1/webhooks`, `/v1/github`), and admin-only routes (`/v1/admin/*`,
`/v1/stats`, `/v1/users`) are **not** part of the public contract and may
change without notice.
</Note>

<Note>
The cloud services the CLI calls during an audit (`/v1/services/*`) are not
part of the public contract either. One of them, the dead-link check
(`/v1/services/dead-links`), bills each link it checks to the audit run it
belongs to. A call that names no run is billed to your org instead: 1 credit
per distinct link it verifies, and nothing for a link it cannot verify (see
[Credits and pricing](/cloud/credits)). The one exception is a `squirrel` CLI
from before v0.0.114: its run-less calls are refused with `426 RUN_REQUIRED`
and never charged. To check a site's links, run an audit
(`POST /v1/agent-runs`) with external link checks on, or a signed-in
`squirrel audit`.
</Note>

## Start a run with a rule filter

`POST /v1/agent-runs` takes the run's settings as a `config` object. This request audits one page and runs the `ax` rules plus `core/robots-meta`, minus the three cloud-backed `ai/` rules. It skips the headless browser and external link checks, and treats the site as a one-shot check:

```bash
curl -X POST https://api.squirrelscan.com/v1/agent-runs \
  -H "Authorization: Bearer $SQUIRREL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com",
    "config": {
      "maxPages": 1,
      "enabledRulePatterns": ["ax/*", "core/robots-meta"],
      "disabledRulePatterns": ["ai/page-type-match", "ai/site-metadata", "ai/llm-parsability"],
      "render": false,
      "externalLinksEnabled": false,
      "ephemeral": true
    }
  }'
```

The response is `201` with the run `id`. Poll `GET /v1/agent-runs/{id}` until `status` is `completed`, then read `GET /v1/agent-runs/{id}/report`. With an API key `trigger` defaults to `api`; a signed-in session has to send it. `config` may also be sent as a JSON-encoded string, the older form.

### Two sets, like a lint config

`enabledRulePatterns` is the include set: only the rules it selects run. `disabledRulePatterns` is the disable set: the rules it names do not run. A run's rules are the include set minus the disable set, and **disable wins**: a rule named in both does not run. Leave `enabledRulePatterns` out to start from every rule. The website's own `disable_rules` are added to the disable set.

Both lists take the same patterns, with the same matching, limits and errors as the CLI's [`--rule-include` and `--rule-exclude`](/cli/audit): a category (`ax`), a category glob (`ax/*`) or an exact rule id (`core/robots-meta`). List ids with [`GET /v1/rules`](/api/rules/list): each rule carries `requiresCloud` (reads a cloud-backed step, credit-metered) and `requiresRender` (reads the render step, skipped with `render: false`), so a client can leave those out. At most 50 patterns of at most 100 characters each, using letters, digits and `-_./*`: no commas, spaces, regular expressions or control characters. Opt-in rules (`gaps/*`) cannot be selected.

<Warning>
`ax` includes three rules that kept the older `ai/` id prefix: `ai/llm-parsability`, `ai/page-type-match` and `ai/site-metadata`. They are the cloud-backed ones (the ai-parse and site-metadata services), so they are slower and credit-metered, and `ax/*` and `--rule-include ax` select them exactly as the CLI does. To leave them out, name their three exact ids in `disabledRulePatterns`, as in the example. Do not disable `ai/*`: `ai` is an alias of the whole `ax` category, so that glob switches off every `ax` rule.
</Warning>

| `config` key | What it does |
|--------------|--------------|
| `enabledRulePatterns` | The include set, above. Never empty. |
| `disabledRulePatterns` | The disable set, above. May be empty. |
| `render` | `false` fetches every page over plain HTTP with no per-page headless browser. `true` renders every page, within what the plan allows. Leave it out to follow the website's setting. Rendering does not change the price. |
| `externalLinksEnabled` | Check external links for this run. Each distinct link the cloud verifies costs 1 credit, so a one-page check that does not need them sends `false`. |
| `editorSummary` | Build the [editor's summary](/cloud/editor-summary), an LLM-written overview of the whole report that adds about 30 seconds to a run. Leave it out for the default: skipped when `enabledRulePatterns` is set (a filtered run), built on every other run. `true` builds it on a filtered run. `false` skips it on any run. No credit effect: the summary has no credit charge, built or skipped. |
| `ephemeral` | The same one-shot check as `ephemeral` on the MCP `run_audit`. If the run creates the website, that website skips the plan's website limit, stays out of website listings and is **archived** once the run ends. The run and its report are **not purged**, until a purge ships: `GET /v1/agent-runs/{id}` and the report keep working, and the run stays in `GET /v1/agent-runs`. An organization can hold at most 5 live one-shot websites (`429`, code `EPHEMERAL_LIMIT`). If the organization already tracks the domain, or you send `websiteId`, the run uses that website, nothing is deleted, and the response has `ephemeral: false` with an `ephemeralIgnoredReason`. Cannot be combined with `auditId`. |

A request the API cannot honour as written is a `400` with code `VALIDATION_ERROR`, and nothing is charged or started: invalid JSON, a value that is not an object, an unknown `config` key, a wrongly typed `maxPages`, `coverageMode`, `externalLinksEnabled`, `render`, `editorSummary` or `ephemeral` (the issue path is `config.editorSummary` for the summary flag), or a bad rule list. For a rule list, `error.patterns` names the entries at fault: an unknown category, a pattern that matches no rule (`core/robots-metaa`), or a list over the limits. A selection that the disable set leaves with no rule to run is refused too. The other refusals use their own codes: `402` `INSUFFICIENT_CREDITS` (checked before a one-shot website is created), `429` `QUEUE_FULL` and `EPHEMERAL_LIMIT`, `404` `WEBSITE_NOT_FOUND`, `409` `AUDIT_ID_IN_USE`.

The create response carries `editorSummary` (boolean) and, when it is `false`, `editorSummarySkippedReason` (`rule-filtered run` or `disabled by the run config`). Both appear only when `enabledRulePatterns` or `editorSummary` was sent.

The config a run reports in `GET /v1/agent-runs/{id}` can be sent back: the keys the server writes into it (`auditLevel`, `pageLimitNotice`, `creditClamp`, `renderMode` and the like) are accepted and dropped. The report of a run started with `enabledRulePatterns` is **partial**: it carries `partial: true`, its `healthScore` and every category `score` are `null` (a score from a subset of the rules is not the site's score), and a sibling `includeFilter` says which rules ran (the patterns and how many). The counts and `topIssues` still cover the rules that ran. The run itself says the same: `GET /v1/agent-runs/{id}` and `GET /v1/agent-runs` return `healthScore: null` and `partial: true` for such a run (the key is absent otherwise), and its row in the report's `history` has no score. A run with no `enabledRulePatterns`, or with only `disabledRulePatterns`, is unchanged.

A partial report also carries `results`: one entry for every rule the run selected, so a rule that passed is told apart from one that did not run (`topIssues` lists only warnings and failures, as text). Each entry has the `ruleId`, `category`, `name` and `severity`, a `status` (`pass`, `warn`, `fail`, `info`, `skipped` or `not_applicable`), a `skipReason` for the last two, and an `evidence` object:

```json
{
  "ruleId": "ax/ai-crawlers",
  "category": "ax",
  "name": "AI Crawler Access",
  "severity": "warning",
  "status": "info",
  "evidence": {
    "checks": { "pass": 0, "warn": 0, "fail": 0, "info": 1, "skipped": 0 },
    "occurrences": 0,
    "affectedPages": 0,
    "checkNames": ["ai-crawler-access"],
    "bots": [
      { "token": "OAI-SearchBot", "verdict": "allowed", "source": "robots_txt" },
      { "token": "GPTBot", "verdict": "blocked", "crawlerClass": "training", "source": "robots_txt" }
    ]
  }
}
```

`info` is an informational finding, neither a pass nor a problem. A rule the run selected but the stored report has no result for is `skipped` with `skipReason: "not_reported"`: it is never reported as `pass`. `skipReason` is one of a fixed set, for example `render_disabled` (a run with `render: false`), `not_authenticated` and `insufficient_credits` (a cloud step that could not run), `external_links_not_checked` and `not_applicable`. `evidence` holds counts and short tokens the rule itself wrote (check ids, and for `ax/ai-crawlers` each AI crawler's user-agent token with its verdict), and never a message, URL or label taken from the audited site, so an agent can read it without passing the site's own words through. The key is absent for a run with no `enabledRulePatterns`. A run with no `enabledRulePatterns` is unchanged: no `partial` key, scores as before. The hosted MCP `get_report` returns the same `partial` flag and null scores, and prints the score as N/A in its `llm` and `markdown` formats.

### Opt in to the editor's summary

A filtered run skips the editor's summary by default, so the one-page request above needs no flag. To get it back, send `editorSummary: true`:

```json
{
  "url": "https://example.com",
  "config": {
    "maxPages": 1,
    "enabledRulePatterns": ["ax/*", "core/robots-meta"],
    "render": false,
    "ephemeral": true,
    "editorSummary": true
  }
}
```

A skipped summary is absent from `GET /v1/agent-runs/{id}/report` (the `editorSummary` field is not there, not `null`). With `editorSummary: true` it is present as on any other run.

### Speed of a filtered run

A one-page filtered run skips the work no selected rule reads: the editor's summary, the external link check (when no selected rule reads link results: `links/dead-links`, `links/broken-external-links`, `reliability/broken-forms`, `integrity/known-malicious-url`) and any cloud service no selected rule reads. Skipped steps are recorded in the run timeline, below. How long a run takes still depends on the site, so treat any timing as an estimate.

### Run timeline and skipped steps

While a run is `pending` or `running`, `GET /v1/agent-runs/{id}` returns its latest `progress` event (`phase`, a message and a page count). A step the run skips is recorded as a single `skipped` event with a reason and no duration, for example `editor_summary skipped: rule-filtered run`. The phase names a polling client may see for skipped steps are:

| Phase | Reasons |
|-------|---------|
| `editor_summary` | `rule-filtered run`, `disabled by the run config` |
| `cloud_prefetch` | `no enabled rule reads a cloud service` |
| `external_links` | `no enabled rule reads external link results` |
| `render_prefetch` | `render disabled by the run config`, `the crawl rendered every page` (filtered runs only) |

The set of phase names is not a stable enum: match on the ones you know and ignore the rest. An API key sees only the latest phase through `progress`. The full event list is a signed-in view in the [dashboard](/dashboard). Skipping a step never changes the price of the steps that ran, and nothing is charged or refunded for a skipped one.

<Note>
The hosted MCP `run_audit` takes the same two sets as `rules` and `disable_rules`, with the same validation and the same errors, plus `editor_summary` for `config.editorSummary`. See [MCP](/developers/mcp).
</Note>

## Error envelope

All errors use one stable, typed shape:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Report not found",
    "requestId": "8a1f…"
  }
}
```

- `code`: stable, machine-readable (`SCREAMING_SNAKE_CASE`). Match on this.
  Treat unknown codes as opaque and fall back to `message`.
- `message`: human-readable; may change. Don't match on it.
- `requestId`: present when available; quote it to support for log lookups.

Common codes: `UNAUTHORIZED`, `FORBIDDEN`, `NO_ORG`, `NOT_FOUND`,
`VALIDATION_ERROR`, `INVALID_JSON`, `PAYLOAD_TOO_LARGE`, `SECURITY_VIOLATION`,
`INSUFFICIENT_CREDITS` (with `error.required` / `error.balance`),
`DUPLICATE_REQUEST`, `RUN_NOT_ACTIVE`, `UPSTREAM_ERROR` (with `error.reason`),
`RATE_LIMITED`, `QUEUE_FULL`, `EPHEMERAL_LIMIT`.

`SECURITY_VIOLATION` (`400`) is returned by `POST /v1/reports` when the report
payload trips the content security scanner; `error.threats` lists the matched
patterns.

<Note>
The shared auth middleware, the org gate, and the credit gate (`402`
`INSUFFICIENT_CREDITS`, `409` `DUPLICATE_REQUEST`, `409` `RUN_NOT_ACTIVE`) now
emit the typed envelope like every other documented route. Branch on the HTTP
status code, then split same-status conditions on `error.code`, not the human
`message`: a `409` is either `DUPLICATE_REQUEST` (this exact payload was already
charged) or `RUN_NOT_ACTIVE` (a cloud run was reaped or failed before the charge
landed, so it was never charged).
</Note>

`5xx` responses from unhandled server errors (DB/storage failures not caught by
a handler) are **not guaranteed** to follow the envelope: handle them by status
code and retry idempotent reads with backoff.

## Rate limiting

Rate limiting is being rolled out. When enforced, throttled requests return
`429 Too Many Requests` with these headers:

| Header | Meaning |
|--------|---------|
| `RateLimit-Limit` | Request quota for the current window |
| `RateLimit-Remaining` | Requests remaining in the window |
| `RateLimit-Reset` | Seconds until the window resets |
| `Retry-After` | Seconds to wait before retrying |

Back off on `Retry-After` and retry idempotent reads.

## Credits

Cloud operations (publishing reports, cloud audits) are priced in
[credits](/cloud/credits). When an organization runs out, the API returns
`402` with `code: "INSUFFICIENT_CREDITS"`.
