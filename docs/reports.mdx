squirrelscan generates comprehensive audit reports with a health score and detailed issue breakdown.

## Health score

The health score is calculated from 0-100 based on:

- **Rule weights** - Each rule has a weight (1-10) reflecting its importance
- **Check results** - Pass/fail/warning status of each check (warnings count as 0.5)
- **Scoring curve** - Compresses high scores to reward perfection
- **Penalties** - Applied for critical crawlability issues and high issue density

### Scoring formula

```text
Base Score = (Earned Weight / Total Weight) × 100
Curved Score = Base Score ^ 1.2
Issue Density Penalty = up to -45% when many errors/warnings (kicks in after 10+ issue units)
Final Score = Curved Score × Penalty Multipliers × Issue Density Multiplier
```

Issue units are volume-aware for errors: a failed check counts every element it
flags (a page with 40 unnamed buttons weighs ~40 units, not 1), capped per check
and page so a single bad page can't zero a score. Warnings count once per check.

The issue density penalty applies to the overall score and to every group and
category score individually, each from its own local counts. A group showing
100 errors can't score green while the overall grade is a D.

### Penalties

Critical crawlability issues reduce the final score:

| Issue | Penalty | Check |
|-------|---------|-------|
| Missing robots.txt | -15% | `crawl/robots-txt` |
| Robots blocks all | -50% | `crawl/robots-txt` |
| Missing sitemap | -20% | `crawl/sitemap-exists` |
| High issue density | up to -45% | Any rules (10+ issue units; errors count per flagged element) |

Penalties are multiplicative. For example, an 80% score with missing robots.txt (-15%) and no sitemap (-20%):

```text
80 × (1 - 0.15) × (1 - 0.20) = 80 × 0.85 × 0.80 = 54.4
```

### Rules that do not apply

A rule that does not apply to the audited site is skipped: its checks have status `skipped`, and they count toward neither the passed, warning and failed totals nor the score. A rule whose checks are all skipped carries no weight, so it cannot lift or lower the grade.

The most visible case is a local or private-network host such as `localhost` or `192.168.1.10`. The transport and delivery rules (HTTPS, HSTS, HTTP to HTTPS redirects, HTTP/2, compression and caching) judge the production edge a dev server is not, so they are skipped there and the report says so once, under Scan details in Report detail at the end. See [Transport and delivery rules do not apply](/guides/local-audits-cli#transport-and-delivery-rules-do-not-apply) for the list and how a host is classified.

### Grade scale

| Score | Grade |
|-------|-------|
| 90-100 | A |
| 80-89 | B |
| 70-79 | C |
| 60-69 | D |
| 0-59 | F |

### Group scores

Every category rolls up into one of four top-level groups, and each group gets its own 0-100 score. These are the four scores shown on reports and in the dashboard alongside the overall health score:

| Group | What it covers |
|-------|----------------|
| **SEO** | Crawlability, core SEO, content, links, structured data, images, social, accessibility, mobile, URLs, internationalization, E-E-A-T, local, video, analytics |
| **Performance** | Page speed and loading performance, and reliability: broken links, scripts, stylesheets, fonts and forms |
| **Security** | HTTPS and headers, site integrity, legal compliance, blocked content |
| **Agents** | Agent experience: how ready the site is for AI agents to read, discover, and operate on it |

Group scores use the same weighted formula and scoring curve as the health score. The crawlability penalties apply only to the overall health score.

### Category scores

Each category (core, content, links, etc.) receives its own score:

- Weighted by rule importance within category
- Includes pass/warning/fail counts
- Sorted by error count (most errors first)
- Perfect categories (100%, no issues) shown last

## Output formats

squirrelscan supports multiple report formats optimized for different use cases.

### Issue ordering

Every format lists issues in the same order, so the top of the list is always
the work to do first:

1. **Severity** - errors, then recommendations, then warnings.
2. **Category** - within a severity, issues from the same category stay together,
   higher-priority categories first.
3. **Rule weight** - within a category, heavier rules first.

Categories are not top-level sections: a category with both an error and a
warning appears under both severities.

### Findings in a shared page region

A finding that sits in a part of the page every page repeats is one thing to
fix in one template, so the report names the region instead of listing every
page:

```text
-> shop
    In the site header, on 120 of 120 pages
```

These are the regions, and how the line names them:

| Region | The line reads |
| --- | --- |
| `header` | In the site header |
| `footer` | In the site footer |
| `navigation` | In the site navigation |
| `sidebar` | In the sidebar |
| `breadcrumbs` | In the breadcrumbs |
| `pagination` | In the pagination |
| `newsletter_signup` | In the newsletter signup |
| `social_share` | In the social share links |
| `business_info` | In the business details |
| `account_login` | In the account links |

The page content, comments, related content and the author byline differ from
page to page and are never regions.

A finding is shown this way when it sits in the region on at least 80% of the
pages that have that region, and on at least 2 pages. The share is counted
against the pages that have the region, not every audited page, so a footer
missing from a few pages does not hide a finding that is on every footer. A
sidebar on 6 pages is judged against those 6. When the finding is also
elsewhere, the line says so (`, and on 3 other pages`) and those other pages
are listed under it. The item's label then leaves out its own section phrase
(`https://example.com/old (404)`, not `..., linked in the footer`), since the
region line says where it is; an item that is not shown for a region keeps it.

The Markdown, text, LLM and console reports print the region line and no
per-page list, and leave out the check's page list when its findings name their
regions. The HTML report keeps every page, behind a collapsed list. The JSON
and XML reports keep the bounded page list and add the region as data (see
[source pages](/configuration/output#source-pages)).

A finding in the page content, a finding in a region on only a few of the pages
that have it, and any report without page structure data (a crawl stored
before link sections were recorded, or the page classifier and landmarks found
nothing) keep their page lists. Which part of the page a link sits in comes
from the page's landmarks and the page classifier; see
[link sections](/rules/links/broken-links#what-squirrel-checks). Nothing about
how a finding is detected, its severity or the score changes.

These rules record where their finding sits: `a11y/link-text`,
`links/broken-links`, `links/broken-external-links`, `links/broken-anchors`,
`links/redirect-chains`, `links/anchor-text`, `links/tel-mailto`,
`links/https-downgrade`, `links/invalid-links`, `links/nofollow-internal` and
`content/stale-copyright` (always the footer).

### Findings on every page of one page type

A finding that sits on all, or nearly all, of the pages of one kind has the same
template behind every page, so the report names the page type instead of
listing the pages. The expected-schema check on a site with a documentation
section reads:

```text
[X] expected-type: Reads as a documentation page but declares no Article, TechArticle, HowTo or FAQPage structured data (9 pages)
    On 9 of 11 documentation pages
```

and `On all 9 documentation pages` when it is every one. The page types are the
ones the [page classifier](/configuration/classifier) names, in the plural words
of the [page structure](/configuration/output#page-structure) block: documentation pages, product
pages, product listings, articles, blog posts, about pages, contact pages and
listing pages.

A finding is shown this way when all of its pages are the same page type, it
is on at least 2 pages, and those pages are at least 80% of the audited pages
of that type. The share is counted against the audited pages of the type in the
page structure block, not every audited page, so a documentation section is
judged against its own pages. Those pages include any the classifier called
documentation pages but the rule did not judge (it only acts on a page type the
model is 0.9 sure of by default), which is why a finding on every page it judged
can still read `9 of 11`. The report never says `all` for a finding on more pages
than it counted of the type.

The Markdown, text, LLM and console reports print that line and no page list.
The HTML report keeps every page, behind a collapsed list. The JSON and XML
reports keep the bounded page list and add `scope` with the page type, the pages
the finding is on and the audited pages of that type (see
[source pages](/configuration/output#source-pages)).

A finding on pages of mixed types, on a single page, on fewer than 80% of the
pages of its type, a finding carried over from an earlier audit (its pages are
not in this audit's counts), and any report without page structure data (a crawl stored
before page types were recorded, or the page classifier off) keep their page
lists. Nothing about how a finding is detected, its severity or the score
changes. Only `schema/expected-type` is scoped this way today: it is the one
rule that records a page type from the classifier on its findings.

### html

Interactive HTML report that opens in a browser.

```bash
squirrel report -f html -o report.html
open report.html
```

The local file and the published report at reports.squirrelscan.com are the same page. [See a live one](<https://reports.squirrelscan.com/01M5NJH51Q6FNRAA3QGW8GYWB6>), or read [how to read your report](/guides/read-your-report) for a walk through it.

![A squirrelscan report for squirrelscan.com. The header shows the site, 220 of 220 pages scanned, the Full audit level and a health score of 79 (C). A notice says 912 of 1412 external links were not checked. Four group cards show SEO 86 (B), Performance 59 (F), Security 95 (A) and Agents 42 (F), each with its error and warning counts. Below are pass, warning and fail totals, an auto-generated summary, and the first three ranked issues, each with a Copy fix prompt button.](/images/report/example-report.webp)

Top to bottom:

- **Overview:** the health score, the four group scores (SEO, Performance, Security, Agents) and the pass, warning and fail counts. Each group score links to its findings. Score rings, numbers and grades are colored by score, red to green, like the health score; each group keeps its own color on its card and label.
- **Coverage notice:** when the crawl hit its page limit, ran out of time or found more pages than it scanned, one line at the top of the report says it may not cover the whole site, with how many more pages are known when there are any. Raise the audit depth with `--level full` or `--max-pages N` in the CLI, or in the website settings for a cloud audit; the line links to [Audit levels](/guides/audit-levels). Dismiss it with its close button: it stays hidden for that report in that browser. The other notice lines under it (checks that did not run, a refused seed redirect and similar) dismiss the same way, each on its own. A published report notes in its footer that it lists sample pages.
- **Summary** (cloud audits): the [editor's summary](/cloud/editor-summary) of the audit.
- **Issues:** what to fix, in order. Cloud audits rank the fixes for the detected stack, each with the rules it clears. A local audit lists its most widespread errors and warnings instead.
- **Findings:** every flagged rule, banded by severity (errors, recommendations, warnings) and filterable by group. Each one opens to its checks, affected pages, the fix and a link to the rule docs.
- **Pages:** the same findings by URL, worst page first.
- **Site:** the site profile and the detected tech stack.
- **Search footprint** (cloud audits) and **Entities**, the site's JSON-LD as one [entity map](/guides/entity-map).

#### Copy fix prompts

Every finding has a **Copy fix prompt** button, and so does every ranked issue. The Issues list also has a **Copy fix plan** button that covers all of them in order. Paste the prompt into your coding agent: it names the rules to fix and links their docs, quotes the audit's evidence (messages and example pages), and ends with the command to verify the fix:

```bash
squirrel audit 'https://example.com/' --rule-include core/meta-title
```

Text that comes from the audited site, or from automated analysis of it, sits inside a fenced block the prompt labels as untrusted data, one line per item, so a page cannot slip instructions into your agent's task. The buttons need JavaScript and clipboard access; without them, the prompt opens on the page for you to select.

#### Local reports

A local HTML report is one self-contained file. Opening it makes no network request: the styles and scripts are inline, and it shows no favicon or technology logos (those come from squirrelscan.com in published reports). Links to the audited pages and the rule docs work as usual.

A signed-out local audit also shows a **Get the full audit with squirrelscan cloud** card: what a free account adds to the same report, and the checks on this site that need the cloud and did not run. Run `squirrel auth login` to add them. See [Cloud overview](/cloud).

#### White-label reports

A report from a Team or Enterprise organization with white-label reports turned on carries its brand instead of squirrelscan's. The header shows the organization's logo, or its brand name when there is no logo, linked to its website when one is set. The footer shows its footer text and a link to its website where the "Generated by squirrelscan.com" credit was, and the squirrelscan sign-up and upgrade prompts are left out. The Markdown and text reports end with the same footer text and website. Only an `https://` website is linked. To set it up, see [Team plan](/cloud/team).

### llm

**Compact token-optimized format for coding agents** - hybrid XML/text structure designed for LLM consumption.

```bash
squirrel report -f llm -o report.xml
```

or pipe directly:

```bash
squirrel report -f llm | claude "analyze this audit and prioritize fixes"
```

**Format Structure:**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<audit version="0.0.13">
<site url="https://example.com" crawled="42" date="2025-01-18T10:30:00Z"/>
<score overall="87" grade="B">
 <cat name="Core SEO" score="100"/>
 <cat name="Links" score="85"/>
 <cat name="Images" score="72"/>
</score>
<summary passed="83" warnings="13" failed="9"/>
<issues>
 <rule id="images/alt-text" severity="error" category="Images" group="seo" status="fail">
  Desc: All images must have descriptive alt text
  Fix: Add alt attributes to img tags
  Items (6):
   - /products/widget.png (from: /products)
   - /hero.jpg (from: /)
 </rule>
 <rule id="content/word-count" severity="warning" category="Content" group="seo" status="warn">
  Low word count: 150 words (min: 300)
  Desc: Pages should have sufficient content for good SEO
  Fix: Add more relevant content to improve page depth
  Pages (3): /blog/post-1, /blog/post-2, /about
 </rule>
</issues>
<locked-rules count="7" audience="anonymous-upsell">
 Cloud-powered checks (page rendering, AI content analysis, link-rot, brand protection, and more) run with a free squirrelscan account.
 <cta label="Get started to unlock them" url="https://squirrelscan.com"/>
 <rule id="ai/llm-parsability" name="LLM Parsability"/>
 <rule id="ai/site-metadata" name="Site Metadata"/>
</locked-rules>
</audit>
```

**Key Features:**
- **40-70% smaller** than verbose XML (125KB vs 209KB for 51-page audit)
- **1-space indentation** for token efficiency
- **Inline attributes** - metadata as XML attributes, not nested elements
- **Text prefixes** - `Desc:`, `Fix:`, `Pages (n):`, `Items (n):`
- **Comma-separated lists** - pages and URLs formatted inline
- **Hybrid structure** - XML tags for parsing, text for readability
- **`<locked-rules>`** - cloud-gated checks that didn't run this audit (logged out, the quick level, out of credits), with an audience-aware action and, for anonymous/free runs, a signup or credits link. Absent when every eligible check ran.
- **`<audit-level>`** - the [audit level](/guides/audit-levels) the audit ran at: `level` (`quick`, `surface`, `full` or `custom`), `based-on`, the `changes` made to it (setting names, comma-separated) and the page budget. On an `--offline` run it also carries `offline="true"`, `cloud-checks="false"`, `render="off"` and `external-links="false"`: the settings that ran, not the level's cloud defaults. Absent on reports from before audit levels.

**Token Efficiency:**
The LLM format achieves significant size reduction through:
- Minimal indentation (1 space vs 2-4)
- Flattened hierarchy (fewer nesting levels)
- Inline attributes instead of nested elements
- Comma-separated lists instead of multiple elements
- Text prefixes instead of wrapping tags

**Use Cases:**
- Piping to Claude Code, Cursor, or other coding agents
- Token-limited API contexts (Claude API, GPT)
- Cost optimization for LLM processing
- Agent-based workflows requiring structured output

See [OUTPUT-FORMAT.md](https://github.com/squirrelscan/skills/blob/main/skills/audit-website/references/OUTPUT-FORMAT.md) for complete format specification.

### xml

**Verbose structured XML format** for enterprise integration and detailed archival.

```bash
squirrel report -f xml -o report.xml
```

**Format Structure:**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<squirrelscan-audit version="0.0.117">
  <site>
    <url>https://example.com</url>
    <pages-crawled>42</pages-crawled>
    <audit-date>2025-01-18T10:30:00.000Z</audit-date>
    <scan-scope origin="cli" crawled="42" max-pages="100" capped="false"/>
  </site>
  <health-score overall="87" grade="B">
    <category name="Core SEO" score="100"/>
  </health-score>
  <summary passed="180" warnings="6" failed="2"/>
  <issues>
    <rule id="content/word-count" severity="warning" category="Content" group="seo">
      <name>Word Count</name>
      <description>Pages should have sufficient content</description>
      <solution>Add more relevant content to improve page depth</solution>
      <check name="word-count" status="warn">
        <message>Low word count: 150 words (min: 300)</message>
        <affected-pages count="2" examples="2" has-more="false">
          <page url="https://example.com/blog/post-1"/>
          <page url="https://example.com/blog/post-2"/>
        </affected-pages>
      </check>
    </rule>
  </issues>
</squirrelscan-audit>
```

`<scan-scope>` says where the audit ran (`origin`: `cli`, `ci` or `cloud`), how many pages it crawled, the page limit in force (`max-pages`), and whether that limit stopped the crawl (`capped`). `requested-max-pages` appears only when the limit you asked for was lowered, and `stop-reason="time"` only when the crawl time budget ended the crawl. `unfetched` appears when the crawl stopped with in-scope URLs still queued: pages it found (in a sitemap, linked from a crawled page, or carried from an earlier audit) but never fetched. `crawled` plus `unfetched` is how many pages the crawl knew of. It is a floor: the links on the pages still queued are unknown, so the site may have more. On a rate-limited run, the `unfetched` count on `<rate-limited>` already includes these. A report from before scan scope existed has no `<scan-scope>`. A white-label report's root element is `<audit>`.

**Key Features:**
- **2-space indentation** for readability
- **Fully nested elements** - all metadata in dedicated tags
- **Explicit structure** - strict schema compliance
- **Detailed metadata** - all information preserved
- **Enterprise-ready** - suitable for XML parsers and validators

**Comparison: LLM vs XML**

| Aspect | LLM Format | XML Format |
|--------|-----------|------------|
| Size (51 pages) | 125KB | 209KB |
| Indentation | 1 space | 2 spaces |
| Structure | Hybrid XML/text | Pure XML |
| Metadata | Inline attributes | Nested elements |
| Lists | Comma-separated | Multiple elements |
| Best For | Coding agents, tokens | Enterprise, archival |

**Use Cases:**
- Enterprise data integration
- Detailed audit archival
- Schema validation requirements
- XML processing pipelines
- Long-term storage with full metadata

## Filtering reports

### By severity

Show only errors:
```bash
squirrel report --severity error
```

Show only warnings:
```bash
squirrel report --severity warning
```

### By category

Filter by single category:
```bash
squirrel report --category core
```

Filter by multiple categories:
```bash
squirrel report --category core,links,images
```

**Available categories:**
- `core` - Core SEO elements (title, meta, canonical)
- `content` - Content quality (word count, headings, duplicates)
- `links` - Link analysis (internal, external, redirects, anchor text)
- `images` - Image optimization (alt text, formats, dimensions)
- `schema` - Structured data (JSON-LD validation)
- `security` - Security headers (HTTPS, CSP, HSTS)
- `a11y` - Accessibility (ARIA, contrast, focus)
- `i18n` - Internationalization (lang, hreflang)
- `perf` - Performance (LCP, CLS, lazy loading)
- `reliability` - Reliability (broken internal, external and anchor links, scripts, stylesheets and fonts that fail to load, broken forms)
- `social` - Social media (Open Graph, Twitter Cards)
- `crawl` - Crawlability (robots, sitemaps, indexability)
- `url` - URL structure (length, keywords, parameters)
- `mobile` - Mobile optimization (viewport, tap targets)
- `legal` - Legal compliance (privacy, cookies, terms)
- `local` - Local SEO (NAP, geo tags)
- `video` - Video optimization (schema, thumbnails)
- `analytics` - Analytics tracking (GTM, consent)
- `eeat` - E-E-A-T signals (author, expertise, trust)
- `blocking` - Ad-blocker & privacy-filter impact (`adblock` still accepted)

A report keeps the categories its rules had when it was stored. The broken-link rules (`links/broken-links`, `links/broken-external-links`, `links/broken-anchors`) moved from `links` to `reliability`, so `--category links` still finds them in a report stored before the move, and `--category reliability` finds them in newer ones.

### Combined filters

Combine severity and category filters:
```bash
squirrel report --severity error --category links,images
```

## Diff reports

Compare a baseline audit to the current report:

```bash
squirrel report --diff a7b3c2d1 --format json
```

Compare the latest report for a domain against a baseline audit:

```bash
squirrel report --regression-since example.com --format llm
```

<Note>
Diff mode supports `console`, `text`, `json`, `llm`, and `markdown`. `html` and `xml` are not supported in diff mode. Diff reports cannot be published with `--publish`.
</Note>

## CI/CD integration

### Fail build on low score

```bash
#!/bin/bash
SCORE=$(squirrel audit https://example.com -f json | jq '.healthScore.overall')
if [ "$SCORE" -lt 80 ]; then
  echo "Health score too low: $SCORE/100 (minimum: 80)"
  exit 1
fi
```

### Fail on errors

```bash
#!/bin/bash
ERRORS=$(squirrel audit https://example.com -f json | jq '.healthScore.errorCount')
if [ "$ERRORS" -gt 0 ]; then
  echo "Audit failed with $ERRORS errors"
  exit 1
fi
```

### GitHub Actions example

Use the official action and gate the build with [`--fail-on`](/cli/audit): it
exits `2` when a threshold trips, so the job fails automatically:

```yaml
name: Audit
on: [pull_request]
jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: squirrelscan/audit-action@v1
        id: audit
        with:
          url: https://preview.example.com
          fail-on: "score<80,severity>=error"
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: audit-report
          path: ${{ steps.audit.outputs.report }}
```

This gates pull requests; swap the trigger to `on: [push]` (or add `branches`)
to gate pushes to a branch instead. See the [CI integration guide](/guides/ci)
for GitLab, generic runners, and token setup.

## Report storage

Audit reports are stored in a local SQLite database at:

```text
~/.local/share/squirrel/audits.db
```

### List stored audits

```bash
squirrel report --list
```

**Output:**
```text
Recent Audits:
================================================================================
ID       Date                   Pages    Status
--------------------------------------------------------------------------------
a7b3c2d1 1/17/2026, 10:30 AM    42       complete
  https://example.com
5e9f1a3b 1/16/2026, 3:45 PM     38       complete
  https://test.com

Total: 2 audits
```

### View specific audit

By ID:
```bash
squirrel report a7b3c2d1
```

By domain:
```bash
squirrel report example.com
```

### Delete old audits

Reports are kept indefinitely. To clean up:

```bash
# Remove specific audit
rm -rf ~/.local/share/squirrel/audits.db

# This will be regenerated on next audit
```

## Publishing reports

Share audit reports online by publishing to `reports.squirrelscan.com`. Published reports can be shared with clients, included in documentation, or consumed programmatically by LLMs and CI pipelines.

<Note>
Publishing requires authentication. Run `squirrel auth login` first.
</Note>

### Auto-publish (default when logged in)

When you're **logged in and online, every `squirrel audit` auto-publishes to your dashboard as `unlisted`** - you get a shareable link and issue history with no extra flags. **Publishing is included in the audit base charge**, whatever the visibility. Logged-out and `--offline` runs never publish.

```bash
# logged in → auto-publishes (unlisted) and prints the URL
squirrel audit example.com
```

Skip publishing for a single run:

```bash
squirrel audit example.com --no-publish
```

Turn auto-publish off for the project (`squirrel.toml`):

```toml
[cloud]
publish = false
```

See [Cloud Settings](/configuration/cloud) for the `publish` and `visibility` config options.

### Publish from CLI

`--publish` forces a publish even when `[cloud] publish = false`, and works from a stored audit too:

```bash
squirrel report --publish
squirrel report a7b3c2d1 --publish --visibility unlisted
```

The CLI prints the published URL:

```text
https://reports.squirrelscan.com/SJEItpldwW
```

### Visibility

| Level | Description |
|-------|-------------|
| `public` | Listed and searchable |
| `unlisted` | Accessible via direct link only (default) |
| `private` | Only visible to you when logged in |

```bash
squirrel report --publish --visibility private
```

<Note>
Publishing is included in the audit base charge, whatever the visibility. Flipping an existing report's visibility later (in the [dashboard](/dashboard) or via the API) is free.
</Note>

### Secrets in URLs

A crawl sometimes reaches a URL that carries a secret: a reset link's `?token=`, a signed file's `X-Amz-Signature`, a session id the server wrote into its links (`;jsessionid=`, `?PHPSESSID=`), a JSON Web Token in the path, or a `user:password@` login. A published report never stores those values. The cloud replaces each one with `REDACTED` everywhere the report names the URL, in page lists, issue items and messages alike:

```
https://example.com/reset?token=REDACTED&lang=en
https://example.com/shop;jsessionid=REDACTED
```

A value that looks like ordinary content is kept: a short number or a word under a name such as `?session=2026` or `?sid=42` is a page, not a secret, and a short one-time code such as `?otp=123456` has the same shape as a page number and is not redacted. The parameter name stays, so you can still see which page it was and which link to fix. The same page gets the same redacted URL in every audit, so issue history and audit diffs still match it. Session parameters on links to other sites are kept as written, and credentials such as `token` or a signature are redacted there too.

Your local report keeps the URLs exactly as the crawler saw them.

### Output formats via URL

Published reports support multiple output formats. Append a file extension to the report URL to get a specific format:

| Format | URL | Use Case |
|--------|-----|----------|
| HTML | [/SJEItpldwW](https://reports.squirrelscan.com/SJEItpldwW) | Browser viewing (default) |
| JSON | [/SJEItpldwW.json](https://reports.squirrelscan.com/SJEItpldwW.json) | CI/CD, programmatic access |
| Markdown | [/SJEItpldwW.md](https://reports.squirrelscan.com/SJEItpldwW.md) | Documentation, READMEs |
| Plain Text | [/SJEItpldwW.txt](https://reports.squirrelscan.com/SJEItpldwW.txt) | Email, logs |
| XML | [/SJEItpldwW.xml](https://reports.squirrelscan.com/SJEItpldwW.xml) | Enterprise integration |
| LLM | [/SJEItpldwW.llm](https://reports.squirrelscan.com/SJEItpldwW.llm) | Coding agents, token-efficient |

Every format is the same capped summary, the JSON included: each issue keeps up to 10 example pages and 5 items beside its true counts, which the JSON carries in a sampled check's `details` (`pagesTruncated` for pages, `occurrences` for per-page checks, `additional` for items left out). The HTML, markdown and text formats print that count beside the items they list, for example `1 item, 37 more not listed`, or on its own (`1,500 items not listed`) for an issue that lists none. The console adds it to its `... +N more` line after the first 5 items, or prints it on its own the same way. The llm format counts it in each rule's item total (`Items (5/1152):`, or `Items (0/1500): none listed` when nothing is listed), and the XML gives it as a `not-listed` attribute on the check's `<items>` element (`<items count="0" not-listed="1500"/>` when nothing is listed). When a rule's issues reach different pages, the JSON's top-level `rulePageCounts` gives that rule's exact page count, which adding up its sampled issues cannot. Its top-level `linkTargetSets` holds, for each link rule, short hashes of every target the rule reported broken and every one it could not verify, so a later audit can tell a newly broken link from one that was already broken. A set marked `complete: false` holds only some of them. No format renders it. A capped report says so in its top-level `detail` field, and every format of a capped report prints one line saying where the full list is. See [size cap on large sites](#size-cap-on-large-sites).

Without an extension, the format is determined by the `Accept` header. Browsers receive HTML, while tools like `curl` can request specific formats:

```bash
# Get JSON via Accept header
curl -H "Accept: application/json" https://reports.squirrelscan.com/SJEItpldwW

# Get JSON via extension (simpler)
curl https://reports.squirrelscan.com/SJEItpldwW.json

# Pipe LLM format to Claude
curl -s https://reports.squirrelscan.com/SJEItpldwW.llm | claude "prioritize fixes"
```

### Size cap on large sites

A published report is a summary. Each issue lists a sample of affected pages with the true count, and your dashboard tracks which issues are fixed from one audit to the next.

To tell a fixed page from one that just fell outside the sample, a publish also sends a compact list of every page it crawled and which of those still fail each check. That list has a fixed size budget of 192 KB, shared with the list of pages that returned an error status. Most sites fit every page, up to the 10,000-page crawl limit. Sites with long, unique URLs fit fewer, about 4,000 to 5,000 pages.

When a crawl is bigger than that:

- The pages that don't fit are still counted as audited.
- An issue on one of those pages is never closed early: it stays open until an audit can confirm the fix.
- The checks that cost the most to list, such as one failing on about half the pages with no pattern, can be dropped first. Their issues stay open the same way.

The full per-page results are never cut. They stay in your local project: run `squirrel report --format json` or `squirrel report --format llm` to read every page and every finding.

### Managing published reports

Visit the [dashboard](https://app.squirrelscan.com) to manage published reports:

- Change visibility (public/unlisted/private)
- Delete published reports
- View report analytics (view count, last viewed)

A report you make private or delete can still be shown to visitors for a few minutes (at most about 3) from a copy that was already cached. Only public and unlisted reports are cached; private reports never are.

See [Dashboard](/dashboard) for full documentation.

## Failed audits

An audit that fetched no pages has no score and no issue list. The report names why: DNS, TLS, a refused or reset connection, a timeout, a 4xx or 5xx status, a redirect it could not follow, or `robots.txt`. See [failed audits](/guides/failed-audits) for the full list and the fix for each.
