title: "Thumbnails without srcset: small images serving large files"
description: "A 60 by 60 avatar that loads a 2000 pixel photo wastes almost all of it. squirrel flags small images whose measured file is heavier than their displayed size needs."
---

## What the size mismatch is

An image is served at one size and displayed at another. When the displayed size is much smaller, most of the downloaded bytes are discarded by the resize.

The clearest case is a thumbnail: an avatar, a product grid tile, a logo in a list. Those are rendered at a hundred pixels or less, and if the same file is also used as a full-size image elsewhere, every thumbnail on the page pays for it. `srcset` or `<picture>` is what lets the browser take a smaller file instead.

## What squirrel checks

The rule runs on every crawled page over every `img[src]` that has both `width` and `height` attributes as parseable non-zero numbers. Images without those attributes, or with a percentage, are not examined. The declared attributes stand in for the displayed size; CSS that resizes the image is not read.

An image is a candidate when its declared width and height are both at or below `max_thumbnail_dimension` and it has no `srcset` and no `<picture>` ancestor. A candidate is reported only on evidence that its file is oversized, and the evidence is the file's byte size from the resource check squirrel runs before the rules. squirrel never downloads an image to read its pixel dimensions.

The test is a byte budget: the size of an uncompressed 8-bit bitmap with 4 bytes a pixel for the displayed box at 2x density, so `128 x 128 x 4` = 64 KB for a 64x64 image. A compressed still image with that many pixels is smaller than the raw bitmap, so a file over the budget is heavier than the box needs. It has more pixels than a 2x screen draws there, or it carries extra bit depth or metadata. The excess must be at least 4 KB, the savings threshold Lighthouse's `uses-responsive-images` audit applies.

Because the rule weighs the file rather than measuring its pixels, it misses an oversized image that compresses well, such as a 1200 pixel JPEG of 20 KB shown at 64x64. It can also report an animated WebP or PNG shown at its natural size, since animation frames add bytes the way extra pixels do.

- Skipped when there is no parsed document. Message: `No document available`.
- Info when the page has no images. Message: `No images found on page`.
- `images-possibly-oversized` warns for candidates whose measured file exceeds the budget by 4 KB or more. The measured file is the one the parser records for the image: `data-src`, `data-original` or `data-lazy-src` when present, otherwise `src`. Message: `6 small image(s) serve files larger than their displayed size needs`. It lists up to ten as `avatar.jpg (64x64, 390.6 KB, no srcset)`, with the URL, the byte size and the budget, and gives the count of the rest. Severity warning, weight 5.
- `responsive-size` passes when images with dimensions were examined and none was reported. Message: `Image sizes appear appropriate`.
- `responsive-size` reports info when no image yielded two dimensions that parse as non-zero integers. An absent attribute reaches this branch, and so does `width="0"` or `height="invalid"`. Message: `No images with explicit dimensions to check`.

A candidate with no measured size is not reported. That covers images on another host (the resource check measures only the site's own domain and its subdomains), and images the check skipped or could not measure. SVG, ICO and GIF files (by the extension of the URL's path, in any case) and `data:` sources are skipped. Vector and icon files do not scale by pixel count, and a GIF's animation frames multiply its bytes.

Elements inside `<noscript>` are skipped: a browser with scripting enabled reads `<noscript>` content as plain text, so nothing in it loads or renders. See [content inside noscript](/rules#content-inside-noscript).

## How to fix it

```html
<img src="/avatar-64.jpg" srcset="/avatar-64.jpg 64w, /avatar-128.jpg 128w"
     sizes="64px" width="64" height="64" alt="…" />
```

Generate a thumbnail variant and reference it, or hand the resize to an image CDN with a width parameter. Two candidates are enough for a fixed-size thumbnail: one for standard displays and one for high-density ones.

A still 8-bit thumbnail served at its natural size, or at twice it for high-density screens, stays under the budget unless it carries heavy metadata, with or without `srcset`.

| | |
|---|---|
| **Rule ID** | `images/responsive-size` |
| **Category** | [Images](/rules/images) |
| **Scope** | Per-page |
| **Severity** | warning |
| **Weight** | 5/10 |

## Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `max_thumbnail_dimension` | number | `100` | Max dimension to consider as thumbnail |

### Configuration example

```toml squirrel.toml
[rule_options."images/responsive-size"]
max_thumbnail_dimension = 200
```

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["images/responsive-size"]
```

### Disable all Images rules

```toml squirrel.toml
[rules]
disable = ["images/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["images/responsive-size"]
disable = ["*"]
```
