## What brand impersonation is

Brand impersonation, in this context, is a page on your own site that presents another company's sign-in or booking surface while sending the credentials somewhere that company does not own. It is the shape of an injected phishing kit: the attacker uses your domain's reputation to make the fake login look trustworthy.

A legitimate integration always targets the provider's own host, `accounts.google.com` for Google or `calendly.com` for Calendly. Merely naming a brand is not impersonation, and neither is your own app's generic sign-in form. The defect is the mismatch between what the control says and where it points.

## What squirrel checks

The rule runs on every crawled page and emits at most one check named `brand-impersonation`. It fires only when all of the following hold on the same page: the page has a credential affordance, meaning an `input[type="password"]`, sign-in copy in the title or body text, or a link whose own label says `sign in`, `log in` or `login` (a link labelled only `verify` or `continue with` is not enough by itself); the text matches a brand's lexicon; the text also matches one of that brand's action cues; and a credential control whose own label names that brand points at a host that is neither the brand's legitimate host nor the site's own registrable domain.

- Info when this is the only integrity signal on the page. Message: `Possible Calendly brand impersonation (single signal — review)`.
- Fail when at least two distinct integrity signals fire on the page. Message: `Likely phishing kit impersonating Calendly (3 corroborating integrity signals)`.

Six brands are covered: Google, Microsoft, Calendly, DocuSign, ClickFunnels and Kajabi, each with its own lexicon, action cues and legitimate hosts. The credential surface is deliberately narrow: form actions on forms that contain a password field, and controls whose own label matches `sign in`, `log in`, `login`, `continue with` or `verify`. A control is a link, a `<button>`, an `<input type="submit">`, `button` or `image`, or an element with `role="button"`, and its label is read from its text and from `aria-label`, `title`, `value` and the `alt` of a logo image inside it, so a label that exists only in an attribute counts. A button's destination is its `formaction` or its form's `action`; a button with neither has none to judge. Google's own wording (`Continue with Google`, `Log in with Google`) and the Microsoft equivalents count as sign-in labels. Labels are normalised before matching: fullwidth and styled letters fold to ASCII (Unicode NFKC), and Cyrillic and Greek look-alikes for Latin letters map to the Latin letter. Text spliced into a label does not hide it: `<script>`, `<style>` and `<noscript>` content is not text, and the label is read both with and without text hidden by an inline style (`display:none`, `visibility:hidden`, zero font size, zero opacity), a class a `<style>` block hides, `hidden` or `aria-hidden`, and with and without a space at each element boundary and with no spaces at all, so `Sign<br>in with Goo<i>gle</i>` reads as the phrase it is. Links and buttons inside a `<template>` (nested ones too), a button tied to its form by `form=`, a label named by `aria-labelledby`, and a logo `alt` any number of levels inside its link (up to 64) are read. The reading is bounded by work, so a hostile page cannot make the rule slow, and every bound that can cut a relevant read is reported (see the end of this paragraph). A link whose destination, as a browser resolves it (tabs and newlines inside the URL are removed first and a backslash is a slash, both when deciding whether it is the page's own site and when ranking which controls get the longer read), is the page's own site is skipped unless it has an attribute that could carry a cue (`aria-label`, `title`, `aria-labelledby`, a logo `alt`); this ignores a `<base href>` that points elsewhere (tracked in #1423). A control with no destination (a script-driven button outside any form) is not read either. Of the rest, buttons and links with a sign-in path come first, then links to other hosts, and at most 60,000 are read (a flood of off-site links cannot push a real control out); a destination is judged as a browser reads it (tabs and newlines removed, `\\` as `/`), and a sign-in path is looked for in its first 8,192 characters; templates (nested ones too) are read in place, at most 5,000 of those with an element inside; an `aria-labelledby` target is read once however many controls name it, at most 256 nodes of it, and at most the first 4 targets of a control are used; an attribute is normalised (padding spaces and zero-width characters removed) over its first 16,000 characters and read in overlapping 300-character windows with a stride of 150, so a phrase crossing a window edge is still read. A window edge that falls inside a word is marked, so a window cut out of `Redesign in with Google` is not read as `sign in with Google`. The first window of every attribute is always read. The windows after it have their own budget, separate from the node budget below: they are read only where the start of a sign-in or brand phrase is in them (the words come from one list of auth wording and the rule's own lexicon, the same list the label patterns are built from), and at most 40 per attribute; over that, windows that name a brand (`google`, `microsoft`, ...) are kept before windows that only repeat a sign-in word. A control that wraps several logos reads the `alt` of its first four in full and the next ones for their first 300 characters, and keeps at most 100 in all; the control is counted as not read in full when a later alt is longer than 300 characters or when there are more than 100. Every control with long attributes keeps two of its cue windows outside the page budgets (its first and its last, across all its attributes), so no run of earlier controls can leave a later one with only the first window of each attribute. That floor is extra work bounded by the page: up to two windows of 300 characters per control, about 120,000 windows on a page of 60,000 controls. Beyond that floor the page has 20,000 windows to spend: half in order (controls with a sign-in or brand word in an attribute first, then document order, so the first controls of the page are always read in full) and half shared fairly over the controls that are still cut, those with no cue word as written (an obfuscated spelling) first. A control is counted as not read in full when its attribute extends beyond the 16,000-character bound (raw or normalised) or when a cap or the budget cut windows from it, and the check is emitted with `details.controlsUnread` even when nothing matched. A control counts once, however many of its bounds it hit (its attributes, its window caps, its text read); controls cut by the prepared-controls cap, the logo-alt cap and the templates are counted too. That count is the limit: a page with more cue-bearing windows than the budget holds reports it instead of reading the rest. The page as a whole has a fixed amount of reading to spend (400,000 nodes), shared fairly: each control's allowance is what is left divided by the controls still to read (at least 4 nodes, at most 256). The most relevant controls (a sign-in attribute, then buttons and links to another host or a sign-in path) also get a longer read from a separate budget. Looking up a control's form or logo is memoised along the path. A phrase is matched as whole words with a space optional between its words, so a label split by markup (`Sign<br>in with Goo<i>gle</i> to continue`) is the phrase, while `Redesign in with Google Workspace` or `Login with GoogleMail` is not a sign-in with Google. A control that is relevant and still could not be read in full (a label of thousands of nested elements, more than 60,000 candidates, an `aria-labelledby` list or an attribute longer than what is read) is counted, and when no impersonation is found it is reported: with no impersonation found, the rule emits an `info` `brand-impersonation` check with `details.scanTruncated` and `details.controlsUnread` instead of nothing. Templates with content past the 5,000-template limit are counted separately, in `details.templatesUnread`, and named as templates in the message. A footer link to an unrelated third party is not read as a credential destination. Body text is read with a space at every element boundary as well as without, so `<h1>Welcome</h1><a>Sign in with Google</a>` is seen as sign-in copy whether or not the markup has whitespace between its elements. Body text and each link's label are read with invisible characters (a soft hyphen, zero-width spaces) removed and every run of whitespace as one space, so a newline, `&nbsp;`, a `<br>` or a zero-width space inside `Sign in with Google` does not hide it. A "Sign in with Google" or "Sign in with Microsoft" control that goes to a hosted identity broker's authorize endpoint (`https://<tenant>.auth0.com/authorize`, `https://<tenant>.okta.com/oauth2/.../v1/authorize`, `https://<tenant>.auth.<region>.amazoncognito.com/oauth2/authorize`, `https://<project>.supabase.co/auth/v1/authorize`, `https://<project>.firebaseapp.com/__/auth/handler`) is a real integration and is not reported. The exemption is the endpoint, the provider and, where the broker has tenants, the tenant: those hosts are open to anyone who registers a tenant, a tenant controls its hosted login page, and the link is written by whoever wrote the page, so neither the authorize path nor a hint in the URL proves a real integration. For Auth0, Okta and Cognito the tenant (the FIRST host label, with only the family's own shape after it: `.auth0.com` with an optional region, `.okta.com` (also `oktapreview.com`, `okta-emea.com`), `.auth.<region>.amazoncognito.com`) must be the audited site's name: exactly (`example.auth0.com`, `example.okta.com` on `example.com`), which needs no hint, or the name plus a hyphenated environment suffix from a fixed list (`prod`, `production`, `dev`, `staging`, `stage`, `test`, `qa`, `uat`, `preview`: `example-prod.okta.com`), which also needs the URL to name the provider the label does in its query (`connection=google-oauth2` or `windowslive` for Auth0, `identity_provider=Google` for Cognito, a non-empty `idp` for Okta, which names a configured identity provider by an opaque id). Any other suffix or prefix (`example-login`, `example-sso`, `examplecorp`, `example-eu`), a deeper label (`evil.example.auth0.com`), a look-alike and a name shorter than three letters are never spared (a short site name matches too much); the name is the registrable name of the page's own host or of its canonical or `og:url` host. A foreign tenant, a bare authorize URL on a tenant that is not the site's, and one naming another provider are judged like any other off-brand host. A hint is read from the first 8,192 characters of the query; one pushed past that is not found, so the link is reported (never spared). Residual: a tenant is a free name, so an attacker who registers the audited site's exact tenant name before the site does (an unused `acme.auth0.com` for `acme.com`) is spared; no check on the URL can close that, only the site owning its tenant. For Supabase (`provider=google` or `azure`) and Firebase (`providerId=google.com`) the endpoint goes straight to the provider with no tenant-controlled login page, so the named provider is the whole condition. A sign-in through a differently named tenant is reported as a single signal (an `info` check). Any other path on these hosts is judged as before, and no other brand is spared by them. A control labelled with a brand that goes to another registrable domain which is not one of these endpoints (another identity service such as WorkOS or Zitadel, or your own sign-in on a different domain) is a single signal: an `info` check, never a failure unless a second integrity signal corroborates it. Microsoft's own hosts include `login.windows.net`, `login.microsoftonline.us` and `b2clogin.com`. Known limits, tracked as public issues: a sign-in to a Supabase or Firebase project's authorize endpoint, to `b2clogin.com` or to a user-content host under `google.com` (`sites.google.com`, `docs.google.com` and similar) is spared though anyone can publish there (#1418); a cue after more than 16,000 characters of an attribute label, or in windows the page budget cut, is not read and the control is counted (#1424); a style attribute over 8,192 characters can hide a decoy and a `<base href>` on another host is not followed (#1423). Sibling subdomains count as the site's own surface, resolved through the Public Suffix List, so a link from `www.acme.com` to `app.acme.com` is spared.

The four page-level integrity rules share one detector module and each computes the full signal set for its own page. Escalation to fail requires two distinct signals from `brand-impersonation`, `obfuscated-script`, `fake-auth-overlay` and `seo-doorway`.

## How to fix it

```html
<a href="https://accounts.google.com/o/oauth2/v2/auth?client_id=...">Sign in with Google</a>
```

Point the control at the provider's own host. If you did not build the page, treat the site as compromised: remove the page, look for recently modified files and unexpected CMS entries, rotate credentials and read the server access logs.

An OAuth flow proxied through your own authentication service is not flagged, because the destination shares your registrable domain. A flow proxied through a separate vendor domain will be flagged as a single signal, which is info rather than a failure.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["integrity/brand-impersonation"]
```

### Disable all Site Integrity rules

```toml squirrel.toml
[rules]
disable = ["integrity/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["integrity/brand-impersonation"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.
