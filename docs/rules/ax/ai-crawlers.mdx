## What an AI crawler block is

"Block AI crawlers" is not one decision. The named bots serve four different purposes, each with its own robots.txt user-agent token, so a rule aimed at one never covers another. Blocking `ClaudeBot`, a training crawler, does not block `Claude-User`, a live fetch a person triggered inside an assistant.

- Training crawlers, such as `GPTBot`, `ClaudeBot`, `Google-Extended`, `Applebot-Extended`, `Meta-ExternalAgent`, `Amazonbot` and `Bytespider`, collect pages for a vendor's future model training.
- AI-search indexers, such as `OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot`, `DuckAssistBot` and `YouBot`, build the index an answer engine cites from.
- User-action fetchers, such as `ChatGPT-User`, `Claude-User`, `Perplexity-User`, `MistralAI-User` and `Meta-ExternalFetcher`, fetch a page because a person asked for it right now.
- Archive crawlers, `CCBot` and the Internet Archive's `ia_archiver` and `archive.org_bot`, feed the Common Crawl corpus and the Wayback Machine, which are the shared sources training sets are built from.

Blocking a training crawler is a policy choice about one vendor. Blocking an archive crawler is wider, because the corpus it feeds is shared: a `CCBot` block keeps future pages out of Common Crawl, which many training sets are built from. robots.txt is a request that cooperative crawlers honour, and it does not remove captures that already exist.

## What squirrel checks

The rule runs once per crawl against the parsed robots.txt and evaluates 24 known crawler tokens. For each one it resolves the groups that apply, preferring a group naming the token over `User-agent: *`, and treats the bot as blocked when those groups carry `Disallow: /` with no `Allow: /`. Token matching is case-insensitive. It emits one to four checks:

- `ai-crawler-access`: always emitted, at info status. With no robots.txt, or one that does not exist, the message is `No robots.txt — all AI crawlers are allowed by default` and nothing else runs. Otherwise the message is `N/24 known AI crawlers allowed`, followed by `; M blocked (<tokens>)` only when something is blocked, listing the tokens in the order the crawler list declares them. The blocked tokens are also listed as items showing vendor and class.
- `ai-crawlers-wildcard-blocked`: emitted when the wildcard group (`User-agent: *` with `Disallow: /`) is what blocks AI crawlers the file does not name. One row, however many crawlers: its message says that robots.txt blocks all (or N) known AI crawlers through the wildcard group, not by name, and that it is the same rule [`crawl/robots-txt`](/rules/crawl/robots-txt) reports as blocking all crawling. It has one item, `User-agent: *`, whose `meta.crawlers` lists the crawlers it blocks, so a comparison between two audits sees one finding added or resolved when the line is added or removed, not one per crawler. It warns when the wildcard also takes an AI-search indexer, a user-action fetcher or an archive crawler, as naming them would, and is info when only training crawlers are left to it. A crawler the file allows by name while the wildcard blocks everything is not listed. The row is a finding in the AX category and `crawl/robots-txt` is one in the Crawlability category: the scoring model has no way to count one cause once across rules, so it counts once in each. A finding you tracked for a crawler continues in this row while the row lists that crawler (`meta.crawlers`), and is not reported fixed; a crawler the file has since allowed by name is no longer listed, so its old finding is reported fixed. Googlebot and the other search engines blocked by the same wildcard keep their own `search-engine-access` row.
- `ai-answer-access`: emitted only when an AI-search indexer or a user-action fetcher is blocked **by its own `User-agent` group**. A crawler only the wildcard blocks is in the row above. It warns with the message `robots.txt blocks <clauses>. These are separate user-agents from the training bots: blocking ClaudeBot (training) does not block Claude-User (user-action); check the block was intended.` The clauses are `AI-search indexers (<tokens>) : lost AI citations` and `user-action fetchers (<tokens>) : breaks live requests users made inside an assistant`, joined with `; `, and a class with nothing blocked is left out.
- `archive-crawler-access`: emitted only when an archive crawler is blocked by its own `User-agent` group. It warns with the message `robots.txt blocks archive crawlers: this removes the site from the Wayback Machine and/or the Common Crawl corpus, the archives AI training sets are built from. Blocking CCBot opts you out of every model trained on Common Crawl, not just one vendor.`
- `search-engine-access`: emitted whenever a robots.txt exists. Its status is `warn` when `Googlebot` is `root-blocked` or `path-blocked` for the audited URL, and `info` otherwise. The search-engine bots `Googlebot`, `Bingbot` and `Applebot`, are evaluated against the audited URL (the URL the crawl started from) with the same longest-match `Allow` and `Disallow` evaluation the crawl rules use, so a path rule counts. `Applebot` with no group of its own follows the `Googlebot` group before `*`, as Apple documents; `Applebot-Extended` is a separate token and does not. Each bot gets one verdict: `allowed`; `root-blocked` (the site root and the audited path are both disallowed); `path-blocked` (the root is open but a rule disallows the audited path); or `allow-override` (the root is disallowed but an `Allow` rule re-permits the audited path). These bots are not part of the 24 AI tokens or the `N/24` count, and the only bot that can make the check warn is `Googlebot`: a robots.txt that blocks it for the entry URL usually means the site is not indexed, often because a staging `Disallow: /` was left in, so it is reported as a warning that counts toward the score. `allowed` and `allow-override` stay `info`, and so does a block of any other engine (`Bingbot`, `Applebot`), which is listed as an item but never warns. The per-bot verdicts, `rootBlocked`, `pathBlocked` and `explicitlyListed` are in `details.bots`, and bots that are not plainly allowed are listed as items. The AI crawler checks above still look at the site root only.

Blocking training crawlers alone produces no warning. The summary check reports it and the score is untouched, because opting out of one vendor's training is a legitimate choice. Ambiguous data harvesters such as `Diffbot` are classified as training for the same reason: that is the class whose blocking never penalises.

## How to fix it

```
User-agent: GPTBot
Disallow: /

User-agent: OAI-SearchBot
Allow: /

User-agent: ChatGPT-User
Allow: /
```

Put the groups in robots.txt at the site root. This example opts out of OpenAI's training crawl while keeping the site citable in ChatGPT search and reachable when a person asks for it.

The common false positive is a block that lives at the edge rather than in robots.txt. A WAF rule or a bot-management toggle can serve a challenge to the same user-agent that robots.txt allows, and this rule reads robots.txt only. [ax/agent-blocking](/rules/ax/agent-blocking) probes the actual responses and catches that case.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["ax/ai-crawlers"]
```

### Disable all Agent Experience rules

```toml squirrel.toml
[rules]
disable = ["ax/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["ax/ai-crawlers"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.
