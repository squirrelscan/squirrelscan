## What text-to-HTML ratio is

An agent that fetches a page pays for every byte of it in tokens, including the parts a reader never sees: inline scripts, inline styles, wrapper divs, and long utility-class strings. The text-to-HTML ratio is the share of the response that is visible text. A page at 5% is spending nineteen tokens on markup for every one on content.

The second number is absolute size. A response large enough to fill a meaningful part of a context window is a problem regardless of its ratio, because the agent has to hold all of it to find the part it wanted.

## What squirrel checks

The rule runs on every crawled page against the raw HTML and emits two checks:

- `token-weight-ratio`: warns with the message `Visible text is under 15% of the page HTML — agents pay token cost mostly for markup, scripts, and styles` when the ratio is below 0.15. The per-page number is in the item, which reads `~N% of HTML is visible text (~N est. tokens)`. Otherwise it passes with `~N% of this page's HTML is visible text, above the 15% floor`.
- `token-weight-budget`: warns with the message `Raw HTML exceeds a generous 100,000-token budget for a single page fetch — too heavy for an agent's context window` when the estimate is over 100,000 tokens, with the item reading `~N estimated tokens (N bytes)`. Otherwise it passes with `~N estimated tokens (N bytes), within budget`.

Instead of both, a single `token-weight` check is emitted as skipped with the message `Page too small (or not a real content page) to assess token weight` when the page has no parsed document or its HTML is under 1,024 bytes. The rule is also skipped on a page detected as a soft 404, whose numbers describe the error template rather than a real page.

The token estimate is the UTF-8 byte length of the HTML divided by four and rounded. It is a heuristic, not any model's tokenizer, and it is there to flag order-of-magnitude bloat rather than to bill anyone. The two warning messages carry the fixed thresholds but no per-page numbers: the report groups checks by message, and differing digits would collapse the shared headline into a literal `N`. The per-page figures live in the item instead.

## How to fix it

Move inline scripts and styles into external files, which also lets them cache:

```html
<link rel="stylesheet" href="/app.css" />
<script src="/app.js" defer></script>
```

Then look at the markup around the content itself. Deeply nested wrapper divs and hundred-character class strings on every paragraph are the other half of the ratio. Serving a Markdown representation, covered by [ax/markdown-response](/rules/ax/markdown-response), removes the markup from the response entirely.

The common false positive is a page that is mostly a data table or a media gallery, where the markup-to-text ratio is inherent to the content. The finding is still true about token cost, but there may be nothing to cut.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["ax/token-weight"]
```

### Disable all Agent Experience rules

```toml squirrel.toml
[rules]
disable = ["ax/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["ax/token-weight"]
disable = ["*"]
```
