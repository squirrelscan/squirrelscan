## What API discovery is

An agent that wants to call an API needs three things it can fetch rather than read: a description of the endpoints, the location of the authorization server, and a way to obtain client credentials.

- An OpenAPI document describes the endpoints. `/.well-known/api-catalog`, defined by RFC 9727, is a link set pointing at one or more of them.
- RFC 8414 defines `/.well-known/oauth-authorization-server`, the authorization server metadata. RFC 9728 defines `/.well-known/oauth-protected-resource`, which points a client from a resource back at the server that guards it.
- RFC 8414's metadata can carry a `registration_endpoint`, which points at the Dynamic Client Registration endpoint defined by RFC 7591, so a client can register itself. Client ID Metadata Documents are the newer alternative, signalled by `client_id_metadata_document_supported`.

Without the last one, an agent can find the authorization server and then stop, because a human still has to create a client by hand.

## What squirrel checks

The rule runs once per crawl against probed well-known paths. A probe counts as a hit when it returned 200, the body parsed as JSON, and it did not sniff as HTML. It emits one or two checks:

- `api-discovery`: reports at info status with the message `well-known probe data not available` when the probes did not run. Otherwise it reports at info status with `No api-catalog or OpenAPI specification found` and the value `absent`, or with `API discovery document(s) found: <list>`, where the list holds `api-catalog (<path>)` and `OpenAPI spec (<path>)` for whichever was found, joined with `, `. The OpenAPI paths probed are `/openapi.json`, `/swagger.json` and `/api/openapi.json`, and a hit at one of them counts only when the document names its own spec version, meaning a top-level `openapi` or `swagger` key or that key visible in the excerpt.
- `api-discovery-oauth`: reports at info status with `No OAuth discovery documents found` when neither OAuth path is a hit. Otherwise the message opens `OAuth discovery found: <found>`, where `<found>` lists `authorization server metadata (RFC 8414)` and `protected-resource metadata (RFC 9728)` for whichever was present, joined with `, `. With the protected-resource document alone the message stops there. With the authorization server metadata and a self-onboarding mechanism it continues `; agent self-onboarding available via <mechanisms>`, naming `Dynamic Client Registration (RFC 7591)`, `Client ID Metadata Documents (CIMD)` or both joined with ` and `. With the metadata and neither mechanism it continues `, but no registration_endpoint (DCR) or client_id_metadata_document_supported (CIMD) — an agent can find the authorization server but a human still has to register a client by hand`.

Every result here is info. Not every site has an API, so absence is never a defect and the rule cannot move the score.

## How to fix it

Publish the spec at a conventional path and, if you already have a `.well-known` directory, point at it:

```json
{
  "linkset": [{
    "anchor": "https://example.com",
    "service-desc": [{ "href": "https://example.com/openapi.json", "type": "application/json" }]
  }]
}
```

That document goes at `/.well-known/api-catalog`. If the API uses OAuth, add `registration_endpoint` to your authorization server metadata so an agent can register a client without a support ticket.

The common false positive is an API documented under a path this rule does not probe, such as `/v2/openapi.yaml`. The check reports absence because it looks at three fixed paths. Adding an `api-catalog` that points at the real location resolves it and is the point of the RFC.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["ax/api-discovery"]
```

### Disable all Agent Experience rules

```toml squirrel.toml
[rules]
disable = ["ax/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["ax/api-discovery"]
disable = ["*"]
```
