## What a server error is

A 5xx status means the server failed to answer a request it should have been able to serve: an unhandled exception, an exhausted database or upstream, a bad deploy. Visitors see an error page, and search engines treat a persistent 5xx as a page that is gone and eventually drop it from the index.

## What squirrel checks

The rule is site-wide and reads every page the crawl fetched. Each failing page is its own finding, stored against that page's URL, so an audit comparison shows "this page answers 503" and a page that recovers resolves on its own while other pages still fail.

- `server-errors` fails once per page that answered 5xx. Message: `https://example.com/boom answers with a 500 server error`. The item is labelled with the URL and its status code. Severity error, weight 8.
- Every other fetched page passes, so a page that answered 5xx last audit and 200 this audit resolves. A page the crawl did not fetch this audit is not judged, and its earlier finding stays open (not crawled).
- Skipped when no pages were crawled. Message: `No pages crawled`.
- A site-level pass when no crawled page answered 5xx and the crawl reached every page it knew of. Message: `No crawled page answered with a 5xx status`.
- Not checked when the crawl stopped at its page cap or with URLs still queued: a page it never fetched may still be failing, so the audit does not call the site clean, and an earlier finding on a page not fetched stays open. Message: `Not checked: the crawl stopped at its 500-page cap, so a page not crawled may still answer 5xx`.
- Not checked when the crawl gave up on some pages (a timeout, a refused connection, a body it could not read): one of those may still be failing, so an earlier finding stays open. Message: `Not checked: the crawl could not fetch 3 page(s), and any of them may still answer 5xx`.

A redirecting URL is a redirect, not a page, so it is not counted here.

### Retries and intermittent errors

squirrel retries a failing fetch before it gives up. A page that errors once and then answers is stored as the healthy page it became and is not reported, and the rule does not label anything intermittent. Only a page that is still 5xx after those retries is a finding. A throttled response (429, or a 503 that carries `Retry-After`) is the host asking squirrel to slow down, not a broken page, and is never reported here.

## How to fix it

Read the server or application logs for the failing URL, fix the fault behind it, then re-run the audit to confirm the page returns 200. A page that is gone on purpose should answer 404 or 410, not 500.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["crawl/server-errors"]
```

### Disable all Crawlability rules

```toml squirrel.toml
[rules]
disable = ["crawl/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["crawl/server-errors"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.

## Check names by outcome

Each check name this rule can emit, by what it means to a tool comparing two audits. A **problem** check is a finding. A **clean** check says the rule ran over what it covers and found nothing; it clears the problem checks listed beside it, so a finding is fixed when the rule ran over the same scope and a clean check took its place. A **not checked** check says the rule did not evaluate, and never clears a finding.
