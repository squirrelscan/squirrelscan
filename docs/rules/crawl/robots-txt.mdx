## What robots.txt is

`robots.txt` is a plain text file at the root of a host that tells automated clients which paths they may request. It is defined by RFC 9309 and consists of `User-agent` groups, each with `Allow` and `Disallow` rules, plus optional `Sitemap` lines that can appear anywhere in the file.

It controls crawling, not indexing. A URL blocked in robots.txt can still be indexed from links elsewhere, because the crawler never fetches it and so never sees a `noindex`. It is also advisory: it constrains well-behaved crawlers and does nothing about anything else.

## What squirrel checks

The rule is site-wide and reads the robots.txt the crawl fetched, as RFC 9309 and Google's parser group it: consecutive `User-agent` lines share the rules that follow them, only an `Allow` or `Disallow` line ends that run of `User-agent` lines, and a `Sitemap`, `Crawl-delay` or unknown line between them does not split the group. Lines may end in CR, LF or CRLF. It emits these checks:

- `robots-txt-exists` reports info when no robots.txt data is available at all. Message: `robots.txt data not available`.
- `robots-txt-exists` reports info when the site refused the request (a 401, 403 or 429, or a bot challenge). Message: `robots.txt could not be checked`, with `The site refused the request (HTTP 403 (Cloudflare)), so this is unknown, not missing` as the value.
- `robots-txt-exists` reports info when the probe recorded an error, so absence was never established. Message: `robots.txt could not be checked`, with `The request did not complete, so this is unknown, not missing` as the value.
- `robots-txt-exists` fails when the file is confirmed absent. Message: `No robots.txt found`, with `Search engines will crawl all accessible pages` as the value. Severity error, weight 8.
- `robots-txt-exists` passes when the file exists. Message: `robots.txt exists`, with the file URL.
- `robots-txt-syntax` warns when the parser recorded errors. Message: `2 syntax error(s) in robots.txt`, listing each. It passes otherwise with `robots.txt syntax is valid`.
- `robots-txt-disallow` fails when the `*` group blocks the root (`Disallow: /`, or a pattern the crawl reads the same way such as `Disallow: /*`), has no `Allow` rule, and no major search crawler is re-allowed by name: every crawler that matters is blocked. A group of its own that lets in only an AI crawler or a niche bot (`User-agent: GPTBot` with `Allow: /`) leaves Google and Bing out, so the check still fails, and `details.allowedByName` lists those bots. Message: `robots.txt blocks all crawling`, with `Disallow: / with no Allow rules`. It reports info when there is a `Disallow: /` alongside `Allow` exceptions, and passes otherwise with `robots.txt does not block all crawling`.
- `robots-txt-disallow-wildcard` warns when the `*` group blocks the root with no `Allow` rule, but a named group lets a major search crawler in: Googlebot, Bingbot, DuckDuckBot, YandexBot or Applebot, with `Allow: /`, or no rule that blocks the site. Message: `robots.txt blocks every crawler without a group of its own (User-agent: * with Disallow: /); still allowed by name: Googlebot, Bingbot`; `details.allowed` lists those crawlers and `details.otherAllowed` any other named crawler let in. `robots-txt-disallow` then passes (`robots.txt does not block every crawler`). Whether a crawler is let in is decided the way the crawl matches rules (longest match, `Allow` wins a tie), asked about a deep path no rule names as well as the root, so a named group whose own `Disallow: /*` blocks the site is not a re-allow, and neither is one with `Disallow: /` that only re-permits the homepage (`Allow: /$`). The same two questions decide "blocks all crawling": `Disallow: /*` blocks the whole site, while a homepage-only `Disallow: /$` does not.
- **Tracking keys.** The two checks are peers: the rule declares them as superseding each other, so a site that adds or removes a named allow moves its finding from one to the other, and a tool tracking by rule and check sees one change, not a fix and a new finding. Removing the wildcard block fixes both.
- `robots-txt-crawl-delay` reports info for a `Crawl-delay` in a `*`, `bingbot`, `msnbot`, `yandex` or `googlebot` group, naming the delay and group. Google ignores this non-standard directive, while Bing and Yandex obey applicable groups. A delay of 10 seconds or more in `*` or `bingbot` warns and estimates Bing's maximum daily URL rate; `Crawl-delay: 10` is about 8,640 URLs per day. Delays limited to other bots are not reported.
- `robots-txt-sitemap` passes when at least one `Sitemap` line is present, listing the URLs. Otherwise it reports info with `No sitemap referenced in robots.txt`.
- `robots-txt-size` warns when the file exceeds 500 KB. Message: `robots.txt is very large`, with the size and Google's 500 KB limit as the value.

## How to fix it

```
User-agent: *
Allow: /

Sitemap: https://example.com/sitemap.xml
```

Serve it from the host root with a `text/plain` content type. Keep `Disallow` for paths that genuinely waste crawl budget, such as faceted search and session URLs, and use `noindex` rather than `Disallow` when the goal is keeping a page out of results.

Remove stale `Crawl-delay` directives unless a crawler-specific throttle is intentional. Google ignores them; Bing and Yandex slow discovery to the requested interval when the directive applies. Prefer server-side rate limiting for abusive non-search bots rather than a wildcard delay that also affects search crawlers.

Do not block the CSS, JavaScript or image paths a renderer needs. A page rendered without its stylesheet can be judged as broken or as having hidden text.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["crawl/robots-txt"]
```

### Disable all Crawlability rules

```toml squirrel.toml
[rules]
disable = ["crawl/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["crawl/robots-txt"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.
