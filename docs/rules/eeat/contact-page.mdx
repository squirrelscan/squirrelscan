## What a contact page is for

A contact page is the answer to how do I reach these people. It carries at minimum a way to get in touch, and usually several: an email address, a phone number, a form, a postal address.

More than one method matters because they fail differently. A form is easy to build and impossible to verify from outside; a `mailto:` address and a `tel:` number are things a reader can check and use immediately.

## What squirrel checks

The rule is site-wide. It finds the contact page by a URL path at one of the configured `paths` (see Options), a URL path matching one of the multilingual contact patterns, or by a page whose structured data declares the `ContactPage` type. It emits up to two checks:

- Skipped when no pages were crawled. Message: `No pages available for analysis`.
- `contact-page` passes when a crawled page is the contact page. Message: `Contact page exists`, with the URL as the value.
- `contact-page` passes when no page matches but a crawled page has a Contact section: an element whose `id` matches a contact slug (`contact`, `contact-us`, a localised one) and a same-page link to it (`href="#contact"`). Message: `Contact section found on the homepage (#contact)`. The section, or the page holding it, needs a `mailto:` or `tel:` link or a form; without one the check is info (`Contact section exists on the homepage (#contact) but has no email, phone or form`). A real contact page always takes precedence, and the `contact-methods` check runs only for a contact page.
- `contact-page` reports info when no crawled page is the contact page but a crawled page links to one the crawl did not fetch. Message: `Contact page linked but not crawled`, with the link target as the value and the linking page in the details. No further checks run, because the page was never read.
- `contact-page` warns instead when the internal link probe requested that uncrawled target and got a 4xx or 5xx. Message: `Contact page link returns N`, where `N` is the status. A 401, a 403 or a rate limit is not read as broken and stays info.
- `contact-page` warns when there is neither a crawled contact page nor a link to one. Message: `No Contact page found`, with `Create /contact page` as the value. No further checks run. Severity warning, weight 5.
- `contact-methods` passes when the page carries both a `mailto:` and a `tel:` link. Message: `Contact page has multiple contact methods`, listing them.
- `contact-methods` reports info when it carries exactly one. Message: `Contact page has limited contact methods`, with `Consider adding email, phone, and address` as the value.

A crawl that excludes the contact page's path, or reaches its page limit first, never fetches it. A link to the same host whose href matches one of the contact patterns is evidence the page exists, not proof that it works, so the rule says it is linked but not crawled instead of advising you to create one. Anchor text alone does not count, and no extra requests are made: the only status the rule can report is one the internal link probe already recorded. To have the page and its contact methods checked, let the crawl fetch it.

Only `mailto:` and `tel:` links count as methods. A contact form is not detected on a contact page, so a page with a form and no direct address emits no methods check at all. In an in-page Contact section a form does count, together with a `mailto:` or `tel:` link anywhere on the page holding the section. The `ContactPoint` schema type is deliberately not used as a fallback, because it is usually an Organization property present on every page rather than a marker of this page.

## How to fix it

On a one-page site you do not need a separate page. Give the section an id (`<section id="contact">`), link it from the navigation (`<a href="#contact">`), and include an email link, a phone link or a form in it.

```html
<a href="mailto:hello@example.com">hello@example.com</a>
<a href="tel:+61292223333">(02) 9222 3333</a>
```

Publish a real address and a real number as links, not as images or as text a reader has to retype. Keep the contact link in the footer so it is reachable from anywhere.

A form is fine as an addition. It is weak on its own, because there is no way for a reader to tell whether anyone reads it.

## Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `paths` | string[] | `[]` | Site-specific paths of the page, checked in addition to the built-in slugs. Patterns are matched like [`excludePatterns`](/configuration/rule-options#url-patterns), against the URL's path only (never the host, query string or fragment): a substring of the path, `/exact-segment/`, or `regex:`. |

### Configuration example

```toml squirrel.toml
[rule_options."eeat/contact-page"]
paths = ["/pages/manufaktur"]
```

A crawled page at a configured path counts as the page, with no structured data needed, and a configured path that pages link to but the crawl did not fetch is reported as linked but not crawled, as for a built-in slug. A `paths` value that is not an array of strings, or a `regex:` entry that does not compile, is reported by `squirrel config validate`.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["eeat/contact-page"]
```

### Disable all E-E-A-T rules

```toml squirrel.toml
[rules]
disable = ["eeat/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["eeat/contact-page"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.
