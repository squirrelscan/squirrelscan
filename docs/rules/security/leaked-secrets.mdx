description: "An API key shipped in HTML or a bundle can be read by anyone who views source. squirrel scans every page and script against more than 90 key patterns."

## What a leaked secret is

A leaked secret is a credential that reaches the browser: an API key in a bundle, a database connection string in server-rendered HTML, a token in an inline script. Anything the browser can load, anyone can read, and automated scrapers do read it. A leaked key is used within hours of being published.

Not every key in client-side code is a leak. Stripe publishable keys, Firebase and Google browser keys, OAuth client IDs, Supabase anon keys and Sentry DSNs are designed to ship publicly and are safe as long as their server-side restrictions are configured. The dangerous ones are secret keys, service-role keys, personal access tokens and anything with a database password in it.

## What squirrel checks

The rule scans the HTML of every crawled page, every inline `<script>`, and the content of external JavaScript files the crawl fetched. It matches against more than 90 patterns covering AI providers, cloud platforms, payment processors, databases, source hosts, messaging services and generic assignments such as `api_key = "..."`. Most carry a literal marker of their own, a prefix such as `sk-`, `ghp_` or `AKIA`, a URL host or a PEM header, and run on all content. The rest are bare runs of hex or alphanumeric characters that only count next to the provider's name, such as `datadog` or `cohere`, and only when assigned to a key that is not a digest or hash. Findings are deduplicated by value across the whole site, and each reported value is masked. It emits these checks:

- `leaked-secrets-critical` fails when a server-only secret sits in a browser-served script. Message: `{count} critical server-only secret(s) shipped to every visitor in browser-served scripts (rotate now)`. Items have the same shape as the high check. See [Server-only secrets in a script are critical](#server-only-secrets-in-a-script-are-critical).
- `leaked-secrets-high` fails when a high-confidence pattern matched. Message: `{count} high-confidence leaked secret(s) detected`. Each item reads as the pattern name plus the masked value, labelled `Found in {location} ({url})`. Severity error.
- `leaked-secrets-medium` warns on medium-confidence matches, which are mostly the generic assignment patterns. Message: `{count} potential secret(s) detected (verify manually)`.
- `leaked-secrets-public` reports info for keys that are public by design. Message: `{count} public client-side key(s) found (public by design — verify usage restrictions are configured)`. These never count as leaks.
- `leaked-secrets-info` reports info for tokens whose own structure says they are not a credential worth stealing: a JWT whose `exp` claim is in the past, or a first-party session token that expires within 30 days (the JWT row in [Token structure raises or lowers confidence](#token-structure-raises-or-lowers-confidence) has the exact conditions). Message: `{count} expired, session-scoped or signature-bound token(s) found (informational, not counted as a leak)`. These never count as leaks either.
- `leaked-secrets-unscanned` reports info when the scan of one or more pages ran past the rule's time budget. Message: `{count} page(s) were not scanned for secrets because the scan exceeded its time budget, so no finding on them is not a clean result`. It lists up to 20 of those pages.
- `leaked-secrets` passes when no critical, high- or medium-confidence match remains and every page was scanned. Message: `No leaked API keys or secrets detected`.

The location on each item is `html`, `inline-script` or `external-script`, with the suffix ` (base64)` when the value was only found inside a base64 blob that the page decodes at runtime. Each item's `meta` has the matched value's `length` and its zero-based `offset`, both measured in JavaScript string indices (UTF-16 code units). For `html`, the offset indexes the DOM serialization squirrel scans, which can differ from the fetched response after parsing normalizes the markup. For `external-script`, it indexes the fetched script body. For `inline-script`, it indexes that element's script text and `scriptIndex` gives the element's zero-based position among all `<script>` elements on the page, including external scripts. For a value decoded from base64, `offset` points to the first character of the encoded blob in that source. Findings are deduplicated by value, so when the same value occurs more than once, the reported location metadata describes the occurrence squirrel kept. Masking keeps the first six and last four characters when the value is longer than twelve, and the first four otherwise, so the report identifies the key without republishing it. Weight is 10, the highest of any rule in the Security category.

### Server-only secrets in a script are critical

Some secrets only ever belong on a server. When one of them is read from a browser-served script, an external JavaScript file or an inline `<script>` (including a base64 blob decoded from one), every visitor already has it. squirrel reports that hit under `leaked-secrets-critical` instead of the high or medium check it would otherwise land in. It is the same finding with a higher severity, never a second one, and it reads "shipped to every visitor" in the check message.

The server-only classes are database connection strings (PostgreSQL, MySQL, MongoDB, Redis), Supabase service-role keys, secret keys and personal access tokens, Shopify Admin API tokens, Stripe restricted keys, Google OAuth client secrets, Stripe and Paystack `sk_live_` keys, Clerk secret keys, AWS secret access keys, Azure storage keys and DigitalOcean tokens. The same class found only in page HTML keeps its current severity, and publishable keys (Stripe `pk_live_`, the Supabase anon and publishable keys) are never escalated. Neither is a DigitalOcean Spaces access key id, which is the public half of the key pair, nor a value a tutorial prints: a value containing `EXAMPLE` in capitals, which is how AWS's documented example credentials end, an Azure connection string whose `AccountKey` is not a real 88-character key (such as `<account-key>`), a connection string that names a placeholder host or database, and a database URL whose every host is `localhost`, a `127.x.x.x` address or `[::1]`. Those still report under their own check. This matters for a docs site whose framework inlines the page content into `<script>` payloads, as Next.js does, where every code sample on the page is also in a script. A value inlined into a bundle under a public-variable prefix such as `NEXT_PUBLIC_` is reported by the pattern that matches its value, not by its name, so it escalates only when its value is one of the classes above.

### Encoded content is decoded before scanning

A key does not have to be spelled out in the bytes the crawler receives. Before the patterns run, the rule decodes four encodings a page uses that a browser undoes anyway:

- HTML character references in the serialized page, so a JSON object stored in an attribute as `data-state="{&quot;apiKey&quot;:&quot;...&quot;}"` is read as the JSON it is. Such a finding reports at location `html`.
- `\uXXXX`, `\u{X}` and `\xXX` escapes in script text, so a string literal a minifier or an obfuscation pass wrote as escapes is read as the characters the engine sees. A `\\u0041` (an escaped backslash followed by `u`) is left alone.
- Percent-encoding, so a settings object embedded as `data-settings="%7B%22key%22%3A%22pk_live_...%22%7D"` or passed to `decodeURIComponent()` in a script is read as the JSON it is. A run has to carry at least three `%XX` escapes and decode to text; a `%` not followed by two hex digits is never decoded. Decoded in place, so the finding keeps the plain location.
- Standalone base64 blobs of 64 or more characters that decode to text, such as a config object assigned to a global or stored in a data attribute. The decoded text is scanned as content of its own, two levels deep, and anything found reports with the ` (base64)` location suffix. The payload of a `data:` URI and the value of an `integrity` hash are never decoded, and a blob that decodes to binary is skipped.

### Token structure raises or lowers confidence

Several formats carry enough structure to confirm or downgrade a match without asking anyone. The rule never contacts a provider to verify a credential it found on someone else's site. What it decodes rides along on the item as `meta` fields in the JSON, LLM and XML report outputs and in the MCP `get_report` result:

| Format | What is decoded | Effect on the finding |
|---|---|---|
| AWS access key id | The account id encoded in the id (`accountId`, `prefix`) | An id whose suffix does not decode to a 12-digit account id is medium, not high |
| GitHub classic tokens (`ghp_`, `gho_`, `ghu_`, `ghr_`) | The CRC32 checksum in the last six characters (`checksum`) | A wrong checksum drops the finding; a right one stays high |
| JWTs, any algorithm (`JSON Web Token` pattern) | Header and payload claims (`issuer`, `role`, `projectRef`, `expiresAt`, `expired`) | Supabase `service_role` is high as `Supabase Service Role JWT`; Supabase `role: anon` is public as `Supabase Anon Key`; an expired `exp` moves the finding to `leaked-secrets-info`; a token issued by a `*.myshopify.com` domain is public as `Shopify Storefront JWT`; a session token that stands alone (an `exp` within 30 days of `iat` or of now, no admin scope, no issuer naming Auth0, Clerk, Firebase, Cognito, Okta or Supabase, and not inside an `Authorization: Bearer` literal or under a key such as `apiKey` or `secret`) is reported as `Session Token (JWT)` in `leaked-secrets-info` with `kind: session`, whether or not it names a subject; any other token from another issuer is medium at most, reported as `JSON Web Token`, and never labelled Supabase; an `admin` scope is high; jwt.io's default sample token (`sub` `1234567890` with `name` `John Doe` or `iat` `1516239022`, the payload every JWT decoder page pre-fills) is dropped when its payload is exactly the published one (`sub` 1234567890, `name` John Doe, `iat` 1516239022, and `admin: true` in the editor's version) and its signature verifies under a secret the decoder pages publish (`your-256-bit-secret`, `secret`); the same claims signed with any other secret, or the sample with any other claim or value (an `iss`, an `exp`, a `scope`), are read like any other token. Which service issued the token comes from the decoded `iss`, never from the header |
| Algolia secured API keys | The restriction parameters in the key (`keyType`, `restrictIndices`, `validUntil`, `filters`, ...) | A key with restrictions is public; one with none is medium; a base64 string near the word `algolia` that is not a secured key is dropped. A 32-hex key near the keyword stays medium with `keyType: admin-or-search-shaped` |
| Stripe keys | `kind` (secret or publishable) and `mode` (live or test) | Informational |
| Slack tokens | `kind` and the numeric workspace id segments | A token without the numeric ids is medium |
| Sentry DSNs | `org` and `projectId` from the ingest host | Informational |

### Vendor identifiers in script URLs are not reported

Some tag vendors put a public project identifier in the query string of the script their install snippet loads. It ships to every visitor by design, so a value in exactly that parameter is not reported at any level, and does not appear under `leaked-secrets-public` either. The match has to be the whole parameter value, on the exact host and path below:

| Vendor | Host | Path | Parameter |
|---|---|---|---|
| Mida | `cdn.mida.so`, `cdn-eu.mida.so` | `/js/optimize.js` | `key` |
| Klaviyo | `static.klaviyo.com` | `/onsite/js/klaviyo.js` | `company_id` |
| Google reCAPTCHA | `www.google.com`, `www.recaptcha.net` | `/recaptcha/api.js`, `/recaptcha/enterprise.js` | `render` |

This applies to the URL of a `src` or `href` in a page or script, and only to that value. The same parameter on any other host, a lookalike host (`cdn.mida.so.example.net`, a host with a port or userinfo), another parameter on the vendor's URL, and the same value anywhere else on the page are all still scanned as usual.

To extend the list, add a row to `PUBLIC_URL_IDENTIFIERS` in `packages/rules/src/security/leaked-secrets.ts` with the exact hosts, paths and parameters, and add the vendor to the table-driven tests in `packages/rules/tests/leaked-secrets.test.ts`. Add a vendor only when its own documentation says the identifier is public and shows it in a URL.

### Labels, templates and documentation placeholders are not values

A generic assignment such as `password: "..."` names a credential, but the value under it is not always one. These values are not reported:

- A storage or configuration key repeated as its value with different case or separators, such as `DROPBOX_ACCESS_TOKEN: "dropbox-access-token"`.
- A label in a compiled JSX string that ends in the credential word, such as `children:"Password:"`. The quote that closes the label is not read as the start of a value, so the match no longer spans into the code that follows. A real assignment after the label is still read.
- A translated password label, such as `Passwort`, `Geheimnis`, `Contraseña` or `Mot-de-passe`. A single word with an accented letter and no digits or symbols counts as a label.
- A template or JSX expression in place of the value, such as `{form.password}`, `{{ user.password }}` or `<%= config.secret %>`.

A connection string whose password is a documentation placeholder is not reported. Placeholders include `password`, `<password>`, `${DB_PASSWORD}`, `your_password` and a mask of `*`, `•` or `.` characters:

```text
postgresql://username:password@host:5432/dbname # pragma: allowlist secret
```

A real-looking password in a connection string whose host or database is itself a placeholder (`@host:5432/dbname`) is kept for review at medium. Its `meta` carries `placeholder: host` or `placeholder: database`.

### Samples, documentation examples and payloads are not credentials

A value is not reported when it is something a page prints rather than something a deploy shipped. Each rule below is narrow on purpose, and a real credential in the same place still reports.

- **PEM private keys need a body.** A `-----BEGIN ... PRIVATE KEY-----` header counts only when 32 or more base64 characters follow it: in one run (a whole key on one line, or 64- and 70-character lines), or added up over narrower lines (a key wrapped at 16, 20, 30 or 31 characters is a key: chunks of 16 or more characters count, several in a row must mix upper case, lower case and digits, and a word or `...` ends them). A body wrapped at fewer than 16 characters per line is NOT matched, and neither is a body whose chunks are shorter than 32 characters in all. Nothing may sit between the header and the body but line breaks in whatever form the page writes them (`\n`, `\u000a`, `%0A`, `&#10;`, any HTML tag (`<br>`, `<p>`, `<td>`, a highlighter's `<span class="line" ...>`), quotes, commas, `+`, brackets, `.concat(` and `.join(` between string literals, spaces) and armor headers such as `Proc-Type:`. At most 400 characters of that filler are allowed. Prose, code or another `-----` marker in between means the header was prose: UI help text that names the header, a validator's regex and a snippet whose body is elided (`MIIE...`) report nothing.
- **Connection strings.** A password a person typed into an example, on a host nobody can reach, is not reported. The password is a documentation word, written out whole or as whole words together: `password`, `secret`, `example`, `test` and a few more, with digits for letters, a trailing number or a separator (`s3cret`, `password123`, `examplepassword`). A password that merely contains one (`CompassRoseAtlas`) is a password. A password made only of stems (`adminroot`) on those hosts is treated as the example it almost always is. The host is `localhost`, a loopback address, or under `.localhost`, `.test`, `.example` or `.invalid`, with no `host=` or `hostaddr=` query parameter pointing elsewhere. `.internal` and `.local` are real private networks and are not on the list. A random password on the same host still reports. A password that is itself a template placeholder (`${pass}`, `{{ pass }}`, `{password}`, `%s`, `%(pw)s`) is a driver's own connection builder and is not reported; a hard-coded password next to a templated host or user, or one that contains `%s` or `{abc}`, is.
- **Stripe's published sample key.** The secret key printed in Stripe's API reference is public and unusable. It is not reported under `sk_test_`, `sk_live_`, `rk_test_` or `rk_live_`. Only the exact documented values are suppressed; any other key of the same length reports.
- **Twitter bearer tokens.** A real token opens with 21 or 22 `A`, then runs through URL-encoded segments (`%2B`, `%2F`, `%3D`) for about 110 to 120 characters. Only the token's own `%2B`, `%2F` and `%3D` escapes are kept as written (decoding them would cut it at its first `+`, `/` or `=`), so the encoded token reports in an assignment, a bare string, a URL parameter, an attribute and a header, including right after an encoded `=`, `"`, `'`, `&` or `:` (`key%3D<token>`; not after the `%2C` of a `data:` URL, a payload); everything else in the same URL-encoded run, a `%26aws_secret_access_key%3D...` after the token included, is decoded and scanned as usual, and an encoded document that merely contains a base64 blob is still decoded. A run of `A` is also what zero bytes look like in base64, so the shape is not a token inside a `data:` URI, next to `/` or `+` (a deliberate trade-off: a real token that is bare-adjacent to `/` or `+` with no `Bearer`, `Authorization`, `token` or `key` before it, including a URL-encoded `Bearer+`, is not matched), when it is mostly `A`, when it has no real characters after the run, or when it is longer than 200 characters.
- **Hashed asset names.** A Neon, legacy OpenAI `sk-`, Mailgun `key-` or Resend `re_` token followed by an image, font or media extension (`png`, `jpg`, `gif`, `webp`, `avif`, `svg`, `ico`, `bmp`, `woff`, `woff2`, `ttf`, `otf`, `eot`, `mp3`, `mp4`, `webm`) is a file name, when it sits after a `/`, a quote, `(`, `=` or a comma (`neon_<hash>.png`, `sk-<hash>.svg`, `key-<hash>.webp`). A `.map` or `.css` after one, and the same token in running text, still report. Distinctive tokens (`sk-ant-`, `AIza`, `SG.`, GitHub tokens, Stripe keys) followed by an extension still report.
- **IBANs.** A 28-character `DO` string whose check digits satisfy mod 97 is a Dominican Republic IBAN, not a DigitalOcean Spaces key.
- **Strings that only look like a JWT.** A `JSON Web Token` match is dropped only when it is proven not to be one: its header or its payload is within the 8,192-character read bound and is not a JSON object (an `eyJ`-prefixed run whose part is not base64 of JSON, truncated JSON, JSON with trailing bytes, an array, a string, a number or `null`). Undecided matches are reported: a part longer than 8,192 characters, JSON nested too deeply to parse, an empty payload, and a header with no string `alg` (or a non-string one) over a payload that decodes, which keeps its own classification (a `service_role` payload is still a high-severity finding). `alg: none`, expired tokens and any claims report.
- **Placeholder words.** A value that is `example` followed by a credential noun and at most a short number (`example-password`, `example_secret`, `example-api-key`, `example-password1`) is a placeholder. `Example1234`, `ExampleKey` and a password that merely starts with `Example` are not. `changeme` is deliberately not on it: it is as often a real default credential as a placeholder.

### Keys that share a prefix

`sk_live_` and `sk_test_` are Stripe's prefixes and other vendors reuse them. The format of what follows tells them apart. Paystack's secret keys are the prefix plus exactly 40 lowercase hex characters and report as `Paystack Live Secret Key` or `Paystack Test Secret Key` at high (live keys count as server-only secrets, so they are critical in a browser-served script). Stripe's own tail is 24 alphanumerics in the old format and about a hundred in the current one. A tail that is only hex and 32 or more characters long, other than Paystack's 40, is not Stripe's: it reports as `Secret Key (sk_live_ prefix, provider unknown)`, at medium inside a `data-*-key` or `data-*-token` attribute whose name does not say `secret`, `private`, `server`, `admin` or `master` (where chat and support widgets read their deployment key, with `meta.hint: embeddable widget key (data-*-key attribute)`) and at high anywhere else. `meta` carries `prefix`, `provider: unknown` and `resembles`.

### Public by design: platform tokens and beacons

Some tokens are put on a page for the browser to read. They report under `leaked-secrets-public` (or `leaked-secrets-info` where noted), never as a leak, and only on positive evidence in the token or right beside it. A name, a path or an issuer host on its own is not evidence, and anything the evidence does not cover keeps reporting.

| What | Evidence | Reported as |
|---|---|---|
| Shopify wallet token | A signed JWT whose payload has `merchantId` and `merchantOrigin` and no other claim beyond the registered ones and `expiresAt` | `Shopify Wallet Token` |
| Shopify Shop sessions token | A signed JWT with `client_id` and `unique_id` (and optionally `client_account_id`), with a `https://shopifyinc.com/sessions` URL in the text beside it. The claim names alone are what any custom app's own session token could be made of. | `Shopify Shop Session Token` |
| Netlify web vitals token | A signed JWT with `iss: netlify` and only the web-vitals ids (`site_id`, `account_id`, `deploy_id`), in a `data-netlify-cwv-token` attribute | `Netlify Web Vitals Token` |
| AWS key id in a presigned URL | An `AKIA` or `ASIA` id right after `X-Amz-Credential=`, with both `X-Amz-Signature=` and `X-Amz-Expires=` in the URL | `leaked-secrets-info`, with `presigned: true` |
| Shopify platform bundle | An `apiKey` assignment (only that one) in a script from `cdn.shopify.com/shopifycloud/` or from `/cdn/shopifycloud/` on a `*.myshopify.com` host (matched on the parsed hostname). A custom-domain shop's copy is not recognised and reports like any other script. Secrets, tokens, AWS keys and provider keys in the same bundle still report. | Not reported |
| Shopify App Store host | Any `apiKey`, `api_key`, `api-key` or `data-api-key` assignment on an `apps.shopify.com` page, in markup or in a script: a first-party host rule (it is Shopify's own site, and its listing pages carry the listed apps' public keys). Other credentials on the same page still report | Not reported |

An unsigned token (`alg: none` or no `alg`), a token with any role, admin scope or other claim, and a token with the right claims in the wrong place all report as ordinary JWTs. A consent-management or API token from a vendor's host (OneTrust, Cookiebot, Transcend, Didomi) reports as an ordinary JWT: an issuer host does not say whether a token is a read-only beacon or an API credential.

A key whose name says `search` (`search_api_key`, `ALGOLIA_SEARCH_API_KEY`) reports at medium as before, with a `meta.hint` that says the name suggests a search-only key and that an admin key stored under the same name reads the same. A search-only key is meant for browsers and an admin key is not, and nothing offline tells them apart, so the name earns a hint, not a downgrade. The same goes for a Typesense client config.

A real secret on a Shopify store still reports: a provider token (`sk_live_`) or a generic assignment in a theme asset under `/cdn/shop/` is not covered by any row above.

### Named provider formats

Formats with a distinctive prefix have their own pattern, so the report names the provider and the remediation is the right one. A tail that is too short, in the wrong alphabet or missing (a docs sentence that names `sk-or-v1-`) does not match.

| Provider | Format | Reported as | Tier |
|---|---|---|---|
| OpenRouter | `sk-or-v1-` and 64 hex characters | `OpenRouter API Key` | high |
| Cerebras | `csk-` and 40 or more lowercase letters and digits | `Cerebras API Key` | high |
| NVIDIA | `nvapi-` and 60 or more letters, digits, `_` or `-` | `NVIDIA API Key` | high |
| Fireworks AI | `fw_` and 24 to 48 letters and digits with upper case, lower case and a digit all present (so `fw_config_name` is not one) | `Fireworks AI API Key` | medium |
| Stripe restricted | `rk_live_` and 24 or more letters and digits | `Stripe Restricted Key` | high, critical in a script |
| Shopify Admin | `shpat_`, `shpss_`, `shpca_` or `shppa_` and 32 hex characters | `Shopify Admin API Token` | high, critical in a script |
| Google OAuth client secret | `GOCSPX-` and 28 letters, digits, `_` or `-` | `Google OAuth Client Secret` | high, critical in a script |
| Supabase personal access token | `sbp_` and 40 hex characters. It is a Management API token for the user's whole account, not a project `service_role` key: revoke the token in the account settings. | `Supabase Personal Access Token` | high, critical in a script |
| Hygraph | A JWT whose `iss` host is `management-*.hygraph.com` (management API), or another `*.hygraph.com` host (content API) | `Hygraph Management Token` (high), `Hygraph Content API Token` (medium) | |

### The plausibility gate on generic assignments

A generic assignment (`password:`, `secret:`, `apiKey:`, `token:`) names a credential in its key, so the value has to be able to be one. These values are never reported, because each is a label or code that a credential word happens to sit next to, and a drawn random value falls into none of them:

- A key name repeated as its value, a translated label, a template expression, a rooted lower-case path, a dotted catalogue key.
- Lower-case words joined by `_`, `:` or `.`, each at most eight characters, with at most two digits in all, when at least one WHOLE word names a credential (`secret`, `token`, `key`, `pass`, `password`, `pwd`, `auth`, `cred`, `credential`, `api`, `private`, `bearer`, `session`, `sign`, `signature`, `salt`, `jwt`, `login`, `access`, `oauth`, and their plurals; `monkey`, `capital`, `bypass` and `author` do not count): `app_secret_v6`, `secret:reset:token`. The same words with none of those are a passphrase or a drawn value and report; the value of a `Bearer` or `Basic` header is never read as a name; a storage key that ends in a version (`_v6`, one or two digits) may have words of up to sixteen characters (`authentication_secret_v6`). A capital, a longer word or a digit run reads as drawn at random (`Prod_token_8fK2mQ9x`) and reports. `-` is not a joiner: a hyphenated passphrase is a password people choose.
- CSS-module classes, the whole value in css-loader's `<file>__<local>___<hash>` form (`styles-module__secret___x9Y2z`, `Button__primary___3xK9z`). A value that merely contains `-module__`, or has no `___hash`, is a password (`Xk9mQ2vL8zPq-module__4tR7yU1iO3`).
- A URL with no credential in it: an `http(s)://` or `//` URL, or a path starting with `/`, whose parts have no run of 20 or more characters, no six-character piece with a digit, no query value of eight or more characters and no userinfo. A webhook URL with an id in its path, a long path secret and `https://user:pw@host/` still report. // pragma: allowlist secret
- An environment-variable reference: `process.env.NAME`, `import.meta.env.NAME` or `${NAME}`. `$ADMIN123` and `env.Secret9x!` are passwords, not references.
- A short elided stub (up to 12 characters, then `...` or `…`) and a mask of bullets, `*`, `.` or `_`.
- Values longer than 256 characters are never skipped by this gate (none of the shapes below is that long, and it bounds the work).
- A captured span of up to 64 characters that is code: `===` or `!==`, or, together with a `;`, `=>`, `) {`, `function`, `return`, `;var` or a statement after the `;`, or unbalanced parentheses around a member call of words of three or more letters (`window.setTimeout(`). A password with a bare `(` (`Pa(ssw.rd9Qx`), a bare `&&` or `||`, a one-letter member call (`a.b(`) or more than 64 characters is a password. `Zx9&&Kw3mQ7` and `return-of-the-king-2024` are passwords.

A random password (`Xk9!mQ2vL8zP`), a 40-hex key, a `client_secret`, an address such as `0x` plus 40 hex or a bech32 `secret1...` string, and a weak default such as `changeme` still report. Whether a lower-case passphrase such as `correct-horse-battery-staple` reports is decided by the generic entropy floor, which this gate does not change.

### Sample data is not configuration

Seed users, breach-lookup demos, puzzle levels and a password generator's output carry realistic credentials as data. The structure around the value tells them apart from a leak:

- A password that is a row of an array of three or more objects with the same keys, where every row that carries that password key has an email and every such email is on a reserved domain (an unrelated row of the same array does not count, and one row with a reserved address does not excuse rows with none) (`example.com`, `.org` or `.net`, and `.test`, `.example`, `.invalid`, `.localhost`), is sample data and is not reported. `.local` and `.internal` are real private networks and are not reserved.
- The same table with any other email can be a working demo login on production, so it stays reported, as `Possible Demo Login (seed data table)` at medium, with a `meta.hint` that says so.
- An object with two distinct puzzle or generator markers is not reported: a `FLAG{...}` value, a string `flag`, `flagPath` or `flagValue`, a `candidates: [...]` list, a `crack...` key, `sample` next to `options`, `options` with a `length`. One marker alone is not enough (a real config can carry `flag: "beta"` or `options: {length: 10}`); one marker inside a table of same-shaped records is.
- A single config object (`{email, password}`), two rows, rows with different keys and a table of credentials with no emails (`[{tenant, secret}, ...]`) are not exempt.
### Public client keys and signed URLs

Keys and tokens the browser needs in order to work are public by design. Where the call, the attribute or the prefix says so, they report under `leaked-secrets-public` and never count as a leak. Where only a name or a URL parameter says so, the finding stays reported at medium with the evidence in `meta`: public and informational findings are not part of the JSON output, so a downgrade on a name would be a silent drop.

| Family | Evidence | Reported as |
|---|---|---|
| Browser SDK init keys | A generic `apiKey` in the object that is the argument of the SDK's init call or the value of the SDK's key: `Bugsnag.start({apiKey`, `amplitude.getInstance().init(..., {apiKey`. The SDK has to be the immediately enclosing call or object, not nearby text. Datadog, Rollbar, Crisp and Tawk.to are not claimed: their `apiKey` or `accessToken` is the secret key, or their public id has no distinctive shape. (PostHog, Mixpanel, Sentry, Hotjar, FullStory, LogRocket, Intercom, Raygun, Builder.io, Mapbox and LaunchDarkly client IDs were public already.) | `Bugsnag API Key`, `Amplitude API Key`, public |
| Widget embed attributes | A `data-*-api-key` or `data-*-access-token` attribute on a `<script src>` that loads from another host: the loader reads it from the DOM. A `secret`, `private`, `admin`, `server`, `service`, `master` or `password` word anywhere in the attribute name (`data-admin-api-key`, `data-secret-api-key`, `data-private-access-token`) disqualifies it. | `Third-party Widget Key`, public |
| RevenueCat public SDK keys | `appl_`, `goog_`, `amzn_`, `strp_` or `rcb_` followed by 28 to 40 letters and digits, with a digit among them, within 200 characters of `Purchases` or `RevenueCat`: the documented client-key prefixes. Without the SDK's name the shape is not reported. | `RevenueCat Public SDK Key`, public |
| Signed URLs | A JWT that is the value of a `token`, `jwt`, `sig`, `signature`, `access_token` or `X-Amz-*` query parameter and carries all of an `exp`, a `url` claim naming the object and no role or admin scope (a Supabase `/storage/v1/object/sign/...?token=eyJ...` in an `img`, `srcset` or `og:image`). The host is not checked, so the label never lowers a finding: it stays at medium, visible, and a token with a role, an admin scope or another classification (a platform token, a Hygraph token, an expired one) keeps that. A session or user JWT in `?token=`, with or without the storage sign path, is an ordinary JWT. It is a live credential until it expires, so it reports. | `Signed URL Token (JWT)` at medium, with `expiresAt`, `expired` and a hint |
| Public-looking names (added last: they never remove a brand, Shopify or widget classification) | A key under `NEXT_PUBLIC_`, `NUXT_PUBLIC_`, `VITE_` or `PUBLIC_`, or named `public...`, `publishable...` or `client...Key` without `secret`, `private`, `server`, `admin`, `password`, `master` or `service` in the name | The generic finding at medium, with a `meta.hint` to confirm the value is a client key |

Stripe `pk_` keys, Supabase publishable and anon keys, Google browser keys, Sentry DSNs and Mapbox `pk.` tokens were public already. A value that starts `sk_`, `rk_` or `sb_secret_`, a `service_role` key and an admin-scope token report under any of the above: a Stripe key in a widget's `data-api-key` is reported as a Stripe key, and a token with a role is never a signed-URL grant.

An AWS access key id with no 40-character base64-alphabet value within 300 characters (keyed or not: `aws_secret_access_key`, an array element, a sibling property) is probably the public half of the pair. It reports at medium instead of high, with `meta.pair` saying so, because the secret may sit in another file. That is a blind spot: each script is read by itself, so an id in one script and its secret in another ranks medium, below high, although both are in the browser. An id beside its secret reports as before and the secret reports as a critical server-only secret. An id in a presigned URL is informational, as before.

### A provider name needs the whole token

A provider name is given only when the pattern matches the whole token, delimited on both sides. A shape that runs on past its token is not that provider's token. Examples are `AKIA` plus 16 characters followed by a word or by digits, and `AKIA..._PROD`.

Such a token may still be a credential. A fixed-length format can grow, a key can carry a suffix, and text with its markup stripped can run a token into the next word. So the whole token is reported at medium as `Secret Key (provider unknown)`. Its `meta` carries `provider: unknown` and the pattern it `resembles`. A token is dropped only when the provider's own structure rules out the matched part, such as a GitHub token whose checksum fails.

`sk_live_` and `sk_test_` are Stripe's prefixes, and other vendors copy them for their own keys. A key such as `sk_live_..._acmewidget` cannot be a Stripe key. It is still reported, at medium, as `Secret Key (sk_live_ prefix, provider unknown)`. Its `meta` carries `prefix`, `provider: unknown` and `resembles: Stripe Live Key`, so the attribution says what is and is not known.

### Key prefixes that say server or client

Some providers write the kind of key into its prefix. Statsig [documents](https://docs.statsig.com/access-management/api-keys) server secret keys (`secret-`) as confidential and client SDK keys (`client-`) as meant for public applications. A value under a generic key such as `serverSideApiKey` or `clientSideApiKey` is classified by its prefix when `statsig` appears in the key or up to 120 characters before it:

| Value | Provider named | Reported as | Check |
|---|---|---|---|
| `secret-` plus 32 to 64 letters and digits | Yes | `Statsig Server Secret Key` | `leaked-secrets-high` |
| `client-` plus 32 to 64 letters and digits | Yes | `Statsig Client SDK Key` | `leaked-secrets-public` |
| `secret-` plus 32 to 64 letters and digits | No | `Secret Key (secret- prefix, provider unknown)` | `leaked-secrets-medium` |
| `client-` plus 32 to 64 letters and digits | No | The generic assignment, as before | `leaked-secrets-medium` |

A finding says what the page shows, not what the key can do. Its `meta` carries `exposure: present in content served to the browser`, `validity: not tested` and `scope: not tested`. The rule never calls the provider to check a key, so a revoked or narrowly scoped key reads the same as a live one. A key passed straight to a call, such as `Statsig.initialize("secret-...")`, is not classified, because a call argument is not a value position.

To add a provider, add a row to `PROVIDER_KEY_PREFIXES` in `packages/rules/src/security/leaked-secrets.ts`. Add one only when the provider's documentation says which prefix is confidential and which is public.

## How to fix it

```js
// server route, not the client bundle
const res = await fetch("https://api.example.com/v1/data", {
  headers: { Authorization: `Bearer ${process.env.EXAMPLE_SECRET_KEY}` },
});
```

Move the call behind an endpoint you control and read the key from an environment variable that the bundler never inlines. In a framework with a public-variable prefix, check that the leaked name does not carry it. Rotate the exposed credential before anything else: it has been public for as long as the page has.

A medium-confidence hit on a variable named `apiKey` holding a placeholder is a false positive. Confirm the value before rotating.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["security/leaked-secrets"]
```

### Disable all Security rules

```toml squirrel.toml
[rules]
disable = ["security/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["security/leaked-secrets"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.
