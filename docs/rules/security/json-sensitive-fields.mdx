## What over-sharing API responses are

Many apps build their JSON responses by serializing a database row or an ORM model as it is. Every column goes out, including the ones the client never shows: `password_hash`, `salt`, `reset_token`, `api_key`, a card number, or the email and phone number of every other user in the list. The page renders three fields and the network tab shows thirty.

Anyone can open the network tab, so a value in a response is public whether the interface displays it or not. A password hash can be cracked offline, a reset or session token can be replayed, and a list of customer emails is a data breach.

## What squirrel checks

This is a probing rule. It sends requests beyond the crawl, so it runs only when [probing intensity](/configuration/security) is `active` or `aggressive`. On a `passive` run it sends nothing and records one skipped check.

### Which endpoints are requested

Only API endpoints the audit found in your own pages and scripts: a `fetch("/api/users")` or `axios.get(...)` call site, an `/api/...` string literal, or a convention path for your detected stack (see [endpoint discovery](/configuration/security#rules-that-probe)). No path is guessed.

- The endpoint must have the same origin as the audited URL (scheme, host and port). An endpoint on another host, such as a vendor API, is never requested.
- The call site must use `GET`, or state no method. An endpoint called with `POST`, `PUT`, `PATCH` or `DELETE` is never sent anything.
- A path or query that names a state-changing action, such as `logout`, `delete`, `update` or `reset`, is skipped, and so are GraphQL endpoints, which [security/graphql-introspection](/rules/security/graphql-introspection) covers.
- Below `aggressive`, a path that `robots.txt` disallows is skipped.
- At most ten endpoints are requested.

### What is sent

One `GET` per endpoint, with `Accept: application/json`. It carries no cookies and no credentials and does not follow redirects, so it sees exactly what an anonymous visitor would. At most 1 MB of the answer is read, counted after decompression.

### What is flagged

A 2xx response that is JSON (by its content type, or by starting with `{` or `[`) is parsed and every field is read:

- **Fail, `json-sensitive-fields`**: a credential is in the response. That is a password hash recognised by its format (bcrypt, argon2, scrypt, PBKDF2, crypt), a server-side key the [leaked-secrets](/rules/security/leaked-secrets) patterns recognise (a database connection string, a live Stripe secret key and the like), or a value under a field named for a credential that looks like one: a password, salt, secret, API key or token, a social security number, a card number that passes the Luhn check, or a CVV. One check per endpoint. Message: `https://example.com/api/users returns bcrypt hash, access token to a request without credentials`.
- **Warn, `json-bulk-pii`**: personal data for many records. Five or more distinct email addresses, five or more distinct phone numbers, or five or more records with a postal address or a date of birth. Role and admin fields in the same response are counted in the message. Message: `https://example.com/api/users returns personal data for many records to a request without credentials: 48 distinct email address(es), 48 distinct phone number(s), and 48 role or admin field(s)`.
- **Pass, `json-api-responses`**: no requested endpoint returned either. Message: `No JSON response carried sensitive fields or bulk personal data (4 endpoint(s) requested, 3 answered with JSON)`.
- **Skipped**: probing is passive, no API endpoint was found in page code (`no-endpoints`), the shared probe budget ran out before the endpoints were all requested (`probe-budget`), every request failed (`probe-errors`), or some endpoints were not verified (`probe-incomplete`). An endpoint is not verified when it answers with an HTTP `429`, a bot challenge (a challenge page, or a `403` that carries WAF markers) or a `5xx`, or when the request times out. A `429` or a challenge stops the run at once. A `401`, or a `403` the app sent itself with no WAF marker, means the endpoint is protected and counts as answered. Findings for the endpoints that did answer are still reported, and the message names how many were not verified. A run cut short is never reported as a pass.

### One finding per field

[security/auth-endpoint-disclosure](/rules/security/auth-endpoint-disclosure) probes current-user and session endpoints such as `/api/me` and `/api/account` with an anonymous `GET` too. When this rule would request the same endpoint (same path, no query string), one audit sends that request once and both rules read the answer. That shared request reads at most 256 KB; a longer answer is requested again by this rule and read up to 1 MB as usual.

Each rule reports what it finds, and once every site rule has finished, squirrel keeps one finding per field. A password, password hash or credential secret field that `security/auth-endpoint-disclosure` reported on the same endpoint keeps that rule's finding, as the more specific one for an auth or session endpoint, and is removed from this rule's check, together with any credential this rule found inside it. This rule's other fields on that endpoint, such as a card number or an access token, and its bulk personal data finding are kept, and the check's message and field count are rebuilt from what is left. When `security/auth-endpoint-disclosure` is disabled, ran out of probe budget, threw an error or ran past its time budget, it reported nothing, so this rule's finding is kept. When the dropped fields were this rule's only finding and every endpoint was verified, the rule passes, and the pass check's details name the other rule (`reportedBy`) and how many fields it reported (`reportedElsewhere`).

### Values are never reported

No character of a flagged value reaches the report. Each item names the endpoint, the field path with array positions folded (`$.data[].passwordHash`), the kind of value, how many records carried it and the value's length, as in `$.data[].passwordHash = <redacted, 60 chars>`. Field paths are cut at 160 characters, and each endpoint reports at most 20 items.

### What is not flagged

- A field whose value is empty, `null`, a boolean, or a placeholder such as `********` or `[REDACTED]`.
- A word under a `password` field outside a user-shaped record, such as a translation file's `"password": "Passwort"`.
- Tokens meant for the browser: CSRF tokens, pagination cursors and CAPTCHA tokens, and keys that are public by design, such as a Firebase `apiKey` or a Stripe publishable key.
- A single email address, such as a contact address.
- A non-2xx response, a redirect, an HTML page or a network error.

### Limits

This check sees only what an endpoint gives an anonymous caller. It cannot tell whose records came back, and it cannot prove that one signed-in user can read another's data: testing that takes two accounts. An endpoint that needs a session, one called only with `POST`, or one the crawled pages never reference is not requested. For a response over 1 MB, only the first 1 MB is read, as text: the leaked-secrets patterns and the email count still apply, field names are not judged, and the finding carries `truncated: true` and `confidence: "lower"`.

## How to fix it

- Serialize through an allowlist. Return a DTO or view model, use `select` in the query, or name the fields in your serializer, so a new column never reaches the wire by default.
- Never send password hashes, salts, reset or session tokens, API keys or full card numbers to a browser.
- Require authentication on endpoints that list users or customers, scope each response to the caller, and paginate.
- Rotate any secret or token that has been served, and treat exposed personal data as a possible breach.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["security/json-sensitive-fields"]
```

### Disable all Security rules

```toml squirrel.toml
[rules]
disable = ["security/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["security/json-sensitive-fields"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.

## Check names by outcome

Each check name this rule can emit, by what it means to a tool comparing two audits. A **problem** check is a finding. A **clean** check says the rule ran over what it covers and found nothing; it clears the problem checks listed beside it, so a finding is fixed when the rule ran over the same scope and a clean check took its place. A **not checked** check says the rule did not evaluate, and never clears a finding.
