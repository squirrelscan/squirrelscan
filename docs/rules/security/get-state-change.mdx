## What a state-changing GET form is

GET requests are meant to be safe: they should not change anything. Browsers prefetch them, crawlers follow them and chat apps preview them. A form with `method="get"`, or with no `method` because GET is the default, that deletes an account, pays or logs out can be triggered by any of those without the visitor clicking anything. It also puts every field in the URL, history and server logs.

[security/password-form-get](/rules/security/password-form-get) covers forms with a password field. This rule covers the rest.

## What squirrel checks

The rule runs on every crawled page that has a `<form>`. It reads the markup only and submits nothing. A form is assessed when any way of submitting it is GET: the form's `method` (absent, or any value other than `post` or `dialog`), or a `formmethod` on a submit control. A form with no `action` and no `method`, or no usable `action` plus an inline handler, is how a script-driven form looks in the DOM, and is skipped. A form with a password field is skipped, because security/password-form-get reports it.

- `get-state-change`, fail: a way of submitting the form by GET whose action path contains a state-changing word (`delete`, `remove`, `destroy`, `erase`, `logout`, `logoff`, `signout`, `create`, `update`, `save`, `pay`, `checkout`, `purchase`, `transfer`, `cancel`, `confirm`, `subscribe`, `unsubscribe`, `approve`, `reject`, `revoke`, or `sign out`, `log out`, `check out`, `opt out`), or whose submit button text or value does. Only submit controls that send by GET are read: a control's `formmethod`, else the form's `method`, decides its method, and its `formaction`, else the form's `action`, is its action path. A Delete button with `formmethod="post"` on a GET listing form is not flagged. The words `create`, `update`, `save`, `confirm`, `cancel`, `checkout` and `check out` also name read-only actions ("Update", "Confirm filters"), so they count in the action path only, never in button text. Words are matched whole, split on punctuation and camelCase, so `paypal` and `updates` do not match. The query string is not part of the path. Only the first 200 characters of an action path or button text, and the first 200 controls of a form, are read. Each item names the form by its id, name or action and its position (`form 2 of 3`), and says whether the action path or the button text matched, and which word.
- `get-credential-form`, warning: a GET form, with no state-changing word, that has an email field (`type="email"`, an `autocomplete` of `email` or `username`, or a `name` or `id` of `email`, `username` or `login`).
- `get-state-change`, pass: forms were assessed and none was flagged.
- Nothing when the page has no form, or every form posts or is script-driven.

Search and filter forms are not flagged. A form is read-only when it has `role="search"`, an `input type="search"`, or only fields named like `q`, `query`, `search`, `filter`, `sort`, `order`, `page` or `category`. A search form is never flagged for its button text, such as "Update results". A state-changing word in the action path of a form with an unmarked field set is still flagged.

The action shown in a finding is the path only: its query, fragment and any credentials are dropped.

## How to fix it

```html
<form action="/account/delete" method="post">
  <input type="hidden" name="csrf" value="...">
  <button>Delete account</button>
</form>
```

Set `method="post"`, remove any `formmethod="get"` from its buttons, and make the server answer GET on that endpoint with an error, so a link, prefetch or crawler cannot trigger it.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["security/get-state-change"]
```

### Disable all Security rules

```toml squirrel.toml
[rules]
disable = ["security/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["security/get-state-change"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.

## Check names by outcome

Each check name this rule can emit, by what it means to a tool comparing two audits. A **problem** check is a finding. A **clean** check says the rule ran over what it covers and found nothing; it clears the problem checks listed beside it, so a finding is fixed when the rule ran over the same scope and a clean check took its place. A **not checked** check says the rule did not evaluate, and never clears a finding.
