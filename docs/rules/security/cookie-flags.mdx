## What the cookie flags are

`Set-Cookie` carries attributes that decide where a cookie may travel and who may read it. `Secure` stops the cookie being sent over plain HTTP. `HttpOnly` stops client-side JavaScript reading it, which closes the usual path from a cross-site scripting bug to a stolen session. `SameSite` decides whether the cookie rides along on requests started by other sites.

Browsers now default an absent `SameSite` to `Lax`, so omitting it is weaker documentation rather than an open door. `SameSite=None` is the exception: it re-enables cross-site sending for cases like an embedded widget, and browsers reject the cookie entirely unless `Secure` is set alongside it.

## What squirrel checks

The rule reads the `set-cookie` response header of each crawled page, splits it into individual cookies, and emits these checks:

- `cookie-flags` passes when the page sets no cookies at all. Message: `No cookies set on this page`.
- `cookie-samesite-none-insecure` fails when a cookie declares `SameSite=None` without `Secure`. Message: `1 cookie(s) set SameSite=None without Secure — modern browsers reject this combination`, with the cookie names listed.
- `cookie-secure` warns when a cookie on an HTTPS page has no `Secure` attribute. Message: `2 cookie(s) missing the Secure flag`. The check is skipped on HTTP pages, where there is no secure connection to pin the cookie to.
- `cookie-httponly` warns when a cookie has no `HttpOnly` attribute. Message: `2 cookie(s) missing the HttpOnly flag`.
- `cookie-httponly-platform` reports info for a cookie without `HttpOnly` that a hosting platform's sites commonly carry, naming the platform. Message: `1 cookie(s) without HttpOnly that Lovable-hosted sites commonly carry (__dpl); the platform does not document it, so it is reported as info, not a warning`.
- `cookie-httponly-csrf` reports info for a CSRF token cookie without `HttpOnly` (`XSRF-TOKEN`, `csrftoken`), naming the frameworks and linking their docs. Message: `1 CSRF token cookie(s) without HttpOnly (csrftoken: Django). Frameworks that read the token from script (Angular, Axios) need it readable; if your frontend does not read it, you can set HttpOnly. Reported as info, not a warning. Docs: https://docs.djangoproject.com/...`.
- `cookie-samesite` reports info when a cookie declares no `SameSite`, or declares it with an empty value such as `SameSite=`. Message: `2 cookie(s) don't explicitly declare SameSite (browsers default to Lax)`.
- `cookie-flags` passes when cookies were set and none of the above fired. Message: `3 cookie(s) set with Secure, HttpOnly, and SameSite configured correctly`.

### Cookies exempt from the HttpOnly check

Two kinds of cookie are exempt. A few cookies appear on every site a hosting platform serves: you didn't set them, you can't change their flags, and nothing session-like is in them, so a missing `HttpOnly` on one is not a cookie-theft risk and reports as info instead of a warning. The list is short and kept on evidence, not on platform documentation (the platforms do not always document their cookies):

| Cookie | Platform | Why it is listed |
|---|---|---|
| `__dpl` | Lovable | Present on 1,013 of 1,066 Lovable-hosted sites in a 35,000-audit batch, the only cookie missing `HttpOnly`. Lovable does not document it. |

A CSRF token cookie is the other exemption. Some frameworks put the token in a cookie so the page's own script can read it and send it back in a request header (Angular and Axios do). `HttpOnly` is needed only when your frontend does not read the cookie, and then you can set it; the docs below differ on how much that matters. So a missing `HttpOnly` on one of these names is reported as info. Only the missing-`HttpOnly` warning is lifted; `Secure` and `SameSite` are still checked.

| Cookie | Framework | Source |
|---|---|---|
| `XSRF-TOKEN` | Angular, Laravel, Spring Security | [Angular](https://angular.dev/best-practices/security): `HttpClient` reads it and sets `X-XSRF-TOKEN`. [Laravel](https://laravel.com/docs/csrf#csrf-x-xsrf-token): sent so Angular and Axios can place it in `X-XSRF-TOKEN`. [Spring](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html): `CookieCsrfTokenRepository` writes it, with `HttpOnly` false so JavaScript frameworks can read it. |
| `csrftoken` | Django | [Django](https://docs.djangoproject.com/en/stable/ref/settings/#csrf-cookie-httponly): the default cookie name; `CSRF_COOKIE_HTTPONLY` defaults to `False` and Django says setting it offers no practical protection. |

Exemption is by exact cookie name only, and names are case-sensitive as RFC 6265 says (`CSRFTOKEN`, `xsrf-token` and `__Host-XSRF-TOKEN` still warn), on any site: a site that names its own session cookie `__dpl` would also be exempt. Every other cookie, whatever its name or value, still gets the `cookie-httponly` warning. `Secure` and `SameSite` are checked on these cookies as on any other.

Multiple cookies in one header value are split on newlines and on commas that are followed by a `name=` pair, so an `Expires` date containing a comma does not split a cookie in two. Only cookies your server sets in a response header are seen; cookies written by JavaScript are not.

## How to fix it

```
Set-Cookie: session=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```

Set the flags where the cookie is created, in the session middleware or the framework's cookie helper. Drop `HttpOnly` only for a cookie your own frontend genuinely reads, such as a CSRF token mirrored into the DOM. When you need `SameSite=None`, add `Secure` in the same change.

Only cookies your server sets in a `Set-Cookie` response header are inspected. A cookie written by JavaScript, whether yours or a third party's, never reaches this rule.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["security/cookie-flags"]
```

### Disable all Security rules

```toml squirrel.toml
[rules]
disable = ["security/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["security/cookie-flags"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.
