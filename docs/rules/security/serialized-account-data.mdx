title: "Serialized account data: password hashes and codes in framework data"
description: "A page that serializes a whole user record into __NEXT_DATA__ or __NUXT__ publishes its password hash, one-time codes, API keys or session references. squirrel names the JSON field path and never prints the value."
---

## What serialized account data is

A server-rendered page hands its state to the browser as JSON or script, so the framework can hydrate it: `__NEXT_DATA__`, `window.__NUXT__`, Qwik state, Astro island props. When the page passes a whole database row through instead of the few fields it shows, every column of that row is in the page source. That can include the account's password hash, a one-time code, an API key or a session reference. Any visitor, cache, crawler or archive can read it.

## What squirrel checks

The rule is passive. It parses the framework payloads already in each crawled page's HTML and makes no request. It reads `<script id="__NEXT_DATA__">`, `<script id="__NUXT_DATA__">`, Qwik `qwik/json` state, scripts that assign `window.__NUXT__`, `__INITIAL_STATE__`, `__PRELOADED_STATE__`, `__APOLLO_STATE__`, `__remixContext` or `__staticRouterHydrationData` to a JSON object, and the `props` of `<astro-island>` elements. Next.js app router flight chunks are not JSON and are not read. A payload longer than 2,000,000 characters is skipped.

The rule emits checks named `serialized-account-data`:

- Skipped when there is no parsed document. Message: `No document available`.
- Pass when no field was found. Message: `No serialised account records found in framework data`.
- Fail when a password hash, plaintext password, API key or access token, current one-time code or one-time-code secret was found. Warn when only session references or expired one-time codes were found. Message: `Account data serialised into the page: N field(s), first <path> in <payload> (<kind>). Kinds: <kinds>. Values are never shown in the report. Serialise an explicit list of public fields, and purge cached copies of the page`. Each item names the payload, the field path and the kind.

### The kinds

The report tells these apart, because each needs a different response.

| Kind | Matches |
|---|---|
| Password hash | A value in a bcrypt, argon2, scrypt, PBKDF2 or crypt format under any key, or a value of 20 or more characters under a key such as `passwordHash` or `hashedPassword`. |
| Plaintext password | A string under `password`, `passwd`, `pwd` and similar keys, in a record that also has an identity field (`email`, `username`, `id`). |
| API key or access token | A token-shaped string under `apiKey`, `secret`, `clientSecret`, `accessToken`, `refreshToken` and similar keys, in a record with an identity field. Values that start with `pk_`, `public`, `anon` or `AIza` (Google browser keys) are not flagged, and neither is a key in a record with `appId`, `applicationId`, `authDomain`, `projectId`, `messagingSenderId`, `storageBucket` or `measurementId` (a Firebase or Algolia client config, public by design). |
| One-time code | A 4 to 10 digit or 6 to 8 character code under `otp`, `verificationCode`, `resetCode`, `mfaCode` and similar keys, in a record with an identity field. |
| Expired one-time code | A one-time code whose sibling expiry field (`otpExpiresAt`, `expiresAt`, `validUntil`) is in the past when the audit runs. It is a warning. The expired code is not described as current access. |
| One-time-code secret | A base32-shaped string under `totpSecret`, `otpSecret` and similar keys. |
| Session reference | A string of 16 or more characters under `sessionId`, `sessionToken`, `sid` and similar keys, in a record with an identity field. It points to server-side state. The audit does not show that it works as a bearer token and does not say so. |

### What is not flagged

- Form definitions and labels, such as `{"name": "password", "label": "Password"}` or a translation table with `"password": "Password"`.
- Placeholders such as `********`, `[REDACTED]`, `changeme` or `your_api_key_here`.
- Documented example values: `password`, `hunter2`, `correcthorsebatterystaple`, and the bcrypt hash that library documentation uses.
- Anything under a path segment named `example`, `examples`, `sample`, `demo`, `mock`, `fixture` or `docs`.
- A `password`, API key or one-time code key with no identity field in the same record. A site-wide key in page config is a matter for [security/leaked-secrets](/rules/security/leaked-secrets).

### The value is never printed

A report is shared and stored. An item holds the JSON field path and the kind, and never a character of the value, an email or any other identifier from the record. Array indices fold to `[]`. A path key is printed only when it is on an allowlist: role and container names such as `user`, `account`, `profile`, `owner` or `props`, and the credential field names in the table above. Every other key is shown as `[*]`, because a map can be keyed by a username or an email. A role name that equals the record's own username or email is shown as `[*]` too.

### Limits

The rule matches field names and value shapes, so a credential under an unusual key is missed, and a field named like a credential that holds something else can be flagged. Only payloads in the page's markup are read, not data fetched after load. A finding shows what the page serves to anyone. It does not show whether the hash or session is still usable.

## How to fix it

Stop serializing the record. Pass the page an explicit list of public fields (a view model or DTO), and select only those columns in the query, so a new column never reaches the page by default. With Next.js, return only the needed fields from `getServerSideProps`, `getStaticProps` or the server component. With Nuxt, map the record before it enters `useAsyncData` or state.

Then purge what was already published. Clear the CDN and server-render caches that held the page, and ask search engines and web archives to drop their copies where you can. After that, rotate the exposed API keys, expire the sessions and one-time codes, and force password resets for affected accounts. Rotation alone leaves the next page free to leak the same field.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["security/serialized-account-data"]
```

### Disable all Security rules

```toml squirrel.toml
[rules]
disable = ["security/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["security/serialized-account-data"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.

## Check names by outcome

Each check name this rule can emit, by what it means to a tool comparing two audits. A **problem** check is a finding. A **clean** check says the rule ran over what it covers and found nothing; it clears the problem checks listed beside it, so a finding is fixed when the rule ran over the same scope and a clean check took its place. A **not checked** check says the rule did not evaluate, and never clears a finding.
