squirrelscan includes **300+ rules** across **22 categories**, plus opt-in cloud gap analysis. Every category rolls up into one of four score groups: **SEO**, **Performance**, **Security**, and **Agents**. These are the four scores you see on reports and in the dashboard, alongside the overall health score.

Most rules run locally and need no login. A handful of [cloud rules](/cloud/rules) use AI analysis, full filter lists, or live search data - they require login and are skipped when you're not logged in. Cloud rules carry a notice banner on their doc pages.

## Content inside noscript

A browser with scripting enabled reads `<noscript>` content as plain text, so nothing in it loads, renders or reaches the accessibility tree. Sites put tracking pixels, Google Tag Manager iframes, lazy-load fallback images and fallback stylesheets there for visitors without JavaScript, so reporting them flags markup that never runs.

The rules that describe what a browser loads or renders skip elements inside `<noscript>`, so a page with a `<noscript>` fallback gets the same result as the same page without it:

- Accessibility: [aria-required-children](/rules/a11y/aria-required-children), [frame-title](/rules/a11y/frame-title), [image-redundant-alt](/rules/a11y/image-redundant-alt), [meta-refresh](/rules/a11y/meta-refresh)
- Images: [alt-text](/rules/images/alt-text), [aspect-mismatch](/rules/images/aspect-mismatch), [broken-images](/rules/images/broken-images), [dimensions](/rules/images/dimensions), [filename-quality](/rules/images/filename-quality), [lazy-loading](/rules/images/lazy-loading), [modern-format](/rules/images/modern-format), [offscreen-lazy](/rules/images/offscreen-lazy), [optimized](/rules/images/optimized), [picture-element](/rules/images/picture-element), [responsive-size](/rules/images/responsive-size), [srcset](/rules/images/srcset)
- Performance: [animated-content](/rules/perf/animated-content), [carousel-hidden-eager](/rules/perf/carousel-hidden-eager), [cls-hints](/rules/perf/cls-hints), [critical-request-chains](/rules/perf/critical-request-chains), [duplicate-js](/rules/perf/duplicate-js), [font-delivery](/rules/perf/font-delivery), [font-loading](/rules/perf/font-loading), [inp-hints](/rules/perf/inp-hints), [js-libraries](/rules/perf/js-libraries), [lazy-above-fold](/rules/perf/lazy-above-fold), [lcp-fetchpriority](/rules/perf/lcp-fetchpriority), [lcp-hints](/rules/perf/lcp-hints), [legacy-js](/rules/perf/legacy-js), [preconnect](/rules/perf/preconnect), [render-blocking](/rules/perf/render-blocking), [source-maps](/rules/perf/source-maps), [total-byte-weight](/rules/perf/total-byte-weight), [unminified-css](/rules/perf/unminified-css), [unminified-js](/rules/perf/unminified-js)
- Security: [csp-blocks-own-resources](/rules/security/csp-blocks-own-resources), [mixed-content](/rules/security/mixed-content), [sri](/rules/security/sri), [third-party-cookies](/rules/security/third-party-cookies)
- Blocking and integrity: [blocked-links](/rules/adblock/blocked-links), [template-discontinuity](/rules/integrity/template-discontinuity)

Same-domain scripts, stylesheets and images that appear only inside `<noscript>` are not fetched for the file-size and compression rules either. Links inside `<noscript>` are still collected for crawling, and the remaining rules read the page as before.

## Content inside shadow roots

A web component can render its controls inside a declarative shadow root, written as `<template shadowrootmode="open">` (or `"closed"`) inside its host element. A browser attaches that content to the host and renders it. squirrel reads it the same way: before the rules run, the content of such a template is placed where the template was, so every DOM rule (button names, links, images, headings, form fields) sees the buttons and links inside the root as it sees any other.

- As in a browser, only the first shadow template of a host counts, an element that cannot host a shadow root (a `table`, an `li`) keeps its template inert, and a plain `<template>` with no `shadowrootmode` is never checked: its content is not rendered.
- **Ids stay scoped to their root.** The same `id` in three copies of a component is not a duplicate, and a `<label for>` or `aria-labelledby` in one root does not point at an element of another. Inlining gives each root's ids an internal suffix, and the references to them from inside that root, while the rules run; findings name the element as it is in your source.
- **Slots.** A `<slot>` shows the host's own children assigned to it instead of its fallback content, so the fallback is not checked where the host supplies content for that slot, and is checked where it does not.
- **Bounds.** At most 5,000 shadow roots are inlined per page, nested up to 16 levels deep; templates that are skipped (inert, on a host that cannot hold a root) do not count against the 5,000. A page past either bound keeps the rest inert.
- A shadow root created by JavaScript after load, with `attachShadow`, exists only in a [browser-rendered](/guides/browser-rendering) audit and is read from the rendered page.

## Pages kept out of search

A page marked `noindex` will not show up in search results, so findings about how it would look there are noise. Twelve rules leave these pages alone:

- [core/meta-title](/rules/core/meta-title), [core/meta-description](/rules/core/meta-description), [core/h1](/rules/core/h1), [content/word-count](/rules/content/word-count) and [content/h1-title-alignment](/rules/content/h1-title-alignment) skip the page. Each records one skipped check, such as `Skipped: page is set to noindex via robots meta tag` (or `via X-Robots-Tag header`), in place of its usual result.
- [core/title-unique](/rules/core/title-unique), [content/duplicate-title](/rules/content/duplicate-title) and [content/duplicate-description](/rules/content/duplicate-description) leave the page out when they group pages by title or description.
- [crawl/sitemap-coverage](/rules/crawl/sitemap-coverage) never lists the page as missing from the sitemap, since a noindex page should not be in it.
- [content/title-pattern-outlier](/rules/content/title-pattern-outlier) leaves the page out when it learns the site's title template, and never reports it as an outlier.
- [content/thin-vs-site-norm](/rules/content/thin-vs-site-norm) leaves the page out when it learns each page type's word-count norm, and never reports it as a thin outlier.
- [links/orphan-pages](/rules/links/orphan-pages) never reports the page as an orphan. Its own links still count toward the pages they point to.

**What counts as noindex.** The page's `<meta name="robots">` content or its `X-Robots-Tag` response header contains `noindex`. This is the same test [crawl/indexability](/rules/crawl/indexability) uses, so a header scoped to one crawler, such as `X-Robots-Tag: googlebot: noindex`, counts too. A URL blocked by robots.txt is not a noindex, and crawler-specific meta tags such as `<meta name="googlebot">` are not read.

**Staging sites and preview deployments.** Pages are skipped only when the site itself is being indexed. squirrelscan decides that from the homepage, which is the page at `/` on the audited host (with or without `www.`, over http or https, with no query string), or, when the homepage was not fetched or answered with an error, from the page the audit started from. If the crawl holds more than one copy of that page, such as both the http and https homepage, any copy marked noindex counts.

| That page is | Result |
|---|---|
| indexable | noindex pages are skipped |
| noindex | nothing is skipped |
| not fetched (neither the homepage nor the start page) | nothing is skipped |

A site-wide `noindex` usually means the audit is checking a site before launch, which is when title, description and H1 findings matter most. Vercel, Netlify and Cloudflare Pages preview deployments send `X-Robots-Tag: noindex` on every page by default, so an audit of a preview URL runs every rule.

**In reports and scores.** A skipped check is not an issue. It does not appear in the issue list in any report format, it is not counted as passed, warning or failed, and the [health score](/reports#health-score) leaves it out. A page left out of a site rule's grouping simply is not in it.

**Everything else still runs.** Accessibility, security and performance rules, and every link rule other than orphan pages, check noindex pages as usual, and so do [core/robots-meta](/rules/core/robots-meta), [crawl/indexability](/rules/crawl/indexability) and [crawl/all-noindex-pages](/rules/crawl/all-noindex-pages), which report the noindex pages themselves.

## Pages short by nature

A contact page or a privacy policy is short on purpose, and nobody searches for it by its title. When the page classifier's model labels a page `contact` or `legal` with a confidence of at least 0.9, four rules leave it alone:

| Rule | Skips | Page types |
|---|---|---|
| [content/word-count](/rules/content/word-count) | the whole check | `contact`, `legal` |
| [core/meta-title](/rules/core/meta-title) | the "too short" finding only | `contact`, `legal` |
| [core/meta-description](/rules/core/meta-description) | the "too short" finding only | `contact`, `legal` |
| [content/keyword-stuffing](/rules/content/keyword-stuffing) | the whole check | `legal` |

Each skipped page gets one skipped check, such as `Skipped: Word Count is not judged on a contact page`, with `details.pageType` and `details.skippedByType`. It is a "does not apply" skip: it does not appear in the issue list, is not counted as passed, warning or failed, leaves the [health score](/reports#health-score) alone, and resolves a finding an earlier audit reported on the page. A "too long" title or description, a missing title or description, and every other rule still apply to these pages.

**Which labels count.** Only a model label at or above 0.9, the same bar as [schema/expected-type](/rules/schema/expected-type), and only when the page's main content bears it out, because the model reads a page's path and heading as much as its text. The main content is the `<main>` landmark, else the body, without the header, navigation, footer and aside: a footer that links "Privacy Policy | Terms | Cookies" or carries a `mailto:` link proves nothing. A `legal` page needs policy vocabulary: at least three distinct whole-word phrases such as "privacy policy", "personal data", "governing law", "you agree" or "last updated", or their German, French, Spanish, Italian, Portuguese and Dutch equivalents. A `contact` page needs a way to reach the organisation in that content: a `tel:` or `mailto:` link, an email address or a phone number (nine to fifteen digits with a separator pattern or brackets, or eight after a `+`; an IP address or a list of years is not one), or a message box; a newsletter field or a site search does not count. A support page with a contact form is a contact surface and is skipped. A page with no text, such as a client-rendered shell at `/privacy`, is never skipped: it is judged like any other thin page. So a marketing page at `/solutions/legal` or `/contact` keeps its finding. A label from the rules fallback is read from the page's own structured data, so it never relaxes a verdict, and neither does a model label below 0.9 or a page the classifier did not run on (`--no-classifier`, or an audit from before the classifier). Those pages are judged as before. A page reused from the crawl cache keeps no label from a different classifier: when the model, the classifier's rules or the `--no-classifier` setting differ from the run that first read the page, the page is fetched and read again, so a label is never older than the classifier running. A skipped page also resolves a finding an earlier audit reported on it, the way a noindex page does.

**Left as they are, with the reason.** [core/h1](/rules/core/h1) (a page without an H1 is a finding whatever its type), [content/reading-level](/rules/content/reading-level) (it judges the text for the reader, and a legal page is hard to read for its readers too), and the [E-E-A-T](/rules/eeat) rules (they are site-wide questions, such as whether any page has an author, not a per-page length floor).

## Rule time budget

Rules read content the audited site controls, so a page can be built to make a pattern match very slowly. The first line of defence is the rules themselves: their patterns are written to avoid catastrophic backtracking. The time budget is the backstop for whatever still gets through, such as a rule repeating a slow match across thousands of elements or pages.

Every rule runs under it: two seconds per page for a page rule, and two seconds per page of the site for a site rule, capped at 60 seconds. A rule that runs past it is abandoned for that page, and the audit carries on with the next rule. The budget is checked between operations, not in the middle of a single pattern match, so a rule can overrun it by about one runaway match before it is abandoned: in testing, a 200 ms budget abandoned a catastrophic pattern after about 430 ms, roughly twice the budget. It is wall-clock time, so on a heavily loaded machine an ordinary page can run out of time too.

The report records it as a skipped check named after the rule with `-error` on the end, such as `content/hidden-text-error`, on every page where it happened, the first one included (or on the whole site, for a site rule). Its `skipReason` is `rule-timed-out` and its message is `Rule not evaluated: exceeded its 2000 ms time budget and was abandoned` (the number is the budget in force). Its details carry `timedOut: true`, the `ruleId`, the `budgetMs` in force, `elapsedMs` (how long the rule had actually run when it was stopped, which is a little over the budget on an idle machine and far over it when the machine was starved of CPU) and `pages`, the number of pages it timed out on. `elapsedMs` is for diagnosing a timeout and is never scored or counted. A timed-out rule is not a finding: the rule did not finish, so nothing was found on that page, and the page is not evaluated for it. It is not counted as a failed check and it does not lower the score: the health score is the same as if that page had been left unchecked for that rule. The audit also gets one info check named after the rule with `-timeouts` on the end, such as `content/hidden-text-timeouts`, whose details carry `pagesNotChecked`, the final count of pages that rule did not check, and `maxElapsedMs`, the longest the rule ran before it was stopped. The console, text, markdown, HTML, XML and LLM reports also print a yellow `Not checked: <rule>.` line for each rule that timed out, with a hint to run the audit again or raise `time_budget_ms`, so a timed-out security rule is never mistaken for a clean one. That rule's own result for those pages is not in the report.

A timed-out rule did not check those pages. For a security rule, such as `security/leaked-secrets`, that means no finding on those pages is not a clean result: the pages were not scanned, so treat them as unchecked and look at them yourself. So a security rule that times out is counted by [`--fail-on`](/cli/audit#gate-ci-on-audit-results) as one warning-severity finding (`warnings>0` and `severity>=warning` trip on it, `errors` and `score` do not, so a gate that only uses those two passes: add a warning gate or raise `time_budget_ms`), while the score stays as if the page had been left unchecked. The count appears only in the gate summary, never as a finding in the report. The report and the gate summary name the rule and the number of pages it did not check, so a page built to make a security rule time out cannot leave a quiet pass. Rules in other categories are not counted by the gate.

Ordinary pages never come close on an idle machine: the slowest rule takes a few milliseconds per page. If you see this on a page that looks normal and the machine was not busy, [open an issue](https://github.com/squirrelscan/squirrelscan/issues) with the page URL.

### Changing the budget

Set [`time_budget_ms`](/configuration/rules#time_budget_ms) in the `[rules]` section of `squirrel.toml`:

```toml squirrel.toml
[rules]
time_budget_ms = 3000  # three seconds per rule per page
```

Raise it when rules time out on ordinary pages because the machine is slow or busy, such as a shared CI runner. A value below 1000 is refused. A site rule gets the same amount per page of the site, capped at 60 seconds, or at the budget itself if you set it above that. `0` turns the budget off, which lets one hostile page stall the audit, so leave it on for sites you do not control. The setting applies to audits the CLI runs; cloud audits use the default.

## A rule that throws

A rule can also throw an error on a page, for example on markup it did not expect. That is a defect in squirrelscan, not a problem with your page, so it is handled the same way as a timeout: the rule is **not evaluated** on that page, never counted as a failure, and the health score is the same as if the page had been left unchecked for that rule. One rule throwing on every page of a 30 page site is one defect, not 30 failures.

That also means a rule that throws on **every** page it runs on leaves the score and the exit code as if it had passed. It is never silent: the report names it in `notChecked` and on a `Not checked:` line, and a [`--fail-on`](/cli/audit#gate-ci-on-audit-results) gate on `warnings` or `severity` counts each such rule as one warning, so a CI job does not go green over a rule that checked nothing. `errors` and `score` gates are unaffected.

The report records a skipped check named after the rule with `-error` on the end (`content/hidden-text-error`) on every page where it happened. They are identical but for the page, so the report shows them as one check that lists the pages. Its `skipReason` is `rule-timed-out` (the same not-evaluated reason as a timeout) and its `details` carry `errored: true`, the `ruleId` and `error` (the first error message, clipped to 200 characters because it can quote page content). A site rule that throws gets one such check for the site. The audit also gets one info check named `<rule>-errors` (`content/hidden-text-errors`) whose details carry `pagesNotChecked`, the final count (or `site: true`), and the first `error`. The console, text, markdown, HTML, XML and LLM reports print a `Not checked:` line for the rule saying it hit an internal squirrelscan error on N pages, and the JSON report lists it in [`notChecked`](/configuration/output#json-output-schema) with its first ten `pages`. Update squirrel and run the audit again, or report it at the issue tracker.

## Configuration

### Enable/Disable rules

Use glob patterns in `squirrel.toml`:

```toml squirrel.toml
[rules]
# Enable specific rules or categories
enable = ["*"]  # all rules (default)

# Disable specific rules
disable = [
  "ax/*", "ai/*",   # disable all Agent Experience rules
  "content/word-count",  # disable specific rule
]
```

### Rule options

Some rules have configurable options:

```toml squirrel.toml
[rule_options."core/meta-title"]
min_length = 30
max_length = 75

[rule_options."content/word-count"]
min_words = 300
```

See individual rule pages for available options.
