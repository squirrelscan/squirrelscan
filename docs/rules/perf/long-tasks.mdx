## What long tasks are

The browser's main thread runs scripts, style, layout and input handling one task at a time. A task over 50 milliseconds is a long task: input that arrives during it waits. Total blocking time (TBT) adds up how far each long task runs past 50 milliseconds, so one 350 ms task contributes 300 ms.

## What squirrel checks

The rule runs once per audit and reads the long-task measurement that squirrelscan's cloud runner recorded on a sample of pages. It needs a cloud audit; a local CLI audit shows it as skipped, not failed. It emits one check:

- `long-tasks`: reports the longest task and the worst page's TBT across the sampled pages. It passes at 200 ms or under, warns above 200 ms and fails above 600 ms, the edges Lighthouse uses for "needs improvement" and "poor". On a warning or failure the pages over 200 ms are listed, worst first, with their TBT, longest task and long-task count. The message says the numbers are from squirrelscan's cloud runner on a sample of pages.
- `long-tasks`, skipped, when the run has no runtime measurement or the runner recorded no long-task data on any sampled page.

This is a lab measurement from one machine with one network and CPU profile. It is useful for finding scripts that block the main thread and for comparing one audit with the next. It is not what your visitors' devices experience: field data from real visits is the measure for that.

## How to fix it

Open a performance trace of the worst page, find the scripts behind the longest tasks, and split or defer that work. Move heavy computation to a web worker, yield to the main thread between chunks, and delay third-party tags until after the page is interactive. Then run a cloud audit again and compare TBT.

## Enable / disable

### Disable this rule

```toml squirrel.toml
[rules]
disable = ["perf/long-tasks"]
```

### Disable all Performance rules

```toml squirrel.toml
[rules]
disable = ["perf/*"]
```

### Enable only this rule

```toml squirrel.toml
[rules]
enable = ["perf/long-tasks"]
```

`enable` replaces the default `["*"]`, so this is the only rule selected. Leave `disable` out: a rule that matches any `disable` pattern is skipped even when `enable` names it. Only an `enabled` setting under a rule's own `[rule_options]` table overrides both lists.

## Check names by outcome

Each check name this rule can emit, by what it means to a tool comparing two audits. A **problem** check is a finding. A **clean** check says the rule ran over what it covers and found nothing; it clears the problem checks listed beside it, so a finding is fixed when the rule ran over the same scope and a clean check took its place. A **not checked** check says the rule did not evaluate, and never clears a finding.
