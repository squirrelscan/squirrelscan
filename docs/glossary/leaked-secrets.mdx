**Leaked secrets** are credentials, such as API keys, access tokens, database URLs or private keys, that end up in something the browser downloads: the HTML, a JavaScript bundle or a source map.

Anything sent to the browser is public. A key in a minified bundle can be read by anyone who opens the developer tools, and automated scanners look for them. OWASP's testing guide treats reviewing page content and scripts for leaked information as a standard step. Source maps are a related exposure. MDN describes them as files that map transformed code back to the original source, so a public map hands out the readable code, including comments and internal paths. Not every key in a page is a leak, though. Some are public by design, such as a maps or analytics key restricted to one domain.

## Why it matters

A leaked server-side key works for whoever finds it, and the bill or the breach lands on the site owner. The usual cause is a build tool inlining an environment variable into the client bundle, a framework's public-variable prefix used on the wrong name, or a debugging line left in a template. Development leftovers cause smaller leaks of the same kind: links to `localhost`, private IP addresses and preview hosts that reveal internal infrastructure.

## How squirrelscan checks it

[security/leaked-secrets](/rules/security/leaked-secrets) scans the HTML of every crawled page, every inline script and the external JavaScript files the crawl fetched, against about ninety patterns for AI providers, cloud platforms, payment processors, databases and generic `api_key = "..."` assignments. It fails on high-confidence matches and on server-only secrets in browser-served scripts, and warns on medium-confidence ones to verify by hand. Keys that are public by design are listed at info level and never count as leaks. Every reported value is masked. [perf/source-maps](/rules/perf/source-maps) finds `sourceMappingURL` comments and `SourceMap` headers that point to a map. It does not fetch the map, so it reports possible exposure rather than proving it. [content/dev-leakage](/rules/content/dev-leakage) finds references to `localhost`, private IP ranges, local-only names such as `myapp.test`, preview deployments and development subdomains on a production page.

## How to fix it

Rotate the exposed credential first. It has been public since it shipped. Then move the call behind your own server:

```js
// server route, not the client bundle
const res = await fetch("https://api.example.com/v1/data", {
  headers: { Authorization: `Bearer ${process.env.EXAMPLE_SECRET_KEY}` },
});
```

Read the key from an environment variable the bundler never inlines ([the secrets fix](/rules/security/leaked-secrets#how-to-fix-it)). Build source maps as hidden, upload them to the error tracker and leave them out of the deploy ([the source map fix](/rules/perf/source-maps#how-to-fix-it)). Replace development origins with relative paths ([the dev leakage fix](/rules/content/dev-leakage#how-to-fix-it)).
