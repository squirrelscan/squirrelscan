An **accessible name** is the text assistive technology announces for an element, such as "Search" for a button or "Email address" for a field, worked out from the element's content, its label or ARIA attributes.

W3C's Accessible Name and Description Computation specification sets the order. `aria-labelledby` wins, then `aria-label`, then the native label: a `<label>` for a form field, `alt` for an image, a `<caption>` for a table. Then comes the element's own text for roles that take their name from content, such as buttons and links, and finally `title`. The Authoring Practices Guide's advice is to prefer visible text, and to treat `aria-label` as the fallback when there is nothing visible to point at. WCAG success criterion 4.1.2, Name, Role, Value, requires every user interface component to have a name that can be determined by software.

## Why it matters

A control with no name is announced as "button" or "edit text" and nothing else. Icon buttons are the usual case: a magnifying glass, a cross or a hamburger menu that is obvious to a sighted user is silent to a screen reader. Voice control users hit a different problem. They say the words they can see, so a button that shows "Search" but is named "Find products" does not respond to "click Search". WCAG 2.5.3, Label in Name, asks that the name contain the visible text for that reason.

## How squirrelscan checks it

Fourteen hand-written rules check names, each for a kind of element. [a11y/button-name](/rules/a11y/button-name) and [a11y/aria-labels](/rules/a11y/aria-labels) cover buttons and clickable SVGs. [a11y/aria-input-field-name](/rules/a11y/aria-input-field-name), [a11y/select-name](/rules/a11y/select-name) and [a11y/aria-toggle-field-name](/rules/a11y/aria-toggle-field-name) cover fields, selects, checkboxes and radios. [a11y/aria-command-name](/rules/a11y/aria-command-name) covers links and menu items, and [a11y/aria-dialog-name](/rules/a11y/aria-dialog-name) covers dialogs. [a11y/frame-title](/rules/a11y/frame-title) covers iframes. Meters, progress bars, tooltips and tree items each have their own rule, and [a11y/table-duplicate-name](/rules/a11y/table-duplicate-name) flags tables that share or lack a name on pages with more than one. [a11y/label-content-name-mismatch](/rules/a11y/label-content-name-mismatch) fails an `aria-label` that does not contain the element's visible text.

Most of these rules skip elements hidden from the accessibility tree, and report ones a style may hide in a way squirrelscan cannot settle as unconfirmed. An icon drawn by a CSS pseudo-element is not in the markup, so such a button reads as empty.

## How to fix it

Name the element that has the role, not the icon inside it, and hide the icon:

```html
<button aria-label="Close settings">
  <svg aria-hidden="true">...</svg>
</button>
<button aria-label="Search products">Search</button>
```

Prefer a visible `<label>` for form fields, which also makes the words clickable ([the select fix](/rules/a11y/select-name#how-to-fix-it), [the field fix](/rules/a11y/aria-input-field-name#how-to-fix-it)). Point a dialog's `aria-labelledby` at its visible heading ([the dialog fix](/rules/a11y/aria-dialog-name#how-to-fix-it)). Start an `aria-label` with the visible words ([the mismatch fix](/rules/a11y/label-content-name-mismatch#how-to-fix-it)), and describe an iframe's content rather than the vendor ([the frame fix](/rules/a11y/frame-title#how-to-fix-it)).

## Related terms

- [ARIA](/glossary/aria): Accessible Rich Internet Applications: roles, states and properties that describe custom widgets to assistive technology.
- [Form labels](/glossary#form-labels): The `<label>` or accessible name tied to each form control, plus autocomplete tokens, so people know what to enter.
- [Anchor text](/glossary/anchor-text): The visible, clickable text of a link, which tells readers and search engines what the target is about.
