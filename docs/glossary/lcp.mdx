**Largest Contentful Paint (LCP)** is the time from the start of a page load until the largest image, text block or video visible in the viewport has rendered.

It is the loading metric of the [Core Web Vitals](/glossary/core-web-vitals). web.dev counts 2.5 seconds or less as good and more than 4 seconds as poor, judged at the 75th percentile of page loads. Its optimization guide splits LCP into four parts that add up to the whole: time to first byte, resource load delay (until the browser starts fetching the LCP resource), resource load duration and element render delay.

## Why it matters

On most pages the LCP element is an image, and most of what delays it is in the markup. A hero the preload scanner cannot find starts late. One marked `loading="lazy"` waits for layout before it is requested at all. Stylesheets and scripts in `<head>` hold up the first paint, and a slow server response pushes everything back, because nothing paints before the HTML arrives. web.dev also warns that shrinking the image alone can just move the saved time into render delay.

## How squirrelscan checks it

squirrelscan does not measure LCP. A crawl has no paint timing, so the rules look for the causes instead.

[perf/lcp-hints](/rules/perf/lcp-hints) and [perf/lcp-fetchpriority](/rules/perf/lcp-fetchpriority) pick the likely hero from the first eligible images in document order, skipping lazy images, SVG and ICO files, tracking pixels, images inside `<header>` or `<nav>` and images declared smaller than 300 pixels. The first wants a matching image preload. The second accepts `fetchpriority="high"` or a preload. [perf/lazy-above-fold](/rules/perf/lazy-above-fold) flags `loading="lazy"` on the first three images that could be above the fold. [perf/render-blocking](/rules/perf/render-blocking) counts blocking stylesheets and scripts in `<head>`, and [perf/preconnect](/rules/perf/preconnect) looks for missing connection hints to thirteen common CDN hosts. [perf/ttfb](/rules/perf/ttfb) is the one measurement here: it times the first byte of each fresh fetch.

The hero is a guess from markup. When the real LCP element is text or a CSS background image, the rules cannot see it and may flag another `<img>` instead.

## How to fix it

Leave the hero image eager and raise its priority:

```html
<img src="/hero.jpg" width="1200" height="630" fetchpriority="high" alt="" />
```

Add a preload in `<head>` when the image is discovered late, for example from CSS or a script ([the preload fix](/rules/perf/lcp-hints#how-to-fix-it)). Keep `loading="lazy"` for images below the fold ([the lazy-loading fix](/rules/perf/lazy-above-fold#how-to-fix-it)). Give scripts `defer` and inline the CSS the first screen needs ([the render-blocking fix](/rules/perf/render-blocking#how-to-fix-it)). If the first byte is slow, cache the HTML at the edge ([the TTFB fix](/rules/perf/ttfb#how-to-fix-it)).

## Related terms

- [Core Web Vitals](/glossary/core-web-vitals): Google's three user-experience metrics: LCP for loading, INP for responsiveness and CLS for visual stability, judged at the 75th percentile of real visits.
- [fetchpriority](/glossary#fetchpriority): An HTML attribute (high, low, auto) that hints how urgently the browser should fetch an image, script or link.
- [Render-blocking resources](/glossary/render-blocking-resources): Stylesheets and synchronous scripts in the head that the browser must fetch before it can paint anything.
- [Lazy loading](/glossary/lazy-loading): Deferring off-screen images and iframes with loading="lazy" so they load as the visitor scrolls.
- [HTTP caching](/glossary/http-caching): Response headers (Cache-Control, ETag, Expires) that let browsers and CDNs reuse a response instead of fetching it again.
