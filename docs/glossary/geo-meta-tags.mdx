**Geo meta tags** are the `geo.region`, `geo.placename`, `geo.position` and `ICBM` meta tags that state the place a page is about.

`geo.region` holds an ISO 3166-2 country and subdivision code, `geo.placename` a city or locality, `geo.position` the coordinates as `latitude;longitude`, and `ICBM` the same coordinates separated by a comma. None of the four is a web standard: they come from an IETF Internet-Draft that expired in 2008 without becoming an RFC.

Looking for GEO in the AI search sense? That is [generative engine optimization](/glossary/generative-engine-optimization), a different thing that shares the abbreviation.

## Why it matters

For search, very little. Google says it ignores locational meta tags such as `geo.position`, so adding them will not move a page in local search. They are valid HTML and cost nothing to serve. If you keep them, keep them in step with your [LocalBusiness structured data](/rules/schema/local-business): a wrong city name then shows up in two places instead of one. Treat them as a supplement to schema, never a replacement.

## How squirrelscan checks it

[local/geo-meta](/rules/local/geo-meta) looks for the four tag names on each page. One or more passes, and none is reported at info level, which does not need fixing on pages that are not about a place. The rule matches names, not values, so a stale city or wrong coordinates still pass, and it only counts `ICBM` in that exact uppercase spelling. It is skipped when the site profile says the site is not a local business.

## How to fix it

Put the tags in the `<head>` of location and service-area pages, not site-wide, with values that match the address in your `LocalBusiness` JSON-LD (see [the geo meta fix](/rules/local/geo-meta#how-to-fix-it)):

```html
<meta name="geo.region" content="US-CA" />
<meta name="geo.placename" content="San Francisco" />
<meta name="geo.position" content="37.7749;-122.4194" />
<meta name="ICBM" content="37.7749, -122.4194" />
```
