**ARIA**, Accessible Rich Internet Applications, is a W3C specification of roles, states and properties, such as `role="tab"`, `aria-expanded` and `aria-label`, that describe an element to assistive technology when HTML alone does not.

ARIA changes what a screen reader announces, not how an element behaves. A `<div role="button">` is announced as a button but does not get focus or respond to Enter until a script makes it. That is why W3C's guidance on using ARIA starts with its first rule: if a native HTML element or attribute already has the semantics and behavior you need, use it instead of adding a role to something else. The ARIA Authoring Practices Guide puts the same point more bluntly: no ARIA is better than bad ARIA.

## Why it matters

The Authoring Practices Guide compares ARIA to CSS for assistive technology: for a screen reader user, it controls the non-visual experience. Wrong ARIA describes a page that is not there. A misspelled role means nothing, a checkbox without `aria-checked` has no state, `aria-hidden="true"` on the body hides the whole page, and a focusable link inside an `aria-hidden` region lands the keyboard on something the screen reader cannot announce. Most of these come from component libraries and copy-paste, and they repeat on every page that uses the component.

## How squirrelscan checks it

Twelve hand-written rules cover the common ARIA errors. [a11y/aria-roles](/rules/a11y/aria-roles) and [a11y/aria-deprecated-role](/rules/a11y/aria-deprecated-role) check role names against core ARIA and flag deprecated and abstract roles. DPUB and Graphics ARIA module roles are reported as invalid. [a11y/aria-valid-attr](/rules/a11y/aria-valid-attr) checks attribute names, [a11y/aria-valid-attr-value](/rules/a11y/aria-valid-attr-value) checks values for 26 attributes, and [a11y/aria-allowed-attr](/rules/a11y/aria-allowed-attr) catches two specific contradictions, such as an `aria-label` on a presentational element. [a11y/aria-required-attr](/rules/a11y/aria-required-attr), [a11y/aria-required-children](/rules/a11y/aria-required-children) and [a11y/aria-required-parent](/rules/a11y/aria-required-parent) check that roles have the states, children and parents they need. [a11y/aria-hidden-body](/rules/a11y/aria-hidden-body) and [a11y/aria-hidden-focus](/rules/a11y/aria-hidden-focus) catch hidden content that should not be. [a11y/duplicate-id-aria](/rules/a11y/duplicate-id-aria) finds ARIA references to missing or duplicate ids, and [a11y/aria-text](/rules/a11y/aria-text) finds focusable elements inside `role="text"`.

## How to fix it

Prefer the native element, and keep ARIA states in step with the visible state:

```html
<button aria-pressed="false" aria-controls="filters">Filters</button>
<div role="tablist" aria-label="Account settings">
  <button role="tab" aria-selected="true" aria-controls="profile">Profile</button>
</div>
```

Replace a `<div role="button">` with a `<button>` ([the roles fix](/rules/a11y/aria-roles#how-to-fix-it)). Use the literal values each attribute expects, such as `aria-expanded="false"` ([the values fix](/rules/a11y/aria-valid-attr-value#how-to-fix-it)). Use `aria-modal` on a dialog rather than `aria-hidden` on the body ([the hidden body fix](/rules/a11y/aria-hidden-body#how-to-fix-it)). Add `inert` to a hidden region that holds links ([the hidden focus fix](/rules/a11y/aria-hidden-focus#how-to-fix-it)).

## Related terms

- [Accessible name](/glossary/accessible-name): The name assistive technology announces for an element, computed from its content, label, aria-label or aria-labelledby.
- [WCAG](/glossary/wcag): The W3C's Web Content Accessibility Guidelines, organised as testable success criteria at levels A, AA and AAA; 2.2 is current.
- [Landmark regions](/glossary#landmark): The page regions (main, nav, header, footer) that screen reader users jump between, plus the skip link to main content.
