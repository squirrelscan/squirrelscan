Cloud audits are priced in **credits** - small integers, not dollars. Local audits never cost credits.

## Getting credits

| Source | Credits | Notes |
|--------|---------|-------|
| Free plan | 500/month | Every account, no card required; resets monthly on your signup date |
| Pro plan ($19/mo or $190/yr) | 3,000/month | Resets each billing period; unused monthly credits expire |
| Team plan ($29/seat/mo or $290/seat/yr) | 3,000/seat/month | Pooled across the org; see [Team plan](/cloud/team) for seat billing rules |
| Credit top-up (min $10) | 100 per $1 | Paid plan only; pick any amount; never expire |

Annual billing is 12 months for the price of 10. Your monthly credits still arrive every month; you just pay once a year.

Monthly credits are spent before purchased top-up credits. Subscribe and top up from the **Billing & Credits** page in the [dashboard](/dashboard).

Free, Pro, and Team run the **same** audit at the same price: the base charge includes every cloud service (AI analysis, editor's summary, blocking check, tech + site metadata, report publishing) on every plan. [Scheduled audits](/cloud/scheduled-audits) are on every plan: free re-audits one website weekly or monthly, Pro and Team re-audit every website daily. Pro and Team just grant more monthly credits and unlock top-ups, that daily cadence and extra scheduled sites, custom headers, and higher render concurrency - Team adds pooled credits, invites, and roles on top.

### Max pages per cloud audit

Audits triggered from the dashboard - on-demand ("Run now") and [scheduled](/cloud/scheduled-audits) - crawl up to a plan-based page ceiling:

| Plan | Max pages per cloud audit |
|------|---------------------------|
| Free | 500 |
| Pro | 2,000 |
| Team | 10,000 |

Free stays at 500 for a technical reason rather than a pricing one: free audits run on a smaller container, and a 10,000-page audit needs several gigabytes of memory to hold the crawl.

A crawl config above your plan's ceiling isn't an error - it's clamped automatically, the same way [`render_concurrency`](/configuration/cloud#render_concurrency) is. This limit is separate from the CLI's own crawl cap: `squirrel audit` run locally on your machine crawls up to **10,000 pages on every plan** - see [Crawl Limits](/configuration/crawler#max_pages).

If you're driving audits through the [REST API](/api/audits/create) or the [MCP server](/developers/mcp), a clamped run's response carries a `notice` field (`type: "page_limit_clamped"`, with the requested and applied page counts and an upgrade hint) so your integration or agent can surface it - the audit still runs normally either way.

## Pricing

Every signed-in audit has one flat price:

| Item | Cost | Notes |
|------|------|-------|
| Audit base | 50 per audit | covers every included service below |
| Audited page | 2 per page | every page the report shows as audited, however it was fetched: plain HTTP, a [cloud browser render](/cloud/rendering), the local or cloud render cache, a `304 Not Modified`, or a plain fetch after a render failed |
| External link check | 1 per link | cloud audits only: each distinct external destination the cloud checks, whatever status it returns |

A page is charged once per audit. Rendering it, serving it from a cache, or retrying a request never adds a second charge, and the same external link on twenty pages is one check. Run the audit again and it is charged again: it is a new audit.

The page count is the one in the report's coverage line ("Coverage: audited 12 of 12 known pages"), or its page count when there is no coverage line. A URL the crawl fetched but could not audit, such as a `404` kept for its broken-link finding or a `500`, is not an audited page. A cloud render paid for one while the audit ran is refunded when the audit completes, so an audit's page charge always matches the pages its report shows. A re-audit is only charged for the pages it fetched itself: pages a [smart audit](/configuration#smart-audits) carries forward from an earlier audit are not charged again.

Link checks are free in two cases: internal links (on the site you are auditing) always, and every link the CLI checks for an audit you run with `squirrel audit`. The external-link charge applies to [cloud audits](/guides/cloud-audits) with external link checking turned on, which is off by default.

The base includes everything else: AI page analysis ([`ai/llm-parsability`](/rules/ai/llm-parsability), [`ai/page-type-match`](/rules/ai/page-type-match)), [authority signals](/rules/eeat/authority-signals), the [Blocking check](/rules/adblock), [technology detection](/cloud/technologies), [site metadata](/cloud/site-metadata), the [editor's summary](/cloud/editor-summary), and publishing the report. None of these are charged separately.

Rendering does not change the price. An HTTP-only (`--http`) audit costs the same per page as a rendered one, so pick the render mode for accuracy, not to save credits.

Opt-in add-ons are the only extra charges:

| Add-on | Cost | Notes |
|--------|------|-------|
| Keyword gaps | 25 per audit | [`gaps/keywords`](/rules/gaps/keywords) (opt-in) |
| Content gaps | 25 per audit | [`gaps/content`](/rules/gaps/content) (opt-in) |
| Issue enrichment | 3 per issue | AI recommendations in the dashboard |
| Link render escalation | 2 per link | a WAF-blocked external link the CLI's [dead-link check](/rules/links/dead-links) retries in a cloud browser |

A 19-page audit costs **88 credits**: 50 base + 38 for its pages. A 100-page audit costs 250. A cloud audit of the same 19 pages that checks 7 distinct external links costs 95.

## Spend controls

Three guardrails keep an audit from spending more than you expect:

```toml squirrel.toml
[cloud]
max_credits_per_audit = 1000  # hard cap per audit; 0 = unlimited
confirm_threshold = 50        # estimates above this prompt before spending
enabled = true                # master switch for all cloud features
```

- **Per-audit cap** - if a full audit would cost more than `max_credits_per_audit`, the page limit comes down to what the cap covers (475 pages at the default of 1000) and the run tells you. Cloud enrichment past the cap is truncated deterministically and the remaining rules report `skipped` with reason `credit-cap-reached`.
- **Confirmation prompt** - in a terminal, an estimate above `confirm_threshold` asks before proceeding. Use `--yes` to skip prompts (e.g. in CI or agent workflows). Non-interactive runs proceed without prompting, bounded by the cap.
- **Master switch** - `enabled = false` turns off all cloud calls for the project.

See the [cloud configuration reference](/configuration/cloud) for all options.

## When credits run out

Nothing breaks. A signed-in audit needs at least 52 credits (the base plus one page) to start: below that, the CLI runs the audit locally instead and tells you so. Above that, an audit your balance can't fully cover is not refused and does not stop part-way: its page limit comes down to what the balance pays for (50 base + 2 per page, or 3 per page for a cloud audit that checks external links), and the run says how many pages it kept. Cloud audits started from the dashboard, the API, the MCP server, or a schedule work the same way. If credits still run out mid-audit, cloud rules report `skipped` with reason `insufficient-credits`, the audit completes with all local rules, and you see a single warning with a top-up link. If an audit fails after you were charged, the charge is automatically refunded.

A cloud audit gives its cloud analysis step (AI page analysis, authority signals, gap analysis, the raw vs rendered comparison and the rest) a time limit, so a slow provider cannot hold the audit up. If that limit is reached, every result that had already come back is kept and used by the rules, and the audit's spend lists exactly the calls that were charged, each once. Rules whose results had not come back report `skipped` with reason `service-unavailable`, and no new cloud call is started after the limit, so nothing more is charged for the audit's enrichment.

Every credit warning the CLI prints states what the run would have cost, the credits you have left, the date your monthly credits reset, and an upgrade link: the notice when a low balance shrinks an audit's page limit, the out-of-credits notice when a run cannot be tracked, and the low-balance footer after one. `squirrel credits` shows the same balance, reset date and link.

That link is scoped to the organization that ran out, so it opens checkout for that organization rather than whichever one your browser used last. Credits are not shared between organizations, so the distinction matters: topping up the wrong one leaves the blocked audit blocked. The link works signed out, and carries the organization through the login. The MCP server returns the same facts as fields on its `run_audit` response, so an agent can relay them without a second call.

One exception: `squirrel credits --upgrade` answers before reading your balance, so you can reach the upgrade page without logging in first. It prints the general upgrade URL rather than an organization-scoped one.
