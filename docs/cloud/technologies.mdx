Every audit, local or cloud, fingerprints the technologies a site is built with - **438 signatures** across CMS and AI app builders, WordPress plugins and managed WordPress hosts, frameworks, CDN & hosting, analytics, tag managers, payment processors, chat widgets, fonts, security/consent tools, and backend and auth services - and surfaces them as a dedicated **Technologies** section in the report.

It's informational: technology detection **never affects your health score**. It's there to give you - and your agent - context about what you're auditing.

## What it detects

Detection runs against response headers, HTML, inline and external scripts, cookies, and meta tags, and reports versions where they can be determined. The crawler keeps every response header a signature reads, such as `X-CDN`, `X-Sucuri-ID` or `Via` (each value cut to 512 characters), so a header-only signature matches in a local audit too. A header a signature only checks for presence, such as a request id or a bot protection token, is kept as a marker, not its value. In an audit the CLI runs, a cookie is matched by its name: only the names of the cookies a page sets are passed to detection, never their values. A page squirrel stored before it kept these headers, and that the crawl cache reuses, is read without them until it is fetched again.

## Local and cloud scans

There is one detector, with one set of fingerprints, and two ways it runs. A report says which one produced its Technologies section (`technologies.source` in JSON: `local` or `cloud`).

| | Local scan | Cloud scan |
|---|---|---|
| Account and credits | None: free, works logged out | Signed in; included in the audit base |
| Reads | The pages the crawl already fetched, their response headers and the first-party bundles it already downloaded | The same bytes, sent to the cloud service |
| Extra requests | None | None |
| Change history | None: no "added" or "removed" since the last scan | Compared with the previous scan of the domain, with the first scan marked |
| Runs when | Every audit where the cloud scan did not run (logged out, offline, Quick) | Signed-in cloud audits |

A local scan keeps no history, so its section never says "No changes since last scan" and shows where the list came from instead. The cloud scan is the one that stores results per domain and reports the difference between scans.

### Why a result can show little more than headers

A local scan can only match what the crawl fetched. When a run lists the server and CDN and little else, check these in order:

- **Page sample.** Detection reads the home page first and up to 11 more crawled HTML pages. A Quick audit crawls the seed URL and the sitemap only, and `-m` caps the pages crawled, so a stack that only appears on pages that were not crawled is not seen.
- **Script bodies.** A signature that matches script content needs the body of a script, and the only bodies read are first-party JavaScript the crawl already downloaded (see [Script bundles](#script-bundles)). A third-party script is detected by its URL, never by its body, and an app whose stack lives only in its bundle was invisible before v0.0.140. `bundle_bytes = 0` switches bodies off.
- **Script URLs.** A signature that matches a script URL reads every `<script src>` on the page and, since the local scan was aligned with the cloud one, up to 40 stylesheet and preload `<link href>` URLs a page, with well-known platform paths such as `/wp-content/plugins/` listed first. A signature that matches a script URL also reads the page's markup (its tags, and the text of its `<script>` elements), so the URL an inline loader writes, such as Microsoft Clarity's standard snippet, is found whether or not the page has script bodies attached; the result does not depend on the byte caps. Text between tags is not read, so a vendor named only in a paragraph is not detected as its script. A URL that only appears in a CSS `@import`, in script-built markup or after a client-side render is not in the fetched HTML, and `--http` does no browser rendering.
- **Signatures.** A technology with no fingerprint is not reported. The fingerprints are written from first-party research, never imported from a third-party catalog.

## Script bundles

A single page app (Vite, Lovable, Bolt, Next.js) ships an almost empty HTML shell, and its libraries live in the script bundles. Detection reads each first-party bundle the crawl fetched whole (the free local scan, up to 8 MB; a signed-in audit's cloud scan sends only the first 64 KB, see below), so a backend or auth service that only a bundle calls is still found: Supabase (a project URL passed with a key, or a quoted project URL anywhere in a bundle that ships supabase-js, whatever the key format), Firebase (the `authDomain` or `storageBucket` of the app config) and Clerk (the `publishableKey` handed to the provider).

A bundled app's own code sits after the framework it ships with, so a bundle bigger than its cap is not read from the top alone. Each bundle gets its first 16 KB, then the text around the vendor markers (a `.supabase.co` URL or supabase-js's own notice and storage-key strings, a `.firebaseapp.com` domain, a `pk_` key) and the end of the file, then more of its start while the cap lasts.

- It uses the bytes the crawl already fetched for the secret rules. No extra request is made, on the cloud or the local path.
- A bundle counts only where it is real code. A product named in a comment, in a string, or as a placeholder (`your-project`) does not match.
- The local scan sends nothing anywhere, so it reads every bundle whole up to its caps: 8 MB per bundle, 32 MB per page and 64 MB per audit. The crawl itself fetches a script only up to 5 MB, and only some of a page's scripts (the first 10 to 50), so in practice a bundle over 5 MB, or a script past those, is never read. That is the script fetch limit, not a detection cap, and the report counts those scripts in `truncated` (`script-too-large`, `script-limit`, below). A bundle that fits is matched from the first byte to the last, wherever the fingerprint sits. A script past a cap keeps its URL; the report says so (below). Change the per-bundle cap in `squirrel.toml`, or set it to `0` to match the page HTML and script URLs only:

```toml
[tech_detect]
bundle_bytes = 8388608   # 0 to 16777216 (16 MiB); unset = 8 MiB locally, 64 KB sent to the cloud
```

| Limit | Default | Where |
|---|---|---|
| Bytes read per bundle | 8 MB local, 64 KB cloud payload | `[tech_detect] bundle_bytes` (sets both) |
| Bytes read per page | 32 MB local, 512 KB cloud payload | fixed |
| Bytes read per audit | 64 MB local, 1 MB cloud payload | fixed |
| Time per page | 30 seconds local | fixed |
| Candidate matches a detector inspects inside strings or comments before the real one | 64 | fixed |

- A bundle past `bundle_bytes` (only when you lower it) is not read from the top alone: the first 16 KB, then the text around the vendor markers and the end of the file, then more of its start while the cap lasts.
- When a byte cap or the time budget cut the local scan short, the report says so instead of listing fewer technologies without a word. The JSON report carries `technologies.truncated` with `reasons` (`bundle-bytes`, `page-bytes`, `audit-bytes`, `time-budget`, `script-too-large`, `script-limit`) and the number of `scripts` read in part or not at all (`script-too-large` counts first-party scripts the crawl dropped for being over its 5 MB fetch cap, `script-limit` the first-party scripts the page references that the audit's script limit left unfetched: it fetches a share of the page count, between 10 and 50); the text, markdown, llm and xml reports say it beside the list. A scan that read everything has no `truncated` field. A signed-in audit shows the cloud section, built from the 64 KB payload caps, and says what those caps cut in the same `truncated` field (never the time budget); the free local scan, which reads whole bundles, runs when the cloud scan is off or skipped. A scan that detects nothing has no technologies section unless a cap or the budget cut it short: then the section is there with an empty list and `truncated`, so the report does not read as a site that runs nothing. Such an empty section is not synced to the dashboard, which would clear the technologies an earlier scan found.

- Only first-party scripts the crawl already fetched are read: those on the audited host or its subdomains (a CDN on another domain is not), within the crawl's script fetch limits, and only JavaScript bodies under 5 MB.
- On a signed-in audit the bundle text sent to the cloud detection service is at most 1 MB per audit, 64 KB per bundle unless you raise `bundle_bytes`. Bundles can contain keys, so set `bundle_bytes = 0` to send none.
- A key kept in a variable and passed by name (`publishableKey: key`) is not matched; a Clerk key is recognised only where it is written out next to `publishableKey`.
- A local scan that runs long on one page stops at its 30 second budget and reports what it found so far, with `truncated.reasons` containing `time-budget`. The scan of a page the cloud service gets is stopped at 5 seconds.

### WordPress plugins and hosts

A WordPress plugin is recognised by something it writes into the page: an asset URL under `wp-content/plugins/<slug>/` (or the cache directory it fills) on a script, stylesheet or image tag, the HTML comment it adds (`This website is like a Rocket` for WP Rocket, `Performance optimized by W3 Total Cache`, the Yoast SEO and Rank Math comments), or its own JSON-LD block (`yoast-schema-graph`, `rank-math-schema`, `aioseo-schema`). Its name in page text, in a code sample or in a link does not count. A managed host is recognised by the response header it sets (`x-kinsta-cache`, `x-powered-by: WP Engine`, `x-sg-cache`), reported as `header:<name>`. LiteSpeed Cache is recognised from its page comment or plugin assets, not from the `x-litespeed-cache` header, which any LiteSpeed-cached site sends. Pressable, WordPress VIP, SiteGround and Cloudways report at medium or low confidence because their headers are the least documented.

## When it runs

- **Logged in** - detection runs automatically as part of every cloud audit. One detection per domain, regardless of how many pages you crawl.
- **Logged out or `--offline`** - the cloud detection is skipped, like every other cloud feature. The CLI runs the same signatures over the crawled pages instead, so the Technologies section still appears, without the change history.

Detection is best-effort and never fails the audit: if the service is unavailable, the Technologies section is simply omitted and you're not charged.

## Cost

**Included in the audit base charge** - a single detection per domain, not per page. See [Credits & Pricing](/cloud/credits).

## Change history

squirrelscan keeps a per-domain record of what it has detected over time, so you can see when a site adopts or drops a technology - a CMS migration, a new analytics vendor, a CDN switch.

- **Current snapshot** - free, shown on every audit. The report notes whether anything changed since the last scan ("No changes since last scan").
- **Historical timeline** - the full add / remove history for a domain is available to any signed-in account, free or Pro, in the [dashboard](/dashboard).

<Note>Technology data is keyed by domain and shared: the current detected stack for a domain is the same for everyone who audits it, so the snapshot stays fast and consistent across re-audits.</Note>
