A plain HTTP fetch is fast and accurate for server-rendered sites - but sites that build their content with JavaScript (SPAs, client-side frameworks) can look nearly empty to it, which skews every content rule.

Cloud browser rendering fixes that: each page is loaded in a **real headless browser** in the cloud, and the fully rendered DOM is returned to your local crawler. Everything downstream - parsing, rules, reports - works exactly as it does with plain HTTP, just on the post-JavaScript HTML.

<Note>Looking for setup instructions? See the [browser rendering guide](/guides/browser-rendering). This page explains how the service behaves.</Note>

## What still comes from your machine

Only the rendering runs in the cloud. Your machine still talks to the audited site, so the site sees your IP address for these requests, and a site that blocks the cloud browser can still be reached from your machine. With `--render-mode all` (or `--render`) and with `auto`, your machine sends:

- **A plain request for each page, beside the render.** On a first visit, or with `--refresh`, the plain request runs at the same time as the render and is only used to fingerprint the page's source. On a later visit it goes first, as a conditional request, to decide whether the page changed and needs rendering again.
- **A plain request for any page the cloud could not render.** If a render fails, times out, or the site blocks the cloud browser (a 401, 403, 429 or 503, or a bot-challenge page), the page is fetched from your machine instead of being left out.
- **The start URL's reachability check and redirects, and the TLS certificate check** of the audited host.
- **`robots.txt`, the sitemaps, and the `llms.txt`, well-known, agent-access and licensing files.**
- **First-party scripts, and the stylesheets, images and PDFs** the asset checks measure.
- **Internal link targets** the crawl did not fetch.
- **External links**, apart from the ones the cloud's link checker answers: the cloud is asked first, and any link it does not answer, and every link to a private address, is requested from your machine.
- **The soft-404 confirmation and the cloaking probes,** which request pages again.

`--http` sends all of these, and every page, from your machine, and nothing runs in the cloud. Pages that `auto` does not render are plain requests from your machine too. A mode where the cloud makes every request to the site is not part of this release.

## When it runs

Rendering follows your login state and the [audit level](/guides/audit-levels) by default:

- **Logged in** - audits render in the cloud browser automatically, with no prompt. The level decides which pages: quick renders only the pages that need JavaScript (`auto`), surface and full render every page (`all`). The first such run prints a one-line note about what audits cost.
- **Logged out or `--offline`** - plain HTTP, no credits.
- **Logged in with `--http`, or rendering turned off in `[cloud]`** - plain HTTP, but the audit is still billed: 50 credits plus 2 per audited page.

Override the default any time:

| Want | How |
|------|-----|
| Plain HTTP for one run | `squirrel audit <url> --http` |
| Render for one run | `squirrel audit <url> --render` |
| Always plain HTTP for a project | `rendering = "http"` in `[cloud]` |
| Always render for a project | `rendering = "browser"` in `[cloud]` |

Flags win over config, and config wins over the auto default. Non-interactive runs (CI, agents, pipes) follow the same rules: they never prompt, and signed in they render by default.

## Cost

Rendering costs nothing extra. A signed-in audit costs 50 credits plus **2 per audited page**, and a rendered page is one audited page: the same 2 credits as a page fetched over plain HTTP, a page served from the render cache, or a page that fell back to plain HTTP after its render failed. A 100-page audit costs 250 credits in total, rendered or not, so mind your [per-audit cap](/cloud/credits#spend-controls): the default cap of 1000 covers about 475 pages. The crawl progress line shows what the rendered pages have been charged so far (the 50-credit base and the plain-HTTP pages are settled when the audit completes, and appear in the final total):

```text
Crawling (cloud-rendered) 34/100 · ~68 credits
```

## Fallback behavior

Rendering is best-effort and degrades gracefully:

- **Single page fails or times out** - that page falls back to plain HTTP; the crawl continues rendering the rest.
- **Out of credits, auth error, or service outage** - the crawler switches permanently to plain HTTP for the remainder of the crawl, prints a one-line warning, and notes the fallback in the report metadata.

A render failure never fails the audit.

## When to use it

| Site | Recommendation |
|------|----------------|
| Server-rendered (most CMS, SSR frameworks, static sites) | Plain HTTP (`--http`) is enough - rendering adds crawl time, not accuracy |
| Client-side SPA (React/Vue/Angular without SSR) | Browser rendering |
| Mixed - mostly SSR with a few JS-dependent pages | Try plain HTTP first; if content rules report thin/missing content on pages you know have content, switch |

A quick tell: run `squirrel audit` normally, and if word counts or headings look implausibly low on pages that render fine in your browser, the site needs rendering.
